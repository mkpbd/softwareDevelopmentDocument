### ১) Unit of Work কি? (এক লাইনে সংজ্ঞা)

**সংজ্ঞা:** Unit of Work হলো এমন একটি প্যাটার্ন যা নিশ্চিত করে যে, ডাটাবেসে করা অনেকগুলো পরিবর্তন হয় **"একসাথে সেভ"** হবে, আর না হয় কোনো সমস্যা হলে **"কোনোটাই সেভ হবে না"**।

> 🍎 **মজার এনালজি:** মনে করো তুমি অনলাইনে শপিং করছো। কার্টে জুতা, মোজা আর ঘড়ি যোগ করলে। চেকআউট বাটনে চাপলে সব একসাথে অর্ডার হবে (All Success), অথবা পেমেন্ট ফেইল হলে কোনোটাই অর্ডার হবে না (All Fail)। একটা মোজা অর্ডার হলো কিন্তু জুতা হলো না—এমনটা হবে না! এটাই Unit of Work.

### ২) এটি কবে ব্যবহার করা উচিত? (Use-cases)

আমরা তখনই এটি ব্যবহার করবো যখন আমাদের **একাধিক টেবিল বা রিপোজিটরিতে** একসাথে কাজ করতে হয়।

যেমন:
1.  **Bank Transfer:** আমার একাউন্ট থেকে টাকা কমবে (Update Account A) **এবং** তোমার একাউন্টে টাকা বাড়বে (Update Account B)। দুইটা কাজই সফল হতে হবে।
2.  **E-commerce Order:** নতুন অর্ডার তৈরি হবে (Insert Order) **এবং** প্রোডাক্টের স্টক কমে যাবে (Update Inventory)।
3.  **Registration:** ইউজার টেবিলে ডাটা যাবে **এবং** ওয়েলকাম ইমেইল লগ টেবিলে এন্ট্রি হবে।

### ৩) এটি Repository Pattern এর সাথে কিভাবে কাজ করে?

Repository Pattern হলো "স্পেশালিস্ট কর্মী" আর Unit of Work হলো "ম্যানেজার"।

*   **Repository:** এরা শুধু নিজেদের টেবিল চিনে। `ProductRepository` শুধু প্রোডাক্ট নিয়ে কাজ করে, `OrderRepository` শুধু অর্ডার নিয়ে।
*   **Unit of Work:** এর কাছে সব রিপোজিটরির এক্সেস থাকে এবং সে একটি `DbContext` শেয়ার করে সবার সাথে।

> 🍳 **কিচেন এনালজি:**
> *   **Repository:** তোমার কিচেনের আলাদা আলাদা শেফ। একজন শুধু সবজি কাটে (VegetableRepo), একজন শুধু মাংস গ্রিল করে (MeatRepo)।
> *   **Unit of Work:** হলো **হেড শেফ**। সবজি ওয়ালা সবজি কেটে দিলো, মাংস ওয়ালা মাংস দিলো—কিন্তু কাস্টমারের টেবিলে খাবারটা যাবে কি না, সেটা ফাইনাল ডিসিশন নেয় হেড শেফ। সে যদি দেখে সব ঠিক আছে, তবেই বলবে "সার্ভ করো" (`SaveChanges`), আর যদি দেখে মাংস পুড়ে গেছে, তবে বলবে "পুরো ডিশ বাতিল, আবার করো" (`Rollback`)।

### ৪) C# (.NET 7/8) কোড উদাহরণ

চলো এবার কোডে হাত দেই। আমরা দেখবো কিভাবে একটি **অর্ডার প্লেস** করার সময় **ইনভেন্টরি** আপডেট হয়।

#### ধাপ ১: ইন্টারফেস তৈরি (IUnitOfWork)
এটি হলো হেড শেফের কাজের লিস্ট (Contract)।

```csharp
using Microsoft.EntityFrameworkCore.Storage;

public interface IUnitOfWork : IDisposable
{
    // রিপোজিটরিগুলোর এক্সেস এখানে থাকবে
    IProductRepository Products { get; }
    IOrderRepository Orders { get; }

    // সব কাজ শেষে ডাটাবেসে সেভ করার মেথড
    int Complete();
    
    // ট্রানজ্যাকশন কন্ট্রোল (অপশনাল কিন্তু পাওয়ারফুল)
    IDbContextTransaction BeginTransaction();
}
```

#### ধাপ ২: ক্লাস ইমপ্লিমেন্টেশন (UnitOfWork)
এখানে আমরা আসল `DbContext` ব্যবহার করবো।

```csharp
public class UnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _context;
    
    // রিপোজিটরিগুলো ইনিশিলাইজ করছি
    public IProductRepository Products { get; private set; }
    public IOrderRepository Orders { get; private set; }

    public UnitOfWork(AppDbContext context)
    {
        _context = context;
        // একই Context সবার সাথে শেয়ার করা হচ্ছে (খুব গুরুত্বপূর্ণ!)
        Products = new ProductRepository(_context);
        Orders = new OrderRepository(_context);
    }

    public int Complete()
    {
        // এই এক লাইনেই সব ম্যাজিক হয়! সব রিপোজিটরির চেঞ্জ একসাথে সেভ হবে।
        return _context.SaveChanges();
    }

    public IDbContextTransaction BeginTransaction()
    {
        return _context.Database.BeginTransaction();
    }

    public void Dispose()
    {
        _context.Dispose();
    }
}
```

#### ধাপ ৩: ব্যবহার (Transaction সহ)
এখন দেখবো কিভাবে সার্ভিসে এটি ব্যবহার করে সেইফলি ডাটা সেভ করা যায়।

> 🏦 **সিনারিও:** কাস্টমার অর্ডার করবে, কিন্তু যদি স্টক আপডেট করতে গিয়ে এরর হয়, তাহলে অর্ডারও বাতিল হয়ে যাবে।

```csharp
public class OrderService
{
    private readonly IUnitOfWork _unitOfWork;

    public OrderService(IUnitOfWork unitOfWork)
    {
        _unitOfWork = unitOfWork;
    }

    public void PlaceOrder(Order newOrder, int productId, int quantity)
    {
        // ১. ট্রানজ্যাকশন শুরু (ম্যাজিক বক্স খোলা হলো)
        using var transaction = _unitOfWork.BeginTransaction();

        try
        {
            // ২. প্রোডাক্ট রিপোজিটরিতে কাজ
            var product = _unitOfWork.Products.GetById(productId);
            if (product.Stock < quantity)
                throw new Exception("স্টক শেষ ভাই!");

            product.Stock -= quantity; // স্টক কমানো হলো (মেমোরিতে চেঞ্জ হলো)

            // ৩. অর্ডার রিপোজিটরিতে কাজ
            _unitOfWork.Orders.Add(newOrder); // অর্ডার অ্যাড হলো (মেমোরিতে)

            // ৪. সব কাজ শেষ? এবার ডাটাবেসে হিট করো!
            _unitOfWork.Complete(); 

            // ৫. সবকিছু সফল হলে ট্রানজ্যাকশন কমিট (Commit)
            transaction.Commit();
            
            Console.WriteLine("অর্ডার সাকসেসফুল! পার্টি হবে! 🎉");
        }
        catch (Exception ex)
        {
            // ৬. ওহ নো! কোনো এরর হয়েছে। সব আগের মতো করে দাও (Rollback)
            transaction.Rollback();
            Console.WriteLine($"অর্ডার ফেইল্ড! কারণ: {ex.Message} 😢");
        }
    }
}
```

### 🔥 শেষ কথা ও Best Practices (টিপস)

Unit of Work ব্যবহার করলে তোমার কোড অনেক বেশি নিরাপদ থাকে। যাওয়ার আগে ৩টি গোল্ডেন রুল মনে রাখবে:

1.  **একই DbContext শেয়ার করো:** নিশ্চিত করবে যে Unit of Work ক্লাসের ভেতরে যেই `DbContext` আছে, সেটাই যেন সব রিপোজিটরিতে পাস করা হয়। আলাদা Context হলে ট্রানজ্যাকশন কাজ করবে না।
2.  **Controller এ লজিক লিখবে না:** `UnitOfWork` সবসময় Service Layer-এ ব্যবহার করবে (যেমন উপরের `OrderService` এ করেছি), Controller-এ নয়। এতে কোড ক্লিন থাকে।
3.  **Dispose করতে ভুলো না:** কাজ শেষ হলে `Dispose()` কল করা উচিত (অথবা Dependency Injection কন্টেইনারকে লাইফটাইম ম্যানেজ করতে দাও), যাতে মেমোরি লিক না হয়।

আশা করি কনসেপ্টটা এখন পানির মতো পরিষ্কার! হ্যাপি কোডিং! 🚀

# আর্কিটেকচারাল গাইড: Unit of Work এবং Repository Pattern

## ১. সংজ্ঞা (Definition)
**Unit of Work** হলো একটি ডিজাইন প্যাটার্ন যা বিজনেস ট্রানজ্যাকশনের সময় একাধিক ডাটাবেস অপারেশনকে (Insert, Update, Delete) একটি একক গ্রুপ বা "ইউনিট" হিসেবে ট্রিট করে।

**এক কথায় সংজ্ঞা:**
> "Unit of Work হলো এমন একটি প্যাটার্ন যা নিশ্চিত করে যে, একাধিক রিপোজিটরির পরিবর্তন হয় **একসাথে ডাটাবেসে সেভ হবে (Commit)**, অথবা কোনো সমস্যা হলে **সব বাতিল হবে (Rollback)**।"

---

## ২. কেন আমরা এটি ব্যবহার করি (Why We Use It)
সফটওয়্যার ডেভেলপমেন্টে ডাটা ইন্টিগ্রিটি (Data Integrity) বজায় রাখা সবচেয়ে গুরুত্বপূর্ণ। আমরা এটি ব্যবহার করি কারণ:

*   **Consistency (সামঞ্জস্যতা):** যখন একটি বিজনেস লজিকের জন্য একাধিক টেবিলে ডাটা পরিবর্তনের প্রয়োজন হয়।
*   **Transaction Management:** ম্যানুয়ালি বারবার ট্রানজ্যাকশন ওপেন এবং ক্লোজ করার ঝামেলা দূর করে।
*   **Code Cleanliness:** `DbContext.SaveChanges()` বারবার কল না করে, একবার কল করেই সব কাজ শেষ করা যায়।
*   **Race Condition রোধ:** একাধিক রিকোয়েস্টের মধ্যে ডাটা কনফ্লিক্ট কমায়।

**Use-Case:** ই-কমার্স সাইটে অর্ডার প্লেস করা। একই সময়ে `Order` টেবিলে ডাটা ইনসার্ট হবে এবং `Product` টেবিল থেকে স্টক (Stock) আপডেট হবে।

---

## ৩. কার্যপদ্ধতি (How It Works)

Unit of Work মূলত একটি **"সেন্ট্রাল বাফার"** হিসেবে কাজ করে। যখন আমরা রিপোজিটরি ব্যবহার করে ডাটা অ্যাড বা আপডেট করি, তখন তা সরাসরি ডাটাবেসে যায় না; বরং মেমোরিতে জমা থাকে। সব শেষে যখন `Commit()` কল করা হয়, তখন সব চেঞ্জেস একসাথে ডাটাবেসে যায়।

**টেক্সট-বেসড ডায়াগ্রাম:**

```text
[User Request] 
      ↓
[Service Layer] (এখানে লজিক লেখা হয়)
      ↓
[Unit Of Work] (শুরু হলো)
      ├──> [Repository A] --> মেমোরিতে ডাটা অ্যাড করলো
      ├──> [Repository B] --> মেমোরিতে ডাটা আপডেট করলো
      ↓
[Unit Of Work] --> Commit() কল করলো
      ↓
[DbContext] --> SaveChanges()
      ↓
[Database] --> ফাইনাল ডাটা সেভ হলো
```

## ৪. Unit of Work এবং Repository Pattern এর সম্পর্ক

Repository এবং Unit of Work একে অপরের পরিপূরক। Repository বিজনেস লজিক থেকে ডাটা এক্সেস লজিক (Data Access Logic) আলাদা করে, আর Unit of Work সেই পরিবর্তনগুলো ম্যানেজ করে।

💡 **সহজ এনালজি:**
> **Repository হলো অফিসের বিভিন্ন বিভাগের কর্মী:** কেউ সেলস দেখে, কেউ ইনভেন্টরি দেখে। তারা সারাদিন কাজ করে ফাইল রেডি রাখে।
>
> **Unit of Work হলো অফিসের জেনারেল ম্যানেজার:** দিন শেষে ম্যানেজার সব ফাইল চেক করে একবারেই সাইন (Commit) করেন। যদি কোনো ফাইলে বড় ভুল থাকে, তবে তিনি পুরো দিনের কাজ বাতিল (Rollback) করে আবার ঠিক করতে বলেন।

## ৫. .NET / C# ইমপ্লিমেন্টেশন

নিচে .NET 8 এবং Entity Framework Core ব্যবহার করে একটি কমপ্লিট উদাহরণ দেওয়া হলো।

### ৫.১. ইন্টারফেস (IUnitOfWork)
প্রথমে আমরা কন্ট্রাক্ট ডিফাইন করবো।

```csharp
using Microsoft.EntityFrameworkCore.Storage;

public interface IUnitOfWork : IDisposable
{
    // রিপোজিটরিগুলোর এক্সেস পয়েন্ট
    IProductRepository Products { get; }
    IOrderRepository Orders { get; }

    // ডাটাবেসে সেভ করার মেথড
    Task<int> CommitAsync();

    // ট্রানজ্যাকশন রোলব্যাক করার মেথড (প্রয়োজন সাপেক্ষে)
    Task RollbackAsync();
}
```

### ৫.২. মেইন ক্লাস (UnitOfWork Implementation)
এখানে আমরা `DbContext` ইনজেক্ট করবো।

```csharp
public class UnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _context;
    private IDbContextTransaction _objTran;

    // রিপোজিটরি প্রপার্টি
    public IProductRepository Products { get; private set; }
    public IOrderRepository Orders { get; private set; }

    public UnitOfWork(AppDbContext context)
    {
        _context = context;
        // রিপোজিটরি ইনিশিলাইজেশন
        Products = new ProductRepository(_context);
        Orders = new OrderRepository(_context);
    }

    public async Task<int> CommitAsync()
    {
        // ১. ট্রানজ্যাকশন শুরু
        _objTran = await _context.Database.BeginTransactionAsync();
        
        try
        {
            // ২. ডাটাবেসে সেভ করা
            var result = await _context.SaveChangesAsync();
            
            // ৩. সব ঠিক থাকলে পার্মানেন্টলি কমিট করা
            await _objTran.CommitAsync();
            return result;
        }
        catch
        {
            // ৪. কোনো এরর হলে রোলব্যাক করা
            await RollbackAsync();
            throw;
        }
    }

    public async Task RollbackAsync()
    {
        if (_objTran != null)
        {
            await _objTran.RollbackAsync();
            await _objTran.DisposeAsync();
        }
    }

    public void Dispose()
    {
        _context.Dispose();
    }
}
```

### ৫.৩. সার্ভিস লেয়ারে ব্যবহার (Service Usage)
এটিই আসল জায়গা যেখানে আমরা প্যাটার্নটির ম্যাজিক দেখবো।

```csharp
public class OrderService
{
    private readonly IUnitOfWork _unitOfWork;

    public OrderService(IUnitOfWork unitOfWork)
    {
        _unitOfWork = unitOfWork;
    }

    public async Task PlaceOrderAsync(OrderDto orderDto)
    {
        try
        {
            // স্টেপ ১: প্রোডাক্ট চেক এবং আপডেট (Repository 1)
            var product = await _unitOfWork.Products.GetByIdAsync(orderDto.ProductId);
            
            if (product.Stock < orderDto.Quantity)
                throw new Exception("Insufficient Stock!");

            product.Stock -= orderDto.Quantity; // মেমোরিতে আপডেট হলো

            // স্টেপ ২: অর্ডার তৈরি (Repository 2)
            var newOrder = new Order
            {
                ProductId = orderDto.ProductId,
                Quantity = orderDto.Quantity,
                OrderDate = DateTime.UtcNow
            };
            
            await _unitOfWork.Orders.AddAsync(newOrder); // মেমোরিতে অ্যাড হলো

            // স্টেপ ৩: ফাইনাল কমিট (Unit of Work)
            // এখানে ডাটাবেসে হিট হবে এবং ট্রানজ্যাকশন হ্যান্ডেল হবে
            await _unitOfWork.CommitAsync();
            
            Console.WriteLine("Order placed successfully!");
        }
        catch (Exception ex)
        {
            // স্টেপ ৪: অটোমেটিক রোলব্যাক হবে (CommitAsync এর catch ব্লকের কারণে)
            // ইউজারকে এরর মেসেজ পাঠানো
            Console.WriteLine($"Error: {ex.Message}");
            throw;
        }
    }
}
```

## ৬. ট্রানজ্যাকশন হ্যান্ডলিং (Transaction Handling)

Unit of Work এর মূল শক্তি হলো ট্রানজ্যাকশন কন্ট্রোল।

1.  **Commit:** `CommitAsync()` মেথড কল করার আগ পর্যন্ত ডাটাবেসে কোনো পরিবর্তন স্থায়ী হয় না। EF Core এর `ChangeTracker` সব পরিবর্তন ট্র্যাক করে রাখে।
2.  **Rollback:** যদি `SaveChanges` বা `Commit` করার সময় কোনো এরর হয় (যেমন: নেটওয়ার্ক ফেইল, কনস্ট্রেইন্ট ভায়োলেশন), তবে `RollbackAsync()` মেথড আগের অবস্থায় ডাটাবেসকে ফিরিয়ে আনে।
3.  **Partial Update Prevention:** এই প্যাটার্ন নিশ্চিত করে যে, টাকা কাটবে কিন্তু প্রোডাক্ট পাবে না—এমন ঘটনা যেন কখনো না ঘটে।

## ৭. ডিপেন্ডেন্সি ইনজেকশন (Dependency Injection - DI)

`Program.cs` ফাইলে Unit of Work রেজিস্ট্রেশন খুবই গুরুত্বপূর্ণ।

```csharp
// Program.cs

// DbContext রেজিস্ট্রেশন
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("DefaultConnection")));

// Repositories এবং UnitOfWork রেজিস্ট্রেশন
// এটি Scoped হতে হবে কারণ DbContext নিজেও Scoped লাইফটাইম ব্যবহার করে।
builder.Services.AddScoped<IUnitOfWork, UnitOfWork>();
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
```

*   **Scoped Lifetime:** এর মানে হলো একটি HTTP রিকোয়েস্টের জন্য একটিই `UnitOfWork` এবং `DbContext` অবজেক্ট তৈরি হবে। পুরো রিকোয়েস্টে সেই একই অবজেক্ট শেয়ার হবে।

## ৮. বেস্ট প্র্যাকটিস (Best Practices & Recommendations)

একজন আর্কিটেক্ট হিসেবে এই গাইডলাইনগুলো মেনে চলার পরামর্শ দিচ্ছি:

*   ✅ **Scoped Lifetime ব্যবহার করুন:** `Transient` বা `Singleton` হিসেবে `UnitOfWork` রেজিস্টার করবেন না। এতে ডাটা কন্সিস্টেন্সি নষ্ট হতে পারে।
*   ✅ **Service Layer-এ লজিক রাখুন:** `UnitOfWork` সরাসরি Controller-এ ব্যবহার না করে Service Layer-এর মাধ্যমে ব্যবহার করুন।
*   ✅ **Async/Await ব্যবহার করুন:** I/O অপারেশনের জন্য সবসময় `Async` মেথড ব্যবহার করুন (যেমন `SaveChangesAsync`) যাতে অ্যাপ্লিকেশনের পারফরম্যান্স ভালো থাকে।
*   ✅ **Read-Only অপারেশনে সতর্কতা:** শুধুমাত্র ডাটা পড়ার জন্য (GET Request) সবসময় Unit of Work বা ট্রানজ্যাকশন ব্যবহারের প্রয়োজন নেই। প্রয়োজনে `AsNoTracking()` ব্যবহার করুন।
*   ✅ **Dispose নিশ্চিত করুন:** `IDisposable` ইমপ্লিমেন্ট করা জরুরি যাতে মেমোরি লিক না হয়।

---

## ৯. যা এড়িয়ে চলবেন (Anti-patterns / Pitfalls)

*   ❌ **Unit of Work in Controller:** কন্ট্রোলারে বিজনেস লজিক এবং ট্রানজ্যাকশন হ্যান্ডলিং করবেন না। এটি "Separation of Concerns" প্রিন্সিপাল ব্রেক করে।
*   ❌ **Massive Unit of Work:** অ্যাপ্লিকেশনের সব (৫০-১০০) রিপোজিটরি একটি `UnitOfWork` ক্লাসে ইনজেক্ট করবেন না। প্রয়োজনে মডিউল ভিত্তিক (যেমন: `SalesUnitOfWork`, `HRUnitOfWork`) আলাদা করুন।
*   ❌ **Mixing Contexts:** একাধিক আলাদা `DbContext` কে একটি Unit of Work এর মধ্যে জোর করে মেশানোর চেষ্টা করবেন না (যদি না ডিস্ট্রিবিউটেড ট্রানজ্যাকশন প্রয়োজন হয়)।

---

## ১০. সারসংক্ষেপ (Final Summary)

*   **Unit of Work** হলো ডাটাবেস ট্রানজ্যাকশনের একটি বিশ্বস্ত ম্যানেজার।
*   এটি নিশ্চিত করে **"সব হবে, নয়তো কিছুই হবে না"** (Atomicity)।
*   এটি **Repository Pattern** এর সাথে মিলে কোডকে মডুলার এবং টেস্টেবল করে।
*   **Scoped Lifetime** এবং **Dependency Injection** এর সঠিক ব্যবহার এখানে অপরিহার্য।
*   **বাস্তব উদাহরণ:** ব্যাংকিং অ্যাপে এক একাউন্ট থেকে ডেবিট এবং অন্য একাউন্টে ক্রেডিট হওয়া; অথবা ইনভয়েস জেনারেট হওয়ার সাথে সাথে ইনভেন্টরি কমে যাওয়া।

এই ডকুমেন্টেশনটি অনুসরণ করলে আপনার অ্যাপ্লিকেশনের ডাটা লেয়ার হবে **নিরাপদ, স্কেলেবল এবং প্রফেশনাল**।

আগের পদ্ধতিতে আমাদের `UnitOfWork` ক্লাসে প্রতিটি রিপোজিটরির জন্য আলাদা প্রপার্টি লিখতে হচ্ছিল (`Products`, `Orders` ইত্যাদি)। ভাবো তো, তোমার প্রজেক্টে যদি ১০০টি টেবিল থাকে, তবে ১০০টি লাইন লিখতে হবে! 😫

তাই এবার আমরা শিখবো **Generic Unit of Work**। এটা হলো "স্মার্ট এবং অলস" (Smart & Lazy) ডেভেলপারদের পছন্দ।

### ১) Generic Unit of Work কি? (সহজ কথায়)

**সংজ্ঞা:** এটি এমন একটি প্যাটার্ন যেখানে আমরা আগে থেকে রিপোজিটরি ডিক্লেয়ার করি না; বরং যখন যেই রিপোজিটরি প্রয়োজন হয়, তখন রানটাইমে (On Demand) সেটি তৈরি করে নিই।

> 🎩 **ম্যাজিক ভেন্ডিং মেশিন এনালজি:**
> *   **Classic Unit of Work:** একটি ফুড কোর্ট, যেখানে পিজ্জার জন্য আলাদা দোকান, বার্গারের জন্য আলাদা দোকান, কফির জন্য আলাদা দোকান। তোমাকে সব দোকানের নাম জানতে হয়।
> *   **Generic Unit of Work:** একটি **জাদুকরী ভেন্ডিং মেশিন**। তুমি মেশিনের কাছে গিয়ে শুধু টাইপ বলবে—"আমাকে `<Pizza>` দাও" অথবা "আমাকে `<Burger>` দাও"—সে সাথে সাথে সেই জিনিসের কাউন্টার ওপেন করে দেবে। আলাদা করে দোকান বানানোর দরকার নেই!

### ২) কোড ইমপ্লিমেন্টেশন (স্টেপ বাই স্টেপ)

আমরা এখানে ৩টি ধাপ দেখবো:
1.  একটি **Generic Repository** ইন্টারফেস।
2.  **Generic Unit of Work** ক্লাস (যেখানে আসল ম্যাজিক বা লজিক থাকবে)।
3.  ব্যবহার বা **Usage**।

#### ধাপ ১: Generic Repository (কাজের কর্মী)
প্রথমে একটি কমন রিপোজিটরি বানাই যা সব টেবিলের জন্য কাজ করবে।

```csharp
public interface IGenericRepository<T> where T : class
{
    Task<T?> GetByIdAsync(int id);
    Task AddAsync(T entity);
    void Remove(T entity);
    // আরো কমন মেথড থাকতে পারে...
}

public class GenericRepository<T> : IGenericRepository<T> where T : class
{
    private readonly AppDbContext _context;
    private readonly DbSet<T> _dbSet;

    public GenericRepository(AppDbContext context)
    {
        _context = context;
        _dbSet = _context.Set<T>(); // এখানে টেবিল সেট হচ্ছে ডাইনামিকালি
    }

    public async Task<T?> GetByIdAsync(int id) => await _dbSet.FindAsync(id);
    public async Task AddAsync(T entity) => await _dbSet.AddAsync(entity);
    public void Remove(T entity) => _dbSet.Remove(entity);
}
```

#### ধাপ ২: Generic Unit of Work (ম্যাজিক মেশিন)
এখানে আমরা একটি `Dictionary` বা `Hashtable` ব্যবহার করবো। কেন?
কারণ, তুমি যদি ৫ বার `Product` রিপোজিটরি চাও, আমরা ৫ বার নতুন অবজেক্ট বানাবো না। একবার বানিয়ে মেমোরিতে (Dictionary-তে) রেখে দেব, পরের বার সেখান থেকেই দেব।

```csharp
public interface IUnitOfWork : IDisposable
{
    // এই মেথডটি যেকোনো এনটিটির জন্য রিপোজিটরি রিটার্ন করবে
    IGenericRepository<TEntity> Repository<TEntity>() where TEntity : class;
    
    Task<int> CompleteAsync();
}

public class UnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _context;
    // রিপোজিটরিগুলো ক্যাশ (Cache) করে রাখার জন্য ঝুড়ি
    private readonly Dictionary<Type, object> _repositories;

    public UnitOfWork(AppDbContext context)
    {
        _context = context;
        _repositories = new Dictionary<Type, object>();
    }

    public IGenericRepository<TEntity> Repository<TEntity>() where TEntity : class
    {
        // ১. চেক করি এই টাইপের রিপোজিটরি আগেই বানানো আছে কি না?
        if (_repositories.ContainsKey(typeof(TEntity)))
        {
            // থাকলে সেটাই রিটার্ন করো (Type Casting করে)
            return (IGenericRepository<TEntity>)_repositories[typeof(TEntity)];
        }

        // ২. না থাকলে নতুন বানাও
        var repository = new GenericRepository<TEntity>(_context);
        
        // ৩. ঝুড়িতে রেখে দাও ভবিষ্যতের জন্য
        _repositories.Add(typeof(TEntity), repository);

        return repository;
    }

    public async Task<int> CompleteAsync()
    {
        return await _context.SaveChangesAsync();
    }

    public void Dispose()
    {
        _context.Dispose();
    }
}
```

#### ধাপ ৩: ব্যবহার (Service Layer)

এখন দেখবে কোড কত ক্লিন হয়ে গেছে। আলাদা করে কোনো প্রপার্টি ডিক্লেয়ার করা ছাড়াই আমরা `Product` এবং `Order` নিয়ে কাজ করবো।

```csharp
public class OrderService
{
    private readonly IUnitOfWork _unitOfWork;

    public OrderService(IUnitOfWork unitOfWork)
    {
        _unitOfWork = unitOfWork;
    }

    public async Task CreateOrderAsync(Order order)
    {
        try
        {
            // ম্যাজিক মেথড কল: আমাকে <Product> এর রিপোজিটরি দাও
            var productRepo = _unitOfWork.Repository<Product>();
            
            // ম্যাজিক মেথড কল: আমাকে <Order> এর রিপোজিটরি দাও
            var orderRepo = _unitOfWork.Repository<Order>();

            // লজিক...
            var product = await productRepo.GetByIdAsync(order.ProductId);
            
            if(product != null)
            {
                // অর্ডার এড করো
                await orderRepo.AddAsync(order);
                
                // ফাইনাল সেভ (Unit of Work)
                await _unitOfWork.CompleteAsync();
                Console.WriteLine("অর্ডার সাকসেস! 🚀");
            }
        }
        catch (Exception ex)
        {
            Console.WriteLine("এরর হয়েছে! " + ex.Message);
            // এখানে আলাদা Rollback দরকার নেই, SaveChangesAsync কল না হলেই ডাটা সেভ হবে না।
        }
    }
}
```

### 🤔 কখন কোনটা ব্যবহার করবো? (Comparison)

| বৈশিষ্ট্য | Classic (Explicit) Unit of Work | Generic Unit of Work |
| :--- | :--- | :--- |
| **সেটআপ** | কঠিন। প্রতিটি রিপোজিটরি হাতে লিখতে হয়। | সহজ। একবার লিখলেই সব টেবিলের জন্য কাজ শেষ। |
| **কাস্টম মেথড** | খুব সহজ। যেমন `GetBestSellingProducts()` | একটু কঠিন। জেনেরিক রিপোজিটরিতে কাস্টম কোয়েরি লেখা ঝামেলা। |
| **কোড** | অনেক বেশি কোড লিখতে হয় (Boilerplate)। | অনেক কম কোড। |
| **উপযুক্ততা** | যখন কমপ্লেক্স কোয়েরি বা লজিক বেশি থাকে। | যখন সাধারণ CRUD (Create, Read, Update, Delete) অপারেশন বেশি থাকে। |

### 💡 শর্ট Best Practices

1.  **Small Projects:** ছোট বা মাঝারি প্রজেক্টের জন্য **Generic Unit of Work** সেরা। এটি ডেভেলপমেন্ট স্পিড বাড়িয়ে দেয়।
2.  **Custom Needs:** যদি তোমার স্পেশাল কোনো কোয়েরি দরকার হয় (যেমন: জটিল রিপোর্ট), তবে Generic এর সাথে **Extension Methods** অথবা **Specification Pattern** ব্যবহার করতে পারো।
3.  **Mix & Match:** তুমি চাইলে Generic এবং Classic মিক্স করতে পারো। কমন কাজের জন্য Generic মেথড রাখবে, আর স্পেশাল কাজের জন্য নির্দিষ্ট প্রপার্টি (`public IProductRepo Products { get; }`) রাখবে।

আজকের ডিশ (লেসন) কেমন লাগলো? এই "জাদুকরী ভেন্ডিং মেশিন" বা Generic Unit of Work তোমার কোডিং লাইফ অনেক সহজ করে দেবে! হ্যাপি কোডিং! 😎👨‍💻
