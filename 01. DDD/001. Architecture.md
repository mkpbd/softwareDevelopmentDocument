
### 1. Goals and Architecture
The book aims to bridge the gap between DDD theory and practical implementation. It advocates for **Clean Architecture** (also known as Onion Architecture), where the core domain is independent of infrastructure and presentation details.

**The Four Fundamental Layers:**
*   **Presentation Layer:** The UI (MVC, Blazor, Angular) that interacts with users.
*   **Application Layer:** Implements use cases. It orchestrates domain objects but contains application-specific logic (not core business rules). It returns DTOs, not Entities.
*   **Domain Layer:** The core of the system. Contains Entities, Value Objects, Domain Services, and Specifications. It depends on no other layer.
*   **Infrastructure Layer:** Implements abstractions (like Repositories) and integrates with third-party libraries (DB, Email, etc.).

### 2. Domain Layer Building Blocks
This is the most critical section, defining how to structure the business heart of the application.

*   **Aggregates & Aggregate Roots:**
    *   **Rule:** Aggregates should be saved and loaded as a single unit.
    *   **Rule:** Reference other Aggregates **only by ID**, not by navigation properties (e.g., An `Issue` aggregate holds a `RepositoryId`, not a `Repository` object). This ensures transaction boundaries and performance.
    *   **Best Practice:** Keep aggregates small to avoid performance issues.
*   **Entities:**
    *   Use **Guid** for primary keys.
    *   **Encapsulation:** Properties should have `private` setters. Use public methods (e.g., `SetTitle()`) to modify state and ensure validity.
    *   **Constructors:** Should require all necessary properties to create a valid entity state immediately.
*   **Domain Services:**
    *   Used when logic depends on multiple aggregates or external services.
    *   Naming convention: end with `Manager` (e.g., `IssueManager`).
    *   Example logic: Checking if an issue title already exists in the database before creation.
*   **Repositories:**
    *   Interfaces reside in the Domain Layer; implementations reside in Infrastructure.
    *   **Rule:** Repositories should remain "dumb." Do not put business logic inside them.
    *   **Specifications:** Use the Specification Pattern to create reusable, combinable filters (e.g., `InActiveIssueSpecification`) rather than creating custom repository methods for every query.

### 3. Application Layer Building Blocks
*   **Application Services:** Stateless services that implement the application's use cases (interactions). They manage the **Unit of Work** (transaction boundaries).
*   **Data Transfer Objects (DTOs):**
    *   **Rule:** Never return Entities to the Presentation Layer; always return DTOs.
    *   **Rule:** Do not reuse Input DTOs. Create specific DTOs for specific use cases (e.g., `IssueCreationDto`, `IssueUpdateDto`).
    *   **Validation:** Perform formal validation (Data Annotations) inside DTOs.
*   **Mapping:** Use `IObjectMapper` (AutoMapper) for Entity-to-DTO mapping. Avoid auto-mapping for Input-to-Entity; manual mapping in constructors or manager methods is preferred for safety.

### 4. Solution Structure
The guide recommends a specific Visual Studio project structure to enforce dependencies:
*   `Domain.Shared`: Enums, constants, and localized strings shared by all projects.
*   `Domain`: Core business layer.
*   `Application.Contracts`: Interfaces and DTOs.
*   `Application`: Implementation of app services.
*   `EntityFrameworkCore`: Database integrations.
*   `HttpApi`: API Controllers (usually automated by ABP).
*   `Web`: The final UI application.

### 5. Key Business Rules & Logic Placement
The book provides a heuristic for where to place logic:
*   **Core Domain Logic:** Logic that applies regardless of the UI (e.g., "An issue cannot be closed if it is locked"). **Place in Entities or Domain Services.**
*   **Application Logic:** Logic specific to a user interaction or flow (e.g., "Send an email notification when an issue is assigned"). **Place in Application Services.**

### 6. Example Domain
Throughout the book, the author uses a GitHub-like "Issue Tracking" system to demonstrate these concepts, featuring aggregates like `Issue`, `Repository`, `Label`, and `User`.

The guide emphasizes that while following these rules (like prohibiting navigation properties between aggregates) may seem restrictive or "hard" at first compared to simple CRUD, it is essential for maintaining large-scale, complex software over time.

### ১. Entity (এনটিটি) – যার নিজস্ব পরিচয় আছে
**সহজ কথা:** এনটিটি হলো এমন একটি অবজেক্ট যার একটি ইউনিক আইডি (ID) থাকে। এর ভেতরের তথ্য পরিবর্তন হলেও এর আইডি দিয়ে একে চেনা যায়।

**মজার উদাহরণ:** ধরুন আপনার ক্লাসের বন্ধু "রাহিম"। রাহিম যদি চুল ছোট করে, নতুন জামা পরে বা দাড়ি রাখে—সে কি বদলে অন্য কেউ হয়ে যাবে? না, সে "রাহিম"-ই থাকবে। কারণ তার ডিএনএ বা পরিচয় (Identity) এক।

*   **বইয়ের উদাহরণ:** `Issue` (Issue Tracking System-এ)। একটি ইশ্যুর টাইটেল বা স্ট্যাটাস বদলাতে পারে, কিন্তু ইশ্যুটির আইডি (Guid) একই থাকে।

### ২. Value Object (ভ্যালু অবজেক্ট) – যার মান-ই আসল
**সহজ কথা:** এদের কোনো আইডি নেই। এদের ভেতরের ভ্যালু বা মান দিয়েই এদের চেনা যায়।

**মজার উদাহরণ:** আপনার পকেটে একটি ৫০০ টাকার নোট আছে। আপনি কি মনে রাখেন নোটটার সিরিয়াল নাম্বার কত? না! আপনি শুধু জানেন ওটা ৫০০ টাকা। আমি যদি আপনার ৫০০ টাকার নোট নিয়ে অন্য একটি ৫০০ টাকার নোট দিই, আপনার কোনো সমস্যা নেই। কারণ এখানে **মান (Value)**-টাই আসল।

*   **বইয়ের উদাহরণ:** `IssueLabel` অথবা কোনো `Address`। ঠিকানা বদলানো মানে আপনি নতুন ঠিকানায় যাচ্ছেন, পুরনো ঠিকানা এডিট করছেন না।

### ৩. Aggregate & Aggregate Root (অ্যাগ্রিগেট ও অ্যাগ্রিগেট রুট) – পুরো প্যাকেজ
**সহজ কথা:** অ্যাগ্রিগেট হলো কয়েকটি অবজেক্টের একটি গুচ্ছ বা প্যাকেট, যারা সবসময় একসাথে থাকে। আর এই প্যাকেটের প্রধানকে বলা হয় **Aggregate Root**। বাইরের জগত শুধু বসের (Root) সাথে কথা বলতে পারে, ভেতরের ছোটখাটো অবজেক্টের সাথে সরাসরি কথা বলা নিষেধ।

**মজার উদাহরণ:** ধরুন একটি **গাড়ি (Car)**।
*   গাড়িটি হলো **Aggregate Root**।
*   গাড়ির চাকা, ইঞ্জিন, সিট হলো এর ভেতরের অংশ।
*   আপনি যখন গাড়ি চালান, আপনি কি সরাসরি ইঞ্জিনের পিস্টন বা চাকা ঘোরান? না! আপনি গাড়ির চাবি ঘোরান (Root-এর মেথড কল করেন), গাড়ি তখন নিজে ইঞ্জিন স্টার্ট দেয়।

*   **বইয়ের উদাহরণ:** `Issue` হলো Aggregate Root। আর `Comment` হলো এর ভেতরের অংশ। কেউ যদি কমেন্ট করতে চায়, তাকে `Issue`-এর মাধ্যমে করতে হবে (যেমন: `Issue.AddComment(...)`)। সরাসরি ডাটাবেসে কমেন্ট টেবিলে হাত দেওয়া যাবে না।

### ৪. Repository (রিপজিটরি) – গোডাউন বা স্টোররুম
**সহজ কথা:** এটি ডোমেইন লেয়ার এবং ডাটাবেসের মাঝখানের একটি মাধ্যম। ডোমেইন লেয়ার জানে না ডাটাবেসটি SQL নাকি Mongo, সে শুধু রিপজিটরির কাছে ডাটা চায়।

**মজার উদাহরণ:** ধরুন আপনি একজন শেফ (Chef)। আপনার রান্না করতে আলু লাগবে। আপনি স্টোরকিপারকে বললেন, "আমাকে ১০টা আলু দাও।" স্টোরকিপার আলু বাজার থেকে আনলো নাকি নিজের বাগান থেকে আনলো—সেটা আপনার জানার দরকার নেই। আপনি শুধু আলু পেলেই হলো।

*   **নিয়ম:** রিপজিটরি শুধু **Aggregate Root**-এর জন্য তৈরি করতে হয়।

### ৫. Domain Service (ডোমেইন সার্ভিস) – স্পেশাল ম্যানেজার
**সহজ কথা:** যখন কোনো বিজনেস লজিক বা নিয়ম একটি নির্দিষ্ট এনটিটির ভেতরে রাখা যায় না অথবা যার জন্য বাইরের সার্ভিসের দরকার হয়, তখন আমরা ডোমেইন সার্ভিস ব্যবহার করি।

**মজার উদাহরণ:** ধরুন "বিয়ে বাড়ি"।
*   বর (Entity) নিজের কাজ করবে।
*   কনে (Entity) নিজের কাজ করবে।
*   কিন্তু বিয়ের আয়োজন, ডেকোরেশন, মেহমানদারি—এগুলো কে সামলাবে? এর জন্য একজন **ওয়েডিং প্ল্যানার (Manager)** দরকার। এই প্ল্যানারই হলো ডোমেইন সার্ভিস।

*   **বইয়ের উদাহরণ:** `IssueManager`। যখন আপনি নতুন কোনো ইশ্যু তৈরি করবেন, তখন চেক করতে হবে একই নামের ইশ্যু আগে আছে কিনা। এটা `Issue` নিজে চেক করতে পারে না (কারণ সে ডাটাবেস চেনে না), তাই `IssueManager` ডাটাবেস চেক করে অনুমতি দেয়।

### ৬. Specification (স্পেসিফিকেশন) – ছাঁকনি বা ফিল্টার
**সহজ কথা:** এটি হলো নির্দিষ্ট কোনো বিজনেস রুল বা শর্ত, যা বারবার ব্যবহার করা যায়।

**মজার উদাহরণ:** ধরুন আপনি চাকরির ইন্টারভিউ নিচ্ছেন। আপনার শর্ত হলো—"প্রার্থীকে অবশ্যই ১৮ বছরের বেশি হতে হবে"। এই শর্তটি আপনি বারবার সব প্রার্থীর ওপর প্রয়োগ করবেন। এটিই স্পেসিফিকেশন।

*   **বইয়ের উদাহরণ:** `InActiveIssueSpecification`। কোন ইশ্যুগুলো ইন-অ্যাক্টিভ (যেমন: ৩০ দিন ধরে কোনো কমেন্ট নেই এবং ওপেন আছে), তা খুঁজে বের করার লজিক বারবার না লিখে একটি স্পেসিফিকেশনে লিখে রাখা হয়।

### এগুলো একসাথে যেভাবে কাজ করে (Flow)

ধরুন, আপনি গিটহাবের মতো একটি সিস্টেমে কাউকে একটি ইশ্যু অ্যাসাইন করতে চান। তখন ঘটনাটি এভাবে ঘটবে:

১. **Application Layer** (ইউজারের রিকোয়েস্ট রিসিভ করে) প্রথমে **Repository** ব্যবহার করে ডাটাবেস থেকে `Issue` (Aggregate Root) লোড করবে।
২. এরপর সে **Domain Service** (যেমন: `IssueManager`)-কে কল করবে এবং বলবে, "এই ইশ্যুটি 'অমুক' ইউজারকে অ্যাসাইন করে দাও।"
৩. **Domain Service** চেক করবে ইউজারটি ভ্যালিড কিনা বা তার ইতিমধ্যে অনেক কাজ আছে কিনা (বিজনেস রুল)।
৪. সব ঠিক থাকলে **Aggregate Root** (`Issue`) তার নিজের প্রপার্টি আপডেট করবে।
৫. সবশেষে **Repository** পুরো `Issue` প্যাকেটটিকে আবার ডাটাবেসে সেভ করে রাখবে।

এভাবেই এই ব্লকগুলো মিলে একটি সুশৃঙ্খল এবং মেইনটেইনযোগ্য সফটওয়্যার তৈরি করে।

নিচে C# (.NET) কোড দিয়ে প্রতিটি বিল্ডিং ব্লক বুঝানো হলো।

### ১. Entity (এনটিটি) – কাস্টমার (Customer)
**গল্প:** মামার দোকানে "বল্টু" একজন রেগুলার কাস্টমার। বল্টু আজ টি-শার্ট পরে আসুক আর কাল পাঞ্জাবি পরে আসুক, মামা তাকে "বল্টু" হিসেবেই চেনে। তার একটি ইউনিক আইডি আছে।

**Code:**
```csharp
using System;

// Entity: যার একটি ID আছে
public class Customer
{
    public Guid Id { get; private set; } // আইডি কেউ বাইরে থেকে বদলাতে পারবে না
    public string Name { get; private set; }
    public decimal TotalBaki { get; private set; } // বাকি'র হিসাব

    // Constructor: এনটিটি তৈরির সময় নাম দিতেই হবে
    public Customer(Guid id, string name)
    {
        Id = id;
        Name = name;
        TotalBaki = 0;
    }

    // বিজনেস লজিক: বাকির পরিমাণ বাড়ানো
    public void AddBaki(decimal amount)
    {
        if (amount < 0) throw new Exception("টাকা নেগেটিভ হতে পারে না!");
        TotalBaki += amount;
    }
}
```

### ২. Value Object – চায়ের রেসিপি (TeaPreference)
**গল্প:** বল্টু এবং তার বন্ধু উভয়েই বলল— "মামা, **চিনি কম, লিকার বেশি** দিয়ে দুই কাপ চা দেন।" এখানে "চিনি কম, লিকার বেশি" হলো ভ্যালু। কার কাপ কোনটা সেটা বিষয় না, দুটোর স্বাদ (Value) একই।

**Code:**
```csharp
// Value Object: এর কোনো ID নেই, মান (Value) টাই আসল।
// C# এ 'record' টাইপ ব্যবহার করা ভ্যালু অবজেক্টের জন্য সেরা।
public record TeaPreference(string SugarLevel, bool IsStrongLikar);

// ব্যবহার:
// var order1 = new TeaPreference("Low", true);
// var order2 = new TeaPreference("Low", true);
// order1 == order2 হবে True।
```

### ৩. Aggregate Root – অর্ডার (Order)
**গল্প:** মামার কাছে **অর্ডার** হলো আসল। একটি অর্ডারে চা থাকতে পারে, কলা থাকতে পারে, কেক থাকতে পারে। মামা সব কিছু একটা ট্রে-তে করে দেয়। পেমেন্ট করার সময় পুরো অর্ডারের টাকা দেন, শুধু কলার টাকা আলাদা দেন না। তাই `Order` হলো বস (Aggregate Root) আর `OrderItem` হলো তার পার্টস।

**Code:**
```csharp
using System.Collections.Generic;
using System.Linq;

public class Order // এটা Aggregate Root
{
    public Guid Id { get; private set; }
    public Guid CustomerId { get; private set; }
    public DateTime OrderTime { get; private set; }
    
    // বাইরের কেউ সরাসরি লিস্টে হাত দিতে পারবে না (Encapsulation)
    private readonly List<OrderItem> _items = new List<OrderItem>();
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();

    public Order(Guid id, Guid customerId)
    {
        Id = id;
        CustomerId = customerId;
        OrderTime = DateTime.Now;
    }

    // বিজনেস মেথড: অর্ডারে আইটেম যোগ করা
    public void AddItem(string itemName, decimal price)
    {
        // নিয়ম: ২০০ টাকার বেশি দামের আইটেম টং দোকানে বিক্রি হয় না
        if (price > 200) 
        {
            throw new Exception("মামা, এত দামি জিনিস আমরা বেচি না!");
        }

        _items.Add(new OrderItem(itemName, price));
    }

    // মোট বিল বের করার মেথড
    public decimal GetTotalBill()
    {
        return _items.Sum(x => x.Price);
    }
}

// সাব-আইটেম (Child Entity inside Aggregate)
public class OrderItem
{
    public string ItemName { get; private set; }
    public decimal Price { get; private set; }

    public OrderItem(string itemName, decimal price)
    {
        ItemName = itemName;
        Price = price;
    }
}
```

### ৪. Domain Service – বাকি ম্যানেজার (BakiManager)
**গল্প:** মামার দোকানে একটি কড়া নিয়ম আছে— **"৫০০ টাকার বেশি বাকি থাকলে চা দেওয়া নিষেধ।"**
এখন `Order` ক্লাস জানে না কাস্টমারের আগের বাকি কত। আবার `Customer` ক্লাস জানে না নতুন অর্ডারের বিল কত। এই দুইজনের মধ্যে সমন্বয় করতে লাগবে **BakiManager**।

**Code:**
```csharp
public class BakiManager
{
    // এই লজিকটা এনটিটির ভেতরে রাখা যাচ্ছিল না, তাই সার্ভিস
    public void CanCustomerOrder(Customer customer, decimal newOrderAmount)
    {
        decimal limit = 500; // বাকির লিমিট

        if (customer.TotalBaki + newOrderAmount > limit)
        {
            throw new Exception($"মাফ করবেন {customer.Name} ভাই! আপনার বাকি ৫০০ পার হয়ে গেছে। আগে শোধ করেন!");
        }
    }
}
```

### ৫. Repository (Interface) – খাতা (Ledger)
**গল্প:** মামা তার লাল খাতায় সব লিখে রাখে। কোডে আমরা জানি না খাতাটা কি SQL Database নাকি Excel file। আমরা শুধু ইন্টারফেস বানাব।

**Code:**
```csharp
// ডোমেইন লেয়ারে শুধু ইন্টারফেস থাকে
public interface IOrderRepository
{
    // অর্ডার সেভ করা
    void Insert(Order order);
    
    // আইডি দিয়ে অর্ডার খুঁজে বের করা
    Order GetById(Guid id);
}
```

### ৬. Application Service – চা বানানোর প্রসেস (Use Case)
**গল্প:** এবার সবগুলোকে জোড়া লাগানোর পালা। একজন ওয়েটার (Application Service) কাস্টমারের অর্ডার নেবে, ম্যানেজারকে (Domain Service) জিজ্ঞেস করবে বাকি দেওয়া যাবে কিনা, তারপর অর্ডার কনফার্ম করবে।

**Code:**
```csharp
public class OrderAppService
{
    private readonly IOrderRepository _orderRepository;
    private readonly BakiManager _bakiManager;
    // ধরে নিচ্ছি কাস্টমার রিপজিটরু আছে
    private readonly ICustomerRepository _customerRepository; 

    public OrderAppService(
        IOrderRepository orderRepository, 
        BakiManager bakiManager,
        ICustomerRepository customerRepository)
    {
        _orderRepository = orderRepository;
        _bakiManager = bakiManager;
        _customerRepository = customerRepository;
    }

    // ইউজ কেস: কাস্টমার চা চাইল
    public void CreateTeaOrder(Guid customerId)
    {
        // ১. ডাটাবেস থেকে কাস্টমারকে আনা
        var customer = _customerRepository.GetById(customerId);

        // ২. নতুন অর্ডার তৈরি করা (চা - ১০ টাকা, বিস্কুট - ৫ টাকা)
        var newOrder = new Order(Guid.NewGuid(), customerId);
        newOrder.AddItem("Masala Tea", 10);
        newOrder.AddItem("Toast Biscuit", 5);

        // ৩. ডোমেইন সার্ভিস দিয়ে চেক করা (বাকি দেওয়া যাবে কি?)
        _bakiManager.CanCustomerOrder(customer, newOrder.GetTotalBill());

        // ৪. সব ঠিক থাকলে অর্ডার সেভ করা
        _orderRepository.Insert(newOrder);
        
        // ৫. কাস্টমারের বর্তমান বাকি আপডেট করা (অন্য মেকানিজমেও হতে পারে)
        customer.AddBaki(newOrder.GetTotalBill());
        _customerRepository.Update(customer);

        Console.WriteLine("চা রেডি মামা!");
    }
}
```

### সারসংক্ষেপ:
১. **Customer (Entity):** বল্টু ভাই।
২. **TeaPreference (Value Object):** লিকার বেশি, চিনি কম।
৩. **Order (Aggregate Root):** পুরো নাস্তার ট্রে।
৪. **BakiManager (Domain Service):** বাকির লিমিট চেক করার পুলিশ।
৫. **OrderAppService:** ওয়েটার, যে সব কাজ জোড়া লাগায়।
