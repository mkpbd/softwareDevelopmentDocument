
স্বাগতম ফিউচার আর্কিটেক্টরা! 🎓

আজকের ক্লাসে আমরা শিখব **Domain Service**। নামটা শুনলে মনে হয় এটা কোনো "কাস্টমার কেয়ার সার্ভিস"। আসলে তা না!

ডোমেইন ড্রিভেন ডিজাইনে (DDD) এটা হলো **"লজিকের চৌধুরী সাহেব"**। যখন দুই বা তার বেশি এনটিটি (Entity) নিজেদের মধ্যে মারামারি বা লেনদেন করতে চায়, তখন তাদের মাঝখানে একজন মধ্যস্থতাকারী লাগে। এই মধ্যস্থতাকারীই হলো **Domain Service**।

আজ আমরা হাসতে হাসতে শিখব এই চৌধুরী সাহেব আসলে কী করেন! 😂

---

# 🕵️‍♂️ Domain Service আসলে কী? (What is it?)

সহজ কথায়, **Domain Service** হলো এমন একটি ক্লাস, যার নিজের কোনো স্টেট (State/Data) নেই, কিন্তু সে **বিজনেসের গুরুত্বপূর্ণ লজিক** হ্যান্ডেল করে—যেটা কোনো নির্দিষ্ট এনটিটির ভেতরে রাখা যাচ্ছিল না।

### 🤣 মজার উদাহরণ: "বিয়ে বাড়ি"
চিন্তা করুন একটি বিয়ের কথা।
১. **বর (Entity):** তার কাজ হলো কবুল বলা।
২. **কনে (Entity):** তার কাজও হলো কবুল বলা।
৩. **কাজী সাহেব (Domain Service):** বরের পকেট থেকে দেনমোহর নিয়ে কনের কাছে দেওয়া এবং বিয়েটা রেজিস্ট্রি করা।

এখন বর যদি কনের পকেটে হাত দিয়ে টাকা ঢুকাতে যায়, সেটা কি ভালো দেখাবে? 🙄 না! আবার কনে যদি বরের পকেটে হাত দেয়, সেটাও অদ্ভুত।
তাই **কাজী সাহেব (Service)** মাঝখানে থেকে দুই এনটিটির মধ্যে ইন্টারেকশন বা লেনদেন করিয়ে দেন।

# 📚 ডোমেইন সার্ভিসের বিস্তারিত বিষয়গুলো

## ১. The Problem: "কার ঘাড়ে লজিক চাপাব?" 🤔

**What happens:** মাঝে মাঝে আমরা এমন বিজনেস লজিক পাই যা কোনো নির্দিষ্ট এনটিটির মধ্যে ফিট হয় না।

**Example:** **টাকা ট্রান্সফার (Money Transfer)**।
ধরি, `Account A` থেকে `Account B`-তে টাকা পাঠাতে হবে।
*   যদি লজিকটা `Account A`-তে লিখি: `AccountA.TransferTo(AccountB)` — তাহলে Account A-কে Account B-এর ভেতরের খবর জানতে হচ্ছে। (Coupling বেড়ে গেল)।
*   আবার উল্টোটাও খারাপ।

**Why it matters:** এনটিটিদের কাজ হলো নিজের ডাটা নিয়ে কাজ করা। অন্যের ডাটায় নাক গলানো তাদের কাজ না।

## ২. The Solution: Domain Service 💡

**What it does:** আমরা একটা আলাদা সার্ভিস ক্লাস বানাই যা এই লেনদেনটা ম্যানেজ করে।

**Simple Code Example (Bank Transfer):**

```csharp
// ১. এনটিটি (Entity) - এরা শুধু নিজের কাজ বোঝে
public class BankAccount
{
    public decimal Balance { get; private set; }

    public void Debit(decimal amount) // টাকা তোলা
    {
        Balance -= amount;
    }

    public void Credit(decimal amount) // টাকা জমা দেওয়া
    {
        Balance += amount;
    }
}

// ২. ডোমেইন সার্ভিস (Domain Service) - চৌধুরী সাহেব
public class MoneyTransferDomainService
{
    public void Transfer(BankAccount fromAcc, BankAccount toAcc, decimal amount)
    {
        // লজিক ১: টাকা আছে তো?
        if (fromAcc.Balance < amount) 
            throw new Exception("ভাই, ব্যালেন্স তো নাই!");

        // লজিক ২: ট্রানজেকশন (দুই এনটিটির অপারেশন)
        fromAcc.Debit(amount);
        toAcc.Credit(amount);

        // এখানে হয়তো কারেন্সি কনভার্শন বা ট্যাক্সের লজিকও থাকতে পারে
        Console.WriteLine("টাকা ট্রান্সফার সফল!");
    }
}
```

**Why it works:**
*   `BankAccount` ক্লাস ক্লিন থাকল। সে শুধু জানে কিভাবে টাকা কমাতে হয় আর বাড়াতে হয়।
*   `MoneyTransferDomainService` জানে কিভাবে ট্রান্সফার করতে হয়।

## ৩. কখন ডোমেইন সার্ভিস ব্যবহার করবেন? (When to use?)

এটা খুব গুরুত্বপূর্ণ! সব লজিক সার্ভিসে নিয়ে আসবেন না। ৩টি ক্ষেত্রে এটি ব্যবহার করবেন:

১. **Multiple Entities:** যখন লজিকটি একাধিক এনটিটিকে জড়িত করে (যেমন: মানি ট্রান্সফার)।
২. **External System:** যখন লজিকটির জন্য ডাটাবেস বা অন্য থার্ড পার্টি টুলের দরকার হয় (যেমন: "এই ইউজারনেমটি ইউনিক কি না" চেক করা)।
৩. **Complex Calculation:** যখন ক্যালকুলেশনটা এনটিটির ভেতরে রাখলে এনটিটিটা অনেক ভারী হয়ে যায়।

# ⚠️ সমস্যা ও সমাধান (Pitfalls & Solutions)

ডোমেইন সার্ভিস ব্যবহার করতে গিয়ে নতুনরা একটা বড় ভুল করে। এর নাম **"Anemic Domain Model"** (রক্তশূন্য ডোমেইন)।

### সমস্যা: The Anemic Model (কুঁড়ে এনটিটি) 🧟‍♂️
**What happens:** আপনি যদি এনটিটির **সব** লজিক কেটে এনে সার্ভিসে দিয়ে দেন, তবে এনটিটি হয়ে যাবে শুধু `Get` আর `Set` এর বস্তা। তার কোনো কাজ থাকবে না।

**Bad Example:**
```csharp
// এনটিটি এখন বোকা (Dumb)
public class BankAccount { public decimal Balance { get; set; } }

public class AccountService
{
    public void AddMoney(BankAccount acc, decimal amount)
    {
        // ছিঃ ছিঃ! এই যোগ করার কাজটা তো এনটিটি নিজেই করতে পারত!
        acc.Balance += amount; 
    }
}
```

### ✅ সমাধান: Rich Domain Model
এনটিটির নিজস্ব লজিক (যেমন: ব্যালেন্স ভ্যালিডেশন, স্ট্যাটাস চেঞ্জ) এনটিটির ভেতরেই রাখুন। শুধু যখন **অন্য কারো সাথে** কাজ করতে হবে, তখন সার্ভিস ডাকুন।

> **রুল অফ থাম্ব:** "যতটা সম্ভব লজিক এনটিটিতে রাখুন। যখন আর উপায় নেই, তখন সার্ভিসে যান।"

# 🌍 রিয়েল-লাইফ ব্যবহার (Real-World Uses)

১. **User Registration (Uniqueness Check):**
    *   ইউজার যখন সাইন-আপ করে, তখন চেক করতে হয় `Email` বা `Username` ডাটাবেসে আগে থেকেই আছে কি না। `User` এনটিটি নিজে ডাটাবেস চেক করতে পারে না। তাই `UserRegistrationService` এই চেকটা করে।

২. **Currency Conversion:**
    *   টাকা থেকে ডলারে কনভার্ট করতে আজকের রেট লাগবে। এটা `Money` এনটিটির কাজ না, এটা `ExchangeRateService`-এর কাজ।

৩. **Order Processing:**
    *   অর্ডার প্লেস করার সময় ইনভেন্টরি (স্টক) চেক করা, ডিসকাউন্ট অ্যাপ্লাই করা এবং পেমেন্ট গেটওয়ে চেক করা—এগুলোর সমন্বয় করে `OrderProcessingService`।

# 📝 সারাংশ (Summary)

আজকের ক্লাসের **"Take Home"** পয়েন্টগুলো হলো:

১. **Domain Service:** হলো Stateless ক্লাস যা জটিল বিজনেস লজিক হ্যান্ডেল করে।
২. **Coordinator:** এটি একাধিক এনটিটির মধ্যে কাজ সমন্বয় করে (যেমন: কাজী সাহেব)।
৩. **Not for Everything:** ছোটখাটো লজিক এনটিটির ভেতরেই রাখবেন। সব লজিক সার্ভিসে আনলে এনটিটি "রক্তশূন্য" (Anemic) হয়ে যাবে।
৪. **Difference:** Application Service (যেমন: ইমেইল পাঠানো) আর Domain Service (যেমন: সুদের হিসাব করা) এক জিনিস না। ডোমেইন সার্ভিস পিওর বিজনেস লজিক নিয়ে কাজ করে।

ব্যাস! এখন আপনি জানেন কখন "চৌধুরী সাহেব" (Service)-কে ডাকতে হবে আর কখন এনটিটিকে দিয়ে কাজ করাতে হবে। হ্যাপি কোডিং! 🚀😎

আজকের ক্লাসে আমরা শিখব **Domain Service**। ডোমেইন ড্রিভেন ডিজাইন (DDD)-এর জগতে এটি হলো সেই **"ঘটক পাখি ভাই"** বা **"কাজী সাহেব"** যার ছাড়া বিয়ে (বা বিজনেস লজিক) সম্পন্ন হয় না।

যখন কোনো বিজনেস লজিক কোনো একটি নির্দিষ্ট `Entity`-এর পেটের ভেতর আঁটে না, অথবা সেই লজিকটা বাস্তবায়ন করতে বাইরের জগতের (যেমন ডাটাবেসের) খবর লাগে—তখনই আমাদের **Domain Service**-এর দরকার হয়।

চলুন, সেটআপ থেকে শুরু করে কোডিং পর্যন্ত পুরো বিষয়টি একদম "হাতে-কলমে" এবং হাসতে হাসতে শিখে ফেলি! 🚀

# 💻 অধ্যায় ২: কোডিং – ইউজার রেজিস্ট্রেশন সিস্টেম

### 🧐 সিনারিও (Real-Life Scenario)
ধরুন আমরা একটি অ্যাপ বানাচ্ছি যেখানে ইউজার রেজিস্ট্রেশন করবে।
**বিজনেস রুল:** "একই ইউজারনেম (Username) দুইবার ব্যবহার করা যাবে না।"

**সমস্যা:**
আমাদের `User` এনটিটি (Entity) কি জানে ডাটাবেসে অন্য কোনো ইউজার আছে কি না? **না!**
এনটিটির কাজ হলো নিজের নাম-ধাম রাখা। সে ডাটাবেস হাতড়াতে পারে না।

তাই এখানে আমাদের একজন **Manager** বা **Domain Service** লাগবে যে ডাটাবেস চেক করে বলবে—"ভাই, এই নাম খালি আছে কি না।"

### ধাপ ১: ডোমেইন এনটিটি (User Entity)
প্রথমে আমাদের `User` ক্লাস বানাই। এটি "বোকা" নয়, এটি নিজের ভ্যালিডেশন নিজেই করতে পারে।

```csharp
using System;

public class User
{
    public Guid Id { get; private set; }
    public string Username { get; private set; }
    public string Email { get; private set; }

    // কনস্ট্রাক্টর ইন্টারনাল (internal) রাখা ভালো, যাতে সার্ভিস ছাড়া কেউ হুট করে ইউজার বানাতে না পারে
    internal User(Guid id, string username, string email)
    {
        Id = id;
        Username = username;
        Email = email;
    }
}
```

### ধাপ ২: রিপজিটরি ইন্টারফেস (The Contract) 📜
ডোমেইন সার্ভিস সরাসরি ডাটাবেসের সাথে কথা বলে না, সে রিপজিটরির মাধ্যমে কথা বলে।

```csharp
public interface IUserRepository
{
    // ডাটাবেস চেক করার মেথড
    User FindByUsername(string username);
    void Save(User user);
}
```

### ধাপ ৩: ডোমেইন সার্ভিস (The Star of the Show) ⭐
এখন আমরা সেই **"ঘটক"** বা **"Manager"** ক্লাসটি লিখব। এর নাম সাধারণত `Manager` বা `Service` দিয়ে শেষ হয়।

```csharp
using System;

public class UserRegistrationManager // এটাই ডোমেইন সার্ভিস
{
    private readonly IUserRepository _userRepository;

    public UserRegistrationManager(IUserRepository userRepository)
    {
        _userRepository = userRepository;
    }

    // বিজনেস লজিক: ইউজার তৈরি করার সময় ডুপ্লিকেট চেক করা
    public User CreateUser(string username, string email)
    {
        // ১. চেক করা ইউজারনেম ইউনিক কি না
        var existingUser = _userRepository.FindByUsername(username);
        
        if (existingUser != null)
        {
            // যদি থাকে, তবে এরর মারবে (বিজনেস রুল ভায়োলেশন)
            throw new Exception($"দুঃখিত বস! '{username}' নামটি আগেই কেউ নিয়ে নিয়েছে।");
        }

        // ২. সব ঠিক থাকলে নতুন ইউজার তৈরি করা
        var newUser = new User(Guid.NewGuid(), username, email);
        
        // ৩. চাইলে এখানে আরও লজিক থাকতে পারে (যেমন: ওয়েলকাম ইমেইল লজিক)
        
        return newUser;
    }
}
```

# 🧠 অধ্যায় ৪: লজিক এবং কমন সমস্যা (Logic & Pitfalls)

### ১. কেন এটা `User` এনটিটির ভেতরে লিখলাম না?
যদি `User` ক্লাসের ভেতরে ডাটাবেস চেক লিখতাম, তাহলে `User` ক্লাসকে রিপজিটরির ওপর নির্ভর করতে হতো।
*   **সমস্যা:** এনটিটি ভারী হয়ে যেত এবং টেস্টিং কঠিন হতো। এনটিটি শুধু নিজের ডাটা চেনে, বাইরের জগত চেনে না।

### ২. কেন এটা `Controller` বা `Application Service`-এ লিখলাম না?
যদি কন্ট্রোলারে লিখতেন, তাহলে এই "ইউনিক ইউজারনেম" লজিকটা শুধু ওয়েব অ্যাপের জন্য কাজ করত।
*   **সমস্যা:** কাল যদি মোবাইল অ্যাপ বা ব্যাকগ্রাউন্ড জব থেকে ইউজার বানাতে হয়, তখন আবার নতুন করে ওই লজিক লিখতে হবে (Code Duplication)।
*   **সমাধান:** ডোমেইন সার্ভিসে লজিক রাখলে পৃথিবীর যেকোনো জায়গা থেকে কল করলে সেইম রুল অ্যাপ্লাই হবে।

### ৩. সাধারণ সমস্যা: Anemic Domain Model (রক্তশূন্য ডোমেইন) 🩸
নতুনরা অনেক সময় **সব** লজিক সার্ভিসে নিয়ে আসে।
*   **ভুল:** `user.ChangePassword()` মেথডটা `UserService`-এ লেখা।
*   **সঠিক:** পাসওয়ার্ড বদলানো ইউজারের নিজস্ব ব্যাপার, তাই এটা `User` এনটিটির ভেতরেই থাকা উচিত।
*   **রুল:** ডোমেইন সার্ভিস শুধু তখনই ব্যবহার করবেন যখন লজিকটি **একাধিক এনটিটি** বা **বাইরের সিস্টেমের** সাথে সম্পর্কিত।

# 📝 অধ্যায় ৫: সারাংশ (Summary)

আজকের ক্লাসের **Key Points**:

১. **Middleman:** ডোমেইন সার্ভিস হলো লজিকের মধ্যস্থতাকারী। সে এনটিটি এবং রিপজিটরির মধ্যে সমন্বয় করে।
২. **Stateless:** ডোমেইন সার্ভিসের নিজস্ব কোনো ডাটা (State) থাকে না, সে শুধু কাজ (Action) করে দেয়।
৩. **Specific Use Case:** যখন কোনো লজিক এনটিটির ভেতরে ফিট হয় না (যেমন: ডাটাবেস চেক করা, থার্ড পার্টি API কল করা), তখনই কেবল ডোমেইন সার্ভিস বানাবেন।
৪. **Naming:** ক্লাসের শেষে `Manager` বা `Service` (যেমন: `ProductManager`, `TransferService`) নাম দেওয়া ভালো প্র্যাকটিস।

**Real-World Application:**
ব্যাংকিং সফটওয়্যারে "টাকা ট্রান্সফার", ই-কমার্সে "অর্ডার ভ্যালিডেশন", বা সোশ্যাল মিডিয়ায় "ফ্রেন্ড রিকোয়েস্ট লজিক"—এসব জটিল জায়গা যেখানে অনেক রুলস মানতে হয়, সেখানেই ডোমেইন সার্ভিসের রাজত্ব।

কোডটি রান করে নিজেরা প্র্যাকটিস করুন। "ডুপ্লিকেট ইমেইল" চেক করার জন্য আরেকটি মেথড লিখে ফেলুন! হ্যাপি কোডিং! 🚀😎
