স্বাগতম ফিউচার সফটওয়্যার ইঞ্জিনিয়াররা! 🎓

আজকের ক্লাসে আমরা শিখব **Application Service**। নামটা বেশ ভাবগাম্ভীর্যপূর্ণ মনে হলেও, আসলে এই ব্যাটা হলো আমাদের সফটওয়্যারের **"কাজের ঠিকাদার"** বা **"ম্যানেজার সাহেব"**।

ডোমেইন ড্রিভেন ডিজাইনে (DDD):
*   **Entity/Domain Service** হলো "কারিগর" (যারা আসল কাজ জানে)।
*   **Repository** হলো "স্টোরকিপার" (যে মালসামানা রাখে)।
*   আর **Application Service** হলো সেই **ম্যানেজার**, যে কাস্টমারের (UI/API) থেকে অর্ডার নেয় এবং কারিগর ও স্টোরকিপারকে হুকুম দিয়ে কাজটা করিয়ে নেয়।

আজ আমরা হাসতে হাসতে শিখব এই ম্যানেজার সাহেবের কাজ কারবার! 😂

# 🕵️‍♂️ Application Service আসলে কী? (What is it?)

সহজ কথায়, **Application Service** হলো বাইরের জগত (User Interface, API) এবং ভেতরের জগত (Domain Layer)-এর মাঝখানের **সেতু (Bridge)**।

### 🤣 মজার উদাহরণ: "রেস্টুরেন্ট ম্যানেজার"
ধরুন আপনি রেস্টুরেন্টে গিয়ে বিরিয়ানি অর্ডার দিলেন।
১. আপনি হলেন **User (UI)**।
২. ওয়েটার/ম্যানেজার হলো **Application Service**।
৩. বাবুর্চি হলো **Domain Logic**।

আপনি কি সরাসরি কিচেনে গিয়ে বাবুর্চিকে বলেন—"চালের সাথে মাংস মেশান"? না!
আপনি ম্যানেজারকে বলেন: **"ভাই, এক প্লেট বিরিয়ানি দেন।"**
ম্যানেজার তখন:
*   অর্ডারটা লেখে (Input DTO)।
*   কিচেনে গিয়ে বাবুর্চিকে বলে (Domain Logic Call)।
*   খাবার রেডি হলে আপনাকে এনে দেয় (Output DTO)।

ম্যানেজার কিন্তু নিজে রান্না করে না, সে শুধু **"কাজটা করিয়ে নেয়"** (Orchestration)।

# 📚 অ্যাপ্লিকেশন সার্ভিসের বিস্তারিত বিষয়গুলো

## ১. Orchestration (কাজের সমন্বয় করা) 🎻
**What it does:** অ্যাপ্লিকেশন সার্ভিস নিজে কোনো জটিল বিজনেস লজিক হ্যান্ডেল করে না। সে শুধু স্টেপ-বাই-স্টেপ কাজগুলো সাজায়।
**Example:**
১. রিপজিটরি থেকে ডাটা আনো।
২. ডোমেইন সার্ভিসে ক্যালকুলেশন করো।
৩. আবার রিপজিটরিতে সেভ করো।
৪. ইউজারকে ইমেইল পাঠাও।

**Why important:** যদি এই ম্যানেজার না থাকত, তবে ইউজারকে (UI) নিজেকেই দৌড়াদৌড়ি করে সব কাজ করতে হতো।

## ২. DTO (Data Transfer Object) কনভার্শন 📦
**What it does:** অ্যাপ্লিকেশন সার্ভিস ইনপুট হিসেবে **DTO** নেয় এবং আউটপুট হিসেবেও **DTO** ফেরত দেয়। সে কখনোই **Entity** (আসল ডোমেইন অবজেক্ট) বাইরে পাঠায় না।
**Bangla Example:** বাবুর্চি কিচেনে যে হাড়িপাতিল (Entity) ব্যবহার করে রান্না করে, ওয়েটার কি সেই হাড়িপাতিল সুদ্ধ আপনার টেবিলে খাবার দেয়? না! সে সুন্দর প্লেটে (DTO) সাজিয়ে খাবার দেয়।

## ৩. Transaction Management (লেনদেন সামলানো) 💰
**What it does:** একটা কাজ পুরোপুরি শেষ হলে "সেভ" করবে, মাঝপথে এরর খেলে সব বাতিল করবে (Rollback)। একে বলে **Unit of Work**।
**Why works:** টাকা কাটল কিন্তু রিচার্জ হলো না—এই সমস্যা যাতে না হয়।

# 💻 কোড দিয়ে বুঝি (Code Example)

আমরা একটি **কোর্স এনরোলমেন্ট** সিস্টেম দেখব।

```csharp
// ১. ইনপুট DTO (কাস্টমারের অর্ডার স্লিপ)
public class EnrollStudentDto
{
    public Guid StudentId { get; set; }
    public string CourseName { get; set; }
}

// ২. অ্যাপ্লিকেশন সার্ভিস (ম্যানেজার সাহেব)
public class EnrollmentAppService : IApplicationService
{
    private readonly IStudentRepository _studentRepository;
    private readonly CourseManager _courseManager; // Domain Service

    public EnrollmentAppService(IStudentRepository repo, CourseManager manager)
    {
        _studentRepository = repo;
        _courseManager = manager;
    }

    // ইউজ কেস: ছাত্র ভর্তি করা
    public void EnrollStudent(EnrollStudentDto input)
    {
        // ধাপ ১: ডাটাবেস থেকে ছাত্র খুঁজে বের করা
        var student = _studentRepository.GetById(input.StudentId);
        
        // ধাপ ২: আসল কাজটা ডোমেইন সার্ভিসকে দিয়ে করানো (ম্যানেজার নিজে লজিক জানে না)
        // _courseManager চেক করবে সিট খালি আছে কিনা, ছাত্রের যোগ্যতা আছে কিনা ইত্যাদি
        _courseManager.Register(student, input.CourseName);

        // ধাপ ৩: সব ঠিক থাকলে সেভ করা (Transaction)
        _studentRepository.Save(student);

        // ধাপ ৪: ইমেইল পাঠানো (Optional)
        SendWelcomeEmail(student.Email);
    }
}
```

# ⚠️ সমস্যা ও সমাধান (Pitfalls & Solutions)

অ্যাপ্লিকেশন সার্ভিস বানাতে গিয়ে নতুনরা কিছু কমন ভুল করে।

### সমস্যা ১: The "Fat" Application Service (মোটা ম্যানেজার) 🍔
**Problem:** অনেকে সব বিজনেস লজিক (`if-else`, calculation) এই সার্ভিসের ভেতরে লিখে ফেলে।
**Result:** ম্যানেজার নিজেই যদি রান্নাঘরে ঢুকে রান্না শুরু করে, তবে রেস্টুরেন্ট চলবে না। ডোমেইন লেয়ারের কোনো দাম থাকে না।
**✅ সমাধান:** অ্যাপ্লিকেশন সার্ভিসে কোনো `if (balance < amount)` টাইপ লজিক লিখবেন না। এগুলো সব **Entity** বা **Domain Service**-এ পাঠিয়ে দিন। ম্যানেজার শুধু হুকুম দেবে।

### সমস্যা ২: Returning Entities (হাড়িপাতিল সার্ভ করা) 🍲
**Problem:** মেথড থেকে সরাসরি `return student;` (Entity) করে দেওয়া।
**Result:** এতে করে বাইরের জগত আপনার ডাটাবেসের স্ট্রাকচার জেনে যায়। সিকিউরিটি রিস্ক বাড়ে।
**✅ সমাধান:** সবসময় `StudentDto` রিটার্ন করুন। `AutoMapper` বা ম্যানুয়ালি ম্যাপ করে নিন।

### সমস্যা ৩: Duplicating Logic (একই কাজ বারবার)
**Problem:** একই লজিক মোবাইল অ্যাপের জন্য এক কন্ট্রোলারে, আবার ওয়েবের জন্য আরেক অ্যাপ সার্ভিসে লেখা।
**✅ সমাধান:** লজিকগুলো **Domain Service**-এ নিয়ে যান, যাতে সবাই সেখান থেকে ব্যবহার করতে পারে।

# 🚀 সুবিধা এবং রিয়েল-লাইফ ব্যবহার (Advantages)

১. **Security Barrier:** হ্যাকার বা বাইরের ইউজার সরাসরি আপনার ডোমেইন লজিক বা ডাটাবেস টাচ করতে পারে না। অ্যাপ সার্ভিস দেয়াল হিসেবে কাজ করে।
২. **Easy API:** আমরা যখন Web API বানাই (Controller), তখন কন্ট্রোলার সরাসরি এই অ্যাপ্লিকেশন সার্ভিসকে কল করে। কন্ট্রোলার থাকে একদম ক্লিন।
৩. **Testing:** আপনি ডোমেইন লজিক আলাদা টেস্ট করতে পারেন, আবার অ্যাপ সার্ভিস মক (Mock) করে ফ্লো টেস্ট করতে পারেন।

**Real-World Scenario:**
উবার (Uber) অ্যাপে যখন আপনি "Request Ride" বাটনে চাপ দেন:
1. রিকোয়েস্টটি `RideAppService`-এ যায়।
2. সার্ভিসটি `DriverRepository` থেকে কাছের ড্রাইভার খোঁজে।
3. `FareCalculator` (Domain Service) দিয়ে ভাড়া হিসাব করে।
4. সবশেষে আপনাকে কনফার্মেশন (DTO) পাঠায়।

# 📝 সারাংশ (Summary)

আজকের ক্লাসের **"Take Home"** পয়েন্টগুলো হলো:

১. **Manager Role:** অ্যাপ্লিকেশন সার্ভিস নিজে কাজ করে না, সে অর্কেস্ট্রেটর (Orchestrator) হিসেবে কাজ করিয়ে নেয়।
২. **DTO In, DTO Out:** সে কখনো এনটিটি বাইরে পাঠায় না, সব সময় প্যাকেট করা ডাটা (DTO) পাঠায়।
৩. **Thin Layer:** এই লেয়ারটি পাতলা হতে হবে। কোনো বিজনেস লজিক এখানে থাকবে না, শুধু প্রসেস ফ্লো থাকবে।
৪. **Transaction:** কাজের শুরু এবং শেষ (Commit/Save) এখান থেকেই কন্ট্রোল হয়।

স্বাগতম ফিউচার সফটওয়্যার ইঞ্জিনিয়াররা! 🎓

আজকের ক্লাসে আমরা শিখব **Application Service**।

ডোমেইন ড্রিভেন ডিজাইন (DDD)-এ:
*   **Entity:** হলো আসল "হিরো" (যেমন: শাকিব খান), যে একাই একশো, মারামারি (লজিক) সব নিজেই করে।
*   **Repository:** হলো "প্রডিউসার", যে টাকা বা ডাটা সাপ্লাই দেয়।
*   **Application Service:** হলো সেই **"পরিচালক (Director)"**। সে নিজে অভিনয় করে না, কিন্তু সে হিরোকে বলে "এখন ফাইট করো", প্রডিউসারকে বলে "টাকা দাও"—অর্থাৎ সে পুরো মুভিটা **পরিচালনা (Orchestrate)** করে।

আজ আমরা কোড করে দেখব একজন পরিচালক বা ম্যানেজার সাহেব কীভাবে পুরো সিস্টেম নাচায়! 🎬🕺

# 💻 অধ্যায় ২: কোডিং – বই বিক্রি করার সিস্টেম

আমাদের টার্গেট: কাস্টমার একটি বই কিনতে চাইবে। অ্যাপ সার্ভিস চেক করবে বই আছে কি না, থাকলে স্টক কমাবে এবং বিক্রি কনফার্ম করবে।

### ধাপ ১: ডোমেইন লেয়ার (Entity) - আসল হিরো 🦸‍♂️
প্রথমে আমাদের `Book` এনটিটি বানাই। মনে রাখবেন, বিজনেস লজিক (স্টক কমানো) হিরোর কাজ, পরিচালকের না।

```csharp
using System;

public class Book
{
    public Guid Id { get; private set; }
    public string Title { get; private set; }
    public int Stock { get; private set; } // কত পিস আছে

    public Book(Guid id, string title, int stock)
    {
        Id = id;
        Title = title;
        Stock = stock;
    }

    // বিজনেস লজিক: বই বিক্রি হলে স্টক কমবে
    public void SellOne()
    {
        if (Stock <= 0)
        {
            throw new Exception("দুঃখিত বস! বই আউট অফ স্টক।");
        }
        Stock--; // স্টক কমালাম
    }
}
```

### ধাপ ২: DTO (Data Transfer Object) - সাজানো প্লেট 🍛
অ্যাপ্লিকেশন সার্ভিস কখনোই বাইরের জগতকে (UI) আসল `Book` (Entity) দেখায় না। সে ডাটা প্যাকেট করে পাঠায়।

```csharp
// ইনপুট DTO (কাস্টমার যা পাঠাবে)
public class SellBookDto
{
    public Guid BookId { get; set; }
}

// আউটপুট DTO (আমরা যা ফেরত দেব)
public class BookResultDto
{
    public string Title { get; set; }
    public int RemainingStock { get; set; }
    public string Message { get; set; }
}
```

### ধাপ ৩: রিপজিটরি (Fake Storekeeper) 🏪
যে ডাটাবেস থেকে বই এনে দেবে।

```csharp
public interface IBookRepository
{
    Book GetById(Guid id);
    void Save(Book book);
}

// আমরা শিখছি অ্যাপ সার্ভিস, তাই ডাটাবেস নিয়ে প্যারা নেব না। ফেইক ক্লাস।
public class FakeBookRepository : IBookRepository
{
    // মেমোরিতে একটা বই আছে ধরে নিই
    private Book _book = new Book(Guid.Parse("11111111-1111-1111-1111-111111111111"), "DDD in Bangla", 5);

    public Book GetById(Guid id) => _book; // আইডির দরকার নেই, একটাই বই রিটার্ন করলাম

    public void Save(Book book)
    {
        Console.WriteLine($"💾 ডাটাবেসে সেভ হয়েছে! বর্তমান স্টক: {book.Stock}");
    }
}
```

### ধাপ ৪: অ্যাপ্লিকেশন সার্ভিস (The Director) 🎬
এটাই আমাদের মেইন টপিক। দেখুন সে কিভাবে কাজগুলো সাজায়।

```csharp
public class BookAppService
{
    private readonly IBookRepository _repository;

    public BookAppService(IBookRepository repository)
    {
        _repository = repository;
    }

    // ইউজ কেস: বই বিক্রি করা
    public BookResultDto SellBook(SellBookDto input)
    {
        Console.WriteLine("--- পরিচালক অ্যাকশন শুরু করলেন ---");

        // ১. রিপজিটরিকে বলল: "বইটা নিয়ে আসো"
        var book = _repository.GetById(input.BookId);
        if (book == null) throw new Exception("বই পাওয়া যায়নি!");

        // ২. এনটিটিকে বলল: "স্টক কমাও" (আসল লজিক)
        // পরিচালক নিজে বিয়োগ করছে না, হিরোকে দিয়ে করাচ্ছে
        book.SellOne();

        // ৩. রিপজিটরিকে বলল: "আপডেট সেভ করো"
        _repository.Save(book);

        // ৪. কাস্টমারকে জানানোর জন্য DTO বানালো
        return new BookResultDto
        {
            Title = book.Title,
            RemainingStock = book.Stock,
            Message = "অভিনন্দন! বই কেনা সফল হয়েছে।"
        };
    }
}
```

# 🧠 অধ্যায় ৩: লজিক এবং কেন এভাবে লিখলাম?

### ১. Orchestration (সমন্বয়)
খেয়াল করুন, `BookAppService` নিজে কোনো `Stock--` বা `if (Stock < 0)` লজিক লেখেনি। সে শুধু স্টেপগুলো ম্যানেজ করেছে:
`Get Data` -> `Do Logic (Entity)` -> `Save Data` -> `Return DTO`.

### ২. DTO কেন?
আমরা যদি মেথড থেকে সরাসরি `return book;` (Entity) করতাম, তাহলে কাস্টমার `book.Stock = 100` করে হ্যাক করতে পারত। DTO ব্যবহার করায় আমাদের ভেতরের স্ট্রাকচার নিরাপদ থাকল।

### ৩. Exception Handling
অ্যাপ সার্ভিস বাউন্ডারি হিসেবে কাজ করে। যদি `book.SellOne()` এরর দেয় (স্টক না থাকলে), অ্যাপ সার্ভিস সেটা ক্যাচ করে ইউজারকে সুন্দর মেসেজ দিতে পারে (যদিও এখানে আমরা সিম্পল রেখেছি)।

# 🌍 অধ্যায় ৪: রিয়েল-লাইফ ব্যবহার (Main Program)

এখন আমরা `Program.cs` এ কাস্টমার সেজে বই কিনব।

```csharp
class Program
{
    static void Main(string[] args)
    {
        // সেটআপ (Dependency Injection)
        IBookRepository repo = new FakeBookRepository();
        BookAppService appService = new BookAppService(repo);

        // কাস্টমার রিকোয়েস্ট (DTO)
        var request = new SellBookDto 
        { 
            BookId = Guid.Parse("11111111-1111-1111-1111-111111111111") 
        };

        try
        {
            // প্রথমবার কেনা
            Console.WriteLine("১ম কাস্টমার আসছে...");
            var result1 = appService.SellBook(request);
            Console.WriteLine($"রেজাল্ট: {result1.Message} (স্টক বাকি: {result1.RemainingStock})");

            Console.WriteLine("\n২য় কাস্টমার আসছে...");
            var result2 = appService.SellBook(request);
            Console.WriteLine($"রেজাল্ট: {result2.Message} (স্টক বাকি: {result2.RemainingStock})");
        }
        catch (Exception ex)
        {
            Console.WriteLine($"সর্বনাশ! {ex.Message}");
        }
    }
}
```

# ⚠️ অধ্যায় ৫: সমস্যা ও সমাধান (Common Pitfalls)

### সমস্যা ১: The "Fat" Service (পেটুক ম্যানেজার) 🍔
**Problem:** নতুন ডেভেলপাররা অনেক সময় `SellBook` মেথডের ভেতরেই `book.Stock = book.Stock - 1` লিখে ফেলে।
**Why Bad:** বিজনেস লজিক লিক হয়ে সার্ভিসে চলে আসল। পরে যদি স্টকের লজিক চেঞ্জ হয়, সব সার্ভিস ঘাঁটতে হবে।
**Solution:** লজিক সবসময় এনটিটি (`Book` class) বা ডোমেইন সার্ভিসে রাখবেন। অ্যাপ সার্ভিস শুধু কল করবে।

### সমস্যা ২: Transaction Management
**Problem:** ধরুন স্টক কমল, কিন্তু ডাটাবেসে সেভ হওয়ার আগেই কারেন্ট চলে গেল। ডাটা ইনকনসিস্টেন্ট হয়ে যাবে।
**Solution:** রিয়েল লাইফে অ্যাপ সার্ভিসের মেথডের ওপর `[UnitOfWork]` অ্যাট্রিবিউট ব্যবহার করা হয়, যাতে পুরো কাজটা একটা ট্রানজেকশনে হয়।

# 📝 অধ্যায় ৬: সারাংশ (Summary)

আজকের ক্লাসের **Key Points**:

১. **Role:** Application Service হলো ইউজ কেস (Use Case) বাস্তবায়নকারী। সে কোঅর্ডিনেটর বা ম্যানেজার।
২. **Isolation:** সে ডোমেইন লেয়ার এবং UI লেয়ারের মধ্যে দেয়াল তুলে দেয়। UI জানে না ভেতরে এনটিটি দেখতে কেমন।
৩. **Input/Output:** সে ইনপুট হিসেবে DTO নেয়, আউটপুট হিসেবেও DTO দেয়।
৪. **Logic Free:** তার ভেতরে কোনো বিজনেস লজিক (Calculation/Rule) থাকবে না, শুধু ফ্লো কন্ট্রোল থাকবে।

**Real-World Scenario:**
যখন আপনি বিকাশে (bKash) "Send Money" করেন:
*   আপনার মোবাইল অ্যাপ (UI) একটি রিকোয়েস্ট পাঠায়।
*   বিকাশের ব্যাকএন্ডে একটি `TransactionAppService` সেই রিকোয়েস্ট ধরে।
*   সে ব্যালেন্স চেক করে (Domain Logic), টাকা কাটে, এবং ট্রানজেকশন হিস্ট্রিতে সেভ করে।
*   শেষে আপনাকে "Successful" মেসেজ (DTO) পাঠায়।
