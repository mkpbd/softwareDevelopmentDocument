
স্বাগতম ফিউচার সফটওয়্যার আর্কিটেক্টরা! 🎓

আজকের ক্লাসটা খুবই ইন্টারেস্টিং এবং একটু "কনফিউজিং" টপিক নিয়ে। টপিকটা হলো **Domain Logic বনাম Application Logic** এবং **Multiple Application Layers**।

অনেকে মনে করে, "লজিক তো লজিকই! যেখানে খুশি লিখলেই হলো।"
কিন্তু ভাই, আপনি কি বিরিয়ানি রান্না করতে গিয়ে বাথরুমের মগ ব্যবহার করেন? 🚽 রান্নাঘরের জিনিস রান্নাঘরে, আর ড্রয়িংরুমের জিনিস ড্রয়িংরুমে—এটাই হলো সফটওয়্যার আর্কিটেকচারের নিয়ম।

আজ আমরা শিখব কোন লজিক কোথায় রাখতে হয় এবং কেন বড় সিস্টেমে একটার বেশি অ্যাপ্লিকেশন লেয়ার লাগে।

---

# ১. Domain Logic (Business Logic) – "ফ্যামিলির সংবিধান" 📜

### 🔍 এটা কী? (What is it?)
**Domain Logic** হলো আপনার সফটওয়্যারের **Core Business Rules** বা ধ্রুব সত্য। সফটওয়্যার থাকুক বা না থাকুক, এই নিয়মগুলো ব্যবসার জন্য সত্য।

### 🤣 মজার উদাহরণ:
ধরুন "ব্যাংকিং সিস্টেম"।
*   **নিয়ম:** "অ্যাকাউন্টে টাকা না থাকলে টাকা তোলা যাবে না।"
*   **নিয়ম:** "সুদের হার ৫%।"

এই নিয়মগুলো কি অ্যাপের বাটন বা কালারের ওপর নির্ভর করে? না! আপনি ব্যাংকে গিয়ে চেক দেন আর অ্যাপ দিয়ে টাকা তুলুন—টাকা না থাকলে ট্রানজেকশন হবে না। এটাই ডোমেইন লজিক।

### 🛠️ কোথায় থাকে?
*   Entities (যেমন: `BankAccount` ক্লাস)
*   Domain Services (যেমন: `InterestCalculator`)

### ⚠️ সমস্যা ও সমাধান
**Problem:** অনেকে এই লজিকগুলো **Controller** বা **UI** তে লিখে ফেলে।
**Result:** মোবাইল অ্যাপে টাকা তোলার সময় ব্যালেন্স চেক করলেন, কিন্তু ওয়েবসাইট দিয়ে তোলার সময় চেক করতে ভুলে গেলেন। ইউজার দেউলিয়া হয়ে যাবে!
**Solution:** এই লজিক সবসময় **Entity** বা **Domain Service**-এ রাখুন। যাতে সব জায়গা থেকে সেইম রুল অ্যাপ্লাই হয়।

---

# ২. Application Logic (Use Case Logic) – "ম্যানেজার সাহেব" 👔

### 🔍 এটা কী? (What is it?)
**Application Logic** হলো সেই কোড যা একটি নির্দিষ্ট কাজ (Use Case) সম্পন্ন করতে ফ্লো বা ধাপগুলো নিয়ন্ত্রণ করে। সে নিজে ব্যবসার নিয়ম জানে না, সে শুধু জানে কার পরে কাকে ডাকতে হবে।

### 🤣 মজার উদাহরণ:
ব্যাংকে গেলেন টাকা তুলতে।
১. দারোয়ান গেট খুলে দিল।
২. আপনি ফর্ম ফিলাপ করলেন।
৩. ক্যাশিয়ার টাকা দিল।
৪. আপনাকে একটা এসএমএস পাঠানো হলো।

এই যে পুরো প্রসেসটা (গেট খোলা -> ফর্ম নেওয়া -> এসএমএস পাঠানো)—এটা হলো **Application Logic**। কিন্তু "টাকা আছে কি না"—এটা চেক করা ডোমেইন লজিক।

### 🛠️ কোথায় থাকে?
*   Application Services (যেমন: `FundTransferAppService`)

### 📋 Domain Logic vs Application Logic পার্থক্য

| বিষয় | Domain Logic (বিজনেস রুল) | Application Logic (প্রসেস ফ্লো) |
| :--- | :--- | :--- |
| **উদাহরণ** | ব্যালেন্স < ০ হলে টাকা তোলা যাবে না। | টাকা তোলার পর ইউজারকে ইমেইল পাঠাও। |
| **অবস্থান** | Entity / Domain Service | Application Service |
| **নির্ভরতা** | কারো ওপর নির্ভর করে না (স্বাধীন)। | ডোমেইন, রিপজিটরি, ইমেইল সার্ভিসের ওপর নির্ভর করে। |
| **পুনঃব্যবহার** | সব অ্যাপে একই থাকে। | অ্যাপভেদে ভিন্ন হতে পারে। |

# ৩. Multiple Application Layers (একাধিক রান্নাঘর) 🏢

### 🔍 এটা কী? (What is it?)
মাঝে মাঝে আমাদের সিস্টেমে এক ধরনের ইউজার থাকে না। তখন আমরা **একই ডোমেইন লজিক** ব্যবহার করি, কিন্তু তাদের জন্য **আলাদা আলাদা Application Layer** তৈরি করি।

### 🤣 রিয়েল লাইফ উদাহরণ: "রেস্টুরেন্ট"
একটি বড় রেস্টুরেন্টের কথা ভাবুন।
১. **Dine-In (বসে খাওয়া):** ওয়েটার এসে অর্ডার নেয়, প্লেটে খাবার দেয়।
২. **Drive-Thru (গাড়ি নিয়ে নেওয়া):** মাইকে অর্ডার নেয়, প্যাকেটে খাবার দেয়।
৩. **Online Delivery:** অ্যাপে অর্ডার নেয়, রাইডারকে দেয়।

খেয়াল করুন: **কিচেন (Domain Logic)** কিন্তু একটাই! বিরিয়ানি রান্নার নিয়ম সবার জন্য এক। কিন্তু কাস্টমার হ্যান্ডেল করার নিয়ম (Application Logic) আলাদা।

### কেন আলাদা লেয়ার লাগে?
ধরুন আপনার একটি সফটওয়্যার আছে:
*   **Public App:** সাধারণ ইউজাররা পণ্য কিনবে।
*   **Admin Panel:** এডমিনরা পণ্য স্টক করবে, রিপোর্ট দেখবে।

এখন সাধারণ ইউজারদের অ্যাপে কি আপনি "স্টক ডিলিট" করার বাটন রাখবেন? না! তাই এডমিনের জন্য আলাদা `AdminAppService` এবং পাবলিকের জন্য `PublicAppService` বানানো বুদ্ধিমানের কাজ।

# 💻 কোড দিয়ে পুরোটা বুঝি (Code Example)

আমরা একটি **ই-কমার্স** সিস্টেম দেখব যেখানে **Admin** এবং **Customer**-এর জন্য আলাদা অ্যাপ্লিকেশন লেয়ার আছে।

### ১. Domain Layer (সবার জন্য এক - The Kitchen)
```csharp
public class Product
{
    public string Name { get; private set; }
    public decimal Price { get; private set; }
    public bool IsActive { get; private set; }

    // Domain Logic: প্রাইস কখনো নেগেটিভ হবে না
    public void UpdatePrice(decimal newPrice)
    {
        if (newPrice < 0) throw new Exception("দাম নেগেটিভ হতে পারে না!");
        Price = newPrice;
    }

    // Domain Logic: প্রোডাক্ট ডিঅ্যাক্টিভেট করা
    public void Deactivate()
    {
        IsActive = false;
    }
}
```

### ২. Admin Application Layer (VIP কাউন্টার)
এডমিন সব কিছু করতে পারে।
```csharp
public class ProductAdminAppService
{
    private readonly IRepository<Product> _repo;

    // এডমিন প্রাইস আপডেট করতে পারে
    public void ChangePrice(Guid id, decimal price)
    {
        var product = _repo.Get(id);
        product.UpdatePrice(price); // ডোমেইন লজিক কল হলো
        _repo.Save(product);
        
        // App Logic: লগ রাখা যে এডমিন দাম বদলেছে
        _logger.Log($"Admin changed price to {price}"); 
    }

    // এডমিন প্রোডাক্ট ডিঅ্যাক্টিভেট করতে পারে
    public void BanProduct(Guid id)
    {
        var product = _repo.Get(id);
        product.Deactivate();
        _repo.Save(product);
    }
}
```

### ৩. Public Application Layer (সাধারণ কাউন্টার)
সাধারণ ইউজার শুধু কিনতে পারে, দাম বদলাতে পারে না।
```csharp
public class ProductPublicAppService
{
    private readonly IRepository<Product> _repo;

    // ইউজার শুধু প্রোডাক্ট দেখতে পারে
    public ProductDto GetProduct(Guid id)
    {
        var product = _repo.Get(id);
        
        // App Logic: ইন-অ্যাক্টিভ প্রোডাক্ট ইউজারকে দেখানো যাবে না
        if (!product.IsActive) throw new Exception("প্রোডাক্ট পাওয়া যায়নি!");

        return new ProductDto { Name = product.Name, Price = product.Price };
    }
    
    // এখানে ChangePrice বা BanProduct মেথড নাই! নিরাপদ! 😎
}
```

# ⚠️ সমস্যা ও সমাধান (Problems & Solutions)

### সমস্যা ১: Logic Leaking (লজিক চুইয়ে পড়া) 💧
**Problem:** ডেভেলপাররা আলসেমি করে ডোমেইন লজিক (যেমন: প্রাইস ক্যালকুলেশন) অ্যাপ সার্ভিসে লিখে ফেলে।
**Result:** পরে যখন মোবাইল অ্যাপ বানাতে যায়, তখন ওই লজিক আবার লিখতে হয় (Code Duplication)।
**Solution:** সবসময় নিজেকে প্রশ্ন করুন—*"এই লজিকটা কি অ্যাপ ছাড়া অন্য কোথাও সত্য?"* যদি হ্যাঁ হয়, তবে সেটা ডোমেইনে পাঠান।

### সমস্যা ২: Fat Controller
**Problem:** অ্যাপ সার্ভিস না বানিয়ে সব কোড API Controller-এ লেখা।
**Solution:** কন্ট্রোলারকে শুধু "Traffic Police" হিসেবে রাখুন। আসল কাজ অ্যাপ সার্ভিসকে দিয়ে করান।

# 🌍 রিয়েল-লাইফ ব্যবহার (Advantages)

১. **Security:** `AdminApplication` লেয়ার আলাদা থাকায়, পাবলিক অ্যাপের হ্যাকাররা এডমিন ফিচারগুলো এক্সেস করার সুযোগই পায় না। কোডেই সেই পথ নেই।
২. **Maintenance:** যদি "ডিসকাউন্ট রুল" (Domain Logic) বদলায়, তবে এক জায়গায় বদলালেই এডমিন ও পাবলিক দুই অ্যাপেই আপডেট হয়ে যাবে।
৩. **Clean Code:** পাবলিক অ্যাপের কোড অনেক হালকা থাকে, কারণ সেখানে অপ্রয়োজনীয় এডমিন লজিক লোড হয় না।

# 📝 সারাংশ (Summary)

আজকের ক্লাসের **Take Home Points**:

১. **Domain Logic:** ব্যবসার আসল নিয়ম (সংবিধান)। এটা সবার জন্য এক। (উদাহরণ: ব্যালেন্স চেক)।
২. **Application Logic:** কাজের ধাপ বা ফ্লো (ম্যানেজার)। এটা অ্যাপভেদে ভিন্ন হতে পারে। (উদাহরণ: ইমেইল পাঠানো)।
৩. **Multiple Layers:** পাবলিক ইউজার এবং এডমিনদের জন্য আলাদা আলাদা অ্যাপ্লিকেশন সার্ভিস লেয়ার বা প্রজেক্ট তৈরি করুন।
৪. **Kitchen Rule:** ডোমেইন লেয়ার হলো কিচেন (সবার জন্য এক), আর অ্যাপ্লিকেশন লেয়ার হলো সার্ভিস কাউন্টার (ভিন্ন ভিন্ন)।

ব্যাস! এখন থেকে লজিক আর "জগাখিচুড়ি" হবে না। সব কিছু থাকবে তার নিজের জায়গায়! হ্যাপি আর্কিটেকটিং! 🏗️🚀

অনেকে কোড লেখার সময় **"জগাখিচুড়ি"** পাকিয়ে ফেলেন। বিরিয়ানির মাংস দিয়ে পায়েস রাঁধলে যেমন খেতে জঘন্য হবে, তেমনি বিজনেসের লজিক বাটনের ক্লিকের মধ্যে লিখলে সফটওয়্যার পচে যাবে। 🤢

আজ আমরা শিখব—কোন লজিক কোথায় রাখতে হয় এবং কেন বড় প্রজেক্টে একাধিক অ্যাপ্লিকেশন লেয়ার (Multiple Application Layers) লাগে। আর এসব শিখব একটা **"বিয়ে বাড়ি"**-র উদাহরণ দিয়ে! 💒🕺

# 🛠️ অধ্যায় ১: সেটআপ এবং প্রস্তুতি (Setup & Prerequisites)

আমরা আর্কিটেকচার শিখছি, তাই ফোল্ডার স্ট্রাকচারটা খুব গুরুত্বপূর্ণ। আমরা C# এবং .NET ব্যবহার করব।

### ১. প্রয়োজনীয় টুলস
*   **Visual Studio 2022** বা **VS Code**।
*   **.NET SDK** (6.0+)।

### ২. প্রজেক্ট স্ট্রাকচার তৈরি (Steps)
আমরা হাত দিয়ে ফোল্ডার না বানিয়ে কমান্ড দিয়ে একটি সুন্দর লেয়ারড আর্কিটেকচার বানাব। টার্মিনাল ওপেন করুন:


*   **Application:** সে ডোমেইনকে ব্যবহার করে, কিন্তু UI চেনে না।
*   **UI:** সে অ্যাপ সার্ভিসকে কল দেয়।
এই **"One Way Dependency"**-র কারণে কোড ক্লিন থাকে।

# 💻 অধ্যায় ২: Domain Logic vs Application Logic

### ১. Domain Logic (Business Logic) – "কাবিননামা" 📜
**বিষয়:** ডোমেইন লজিক হলো সেই অকাট্য নিয়ম যা সফটওয়্যার থাকুক বা না থাকুক, ব্যবসার জন্য সত্য।

**মজার উদাহরণ:** বিয়েতে "বরের বয়স ২১ হতে হবে"—এটা আইন (Domain Logic)। বর শেরওয়ানি পরবে নাকি পাঞ্জাবি, সেটা ইভেন্ট ম্যানেজমেন্টের বিষয়, আইনের না।

**Code (Domain Layer):**
আমরা `Account` নামক একটি এনটিটি বানাব।

```csharp
// LogicMaster.Domain/Account.cs
namespace LogicMaster.Domain;

public class Account
{
    public Guid Id { get; private set; }
    public decimal Balance { get; private set; }
    public bool IsFrozen { get; private set; }

    public Account(Guid id, decimal initialBalance)
    {
        Id = id;
        Balance = initialBalance;
        IsFrozen = false;
    }

    // 🔥 Pure Domain Logic: টাকা তোলার নিয়ম
    public void Withdraw(decimal amount)
    {
        // রুল ১: অ্যাকাউন্ট ফ্রিজ থাকলে টাকা তোলা যাবে না
        if (IsFrozen) 
            throw new Exception("অ্যাকাউন্ট ফ্রিজ করা হয়েছে মামা! টাকা পাবেন না।");

        // রুল ২: ব্যালেন্সের বেশি তোলা যাবে না
        if (Balance < amount)
            throw new Exception("বাপের ব্যাংকে এত টাকা নাই!");

        Balance -= amount;
    }

    // 🔥 Domain Logic: অ্যাকাউন্ট ফ্রিজ করা
    public void FreezeAccount()
    {
        IsFrozen = true;
    }
}
```
**কেন এভাবে লিখলাম?**
দেখুন, `Withdraw` মেথডের লজিকগুলো অ্যাপের বাটন বা কালারের ওপর নির্ভর করে না। এগুলো ব্যবসার **Core Rules**। তাই এগুলো এনটিটির পেটের ভেতর।

---

### ২. Application Logic (Use Case) – "ইভেন্ট ম্যানেজার" 🤵
**বিষয়:** অ্যাপ্লিকেশন লজিক হলো কাজের ধাপগুলো সাজানো। সে নিজে কোনো রুল বানায় না, সে শুধু রুলগুলো এক্সিকিউট করে।

**মজার উদাহরণ:** ইভেন্ট ম্যানেজার (Application Service) কাজী সাহেবকে (Domain) ডাকে, কবুল পড়ায়, তারপর মিষ্টি মুখ করায়। সে নিজে কবুল পড়ায় না।

**Code (Application Layer):**

```csharp
// LogicMaster.Application/AccountAppService.cs
using LogicMaster.Domain;

namespace LogicMaster.Application;

public class AccountAppService
{
    // আসল প্রজেক্টে এখানে রিপজিটরি থাকবে, আমরা সিমপ্লিফাইড রাখলাম
    private static Account _myAccount = new Account(Guid.NewGuid(), 5000); // মেমোরিতে ডাটা

    // Use Case: টাকা তোলা
    public void WithdrawMoney(decimal amount)
    {
        Console.WriteLine("--- প্রসেস শুরু: টাকা তোলা হচ্ছে ---");

        try
        {
            // ১. ডোমেইন লজিক কল করা (আসল কাজ)
            _myAccount.Withdraw(amount);
            
            // ২. অ্যাপ্লিকেশন লজিক: ডাটাবেসে সেভ করা (এখানে সিমুলেট করা হলো)
            Console.WriteLine("✅ ডাটাবেসে আপডেট করা হলো।");

            // ৩. অ্যাপ্লিকেশন লজিক: ইউজারকে এসএমএস পাঠানো
            Console.WriteLine($"📧 SMS পাঠানো হলো: আপনার নতুন ব্যালেন্স {_myAccount.Balance}");
        }
        catch (Exception ex)
        {
            Console.WriteLine($"⛔ এরর: {ex.Message}");
        }
    }
}
```
**কেন এভাবে লিখলাম?**
SMS পাঠানো বা ডাটাবেসে সেভ করা—এগুলো ব্যবসার "কোর রুল" না, এগুলো সফটওয়্যারের ফিচার বা ফ্লো। তাই এগুলো অ্যাপ্লিকেশন লেয়ারে।

# 🏢 অধ্যায় ৩: Multiple Application Layers (একাধিক কাউন্টার)

**কেন লাগবে?**
ধরুন আপনার অ্যাপে দুই ধরনের ইউজার আছে:
১. **সাধারণ ইউজার (Customer):** শুধু টাকা তুলতে পারে।
২. **ব্যাংক ম্যানেজার (Admin):** অ্যাকাউন্ট ফ্রিজ করতে পারে।

আপনি কি সাধারণ ইউজারের অ্যাপে "Freeze Account" বাটন রাখবেন? **কখনো না!**
তাই আমরা একই ডোমেইন লজিক ব্যবহার করে, দুটি আলাদা অ্যাপ্লিকেশন লেয়ার বা সার্ভিস বানাব।

**Code (Application Layer - Extended):**

```csharp
// ১. সাধারণ কাস্টমারদের জন্য সার্ভিস
public class CustomerAppService
{
    private Account _account; // রিপজিটরি থেকে আসবে

    public CustomerAppService(Account acc) { _account = acc; }

    public void MyWithdraw(decimal amount)
    {
        // কাস্টমার শুধু উইথড্র করতে পারে
        _account.Withdraw(amount);
    }
    
    // এখানে Freeze করার কোনো মেথড নেই! নিরাপদ! 😎
}

// ২. এডমিন বা ম্যানেজারদের জন্য সার্ভিস
public class AdminAppService
{
    private Account _account;

    public AdminAppService(Account acc) { _account = acc; }

    public void BlockUser()
    {
        // এডমিন পাওয়ার খাটিয়ে অ্যাকাউন্ট ফ্রিজ করতে পারে
        _account.FreezeAccount();
        Console.WriteLine("⚠️ সাবধান! এডমিন অ্যাকাউন্ট ফ্রিজ করে দিয়েছে।");
    }
}
```

# ⚠️ অধ্যায় ৫: সমস্যা ও সমাধান (Common Problems)

### সমস্যা ১: Logic Leaking (লজিক লিক হওয়া) 💧
**Problem:** ডেভেলপাররা আলসেমি করে `Withdraw` মেথডের ভেতরের `if (Balance < amount)` লজিকটা অ্যাপ সার্ভিসে লিখে ফেলে।
**Why Bad:** পরে যদি মোবাইল অ্যাপ বা এটিএম মেশিনের জন্য কোড লেখেন, তখন ওই লজিক আবার লিখতে হবে। এক জায়গায় ভুলে গেলে সর্বনাশ!
**Solution:** `if-else` যা ব্যবসার নিয়ম, তা সবসময় **Domain (Entity)**-তে থাকবে।

### সমস্যা ২: One Service for All (সবার জন্য এক সার্ভিস)
**Problem:** `AccountAppService`-এ `Withdraw` এবং `FreezeAccount` দুটোই রাখা।
**Why Bad:** ফ্রন্টএন্ড ডেভেলপার ভুল করে সাধারণ ইউজারের ড্যাশবোর্ডে "Freeze" বাটন বসিয়ে দিতে পারে, কারণ সে দেখবে API তে মেথডটা আছে।
**Solution:** রোল (Role) অনুযায়ী আলাদা অ্যাপ সার্ভিস বা ইন্টারফেস ব্যবহার করুন (Multiple Application Layers)।

# 📝 অধ্যায় ৬: সারাংশ (Summary)

আজকের ক্লাসের **Key Points**:

১. **Domain Logic:** ব্যবসার সংবিধান (যেমন: ব্যালেন্স চেক)। এটি **Entity**-র ভেতরে থাকে। এটি UI বা অ্যাপ চেনে না।
২. **Application Logic:** কাজের ফ্লো বা প্রসেস (যেমন: ইমেইল পাঠানো, সেভ করা)। এটি **Application Service**-এ থাকে।
৩. **Multiple Layers:** ভিন্ন ভিন্ন ইউজারের জন্য (Admin vs User) ভিন্ন ভিন্ন অ্যাপ সার্ভিস তৈরি করা বুদ্ধিমানের কাজ। এতে সিকিউরিটি বাড়ে এবং কোড ক্লিন থাকে।
৪. **Dependency Rule:** UI ডিপেন্ড করে Application-এর ওপর, Application ডিপেন্ড করে Domain-এর ওপর। উল্টোটা কখনো হবে না।

**Real-World Scenario:**
একটি ই-কমার্স সাইটে:
*   **Public App:** ইউজার অর্ডার করতে পারে (OrderAppService)।
*   **Warehouse App:** স্টোরকিপার স্টক আপডেট করতে পারে (InventoryAppService)।
*   **Admin Panel:** মালিক প্রাইস চেঞ্জ করতে পারে (ProductAdminAppService)।
সবার জন্য আলাদা অ্যাপ লেয়ার, কিন্তু পেছনের **Domain Logic (Product Entity)** সবার জন্য এক!
