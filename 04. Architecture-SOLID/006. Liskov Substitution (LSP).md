স্বাগতম ফিউচার আর্কিটেক্টরা! 👷‍♂️🚀

আমি আপনাদের আর্কিটেকচার গুরু। আজ আমরা SOLID প্রিন্সিপালের **‘L’** মানে **Liskov Substitution Principle (LSP)** নিয়ে আড্ডা দেব।

নামটা শুনে ভয় পাওয়ার কিছু নেই। বারবারা লিসকভ (Barbara Liskov) নামের এক ভদ্রমহিলা এটি আবিষ্কার করেছিলেন, তাই তাঁর নামে নামকরণ। তবে আমি এটাকে বলি **"বাপ কা বেটা" (Like Father, Like Son)** প্রিন্সিপাল।

সহজ কথায় এর স্লোগান হলো:
**"বাপ যা যা পারে, ছেলেরও (অন্তত) তা তা পারতে হবে। বাপকে সরিয়ে ছেলেকে বসালে যেন কোনো গণ্ডগোল না হয়!"** 👨‍👦

ভাবুন তো, আপনি একটা রিমোট কন্ট্রোল খেলনা গাড়ি কিনলেন। প্যাকেটে লেখা "ব্যাটারি লাগান, চলবে"।
আপনি ডিউরাসেল ব্যাটারি লাগালেন, চলল। (এটা বাপ)।
এখন যদি আপনি চাইনিজ ব্যাটারি (এটা ছেলে) লাগান, আর গাড়িটা বিস্ফোরিত হয়—তাহলে কি হবে? মেজাজ খারাপ হবে, তাই না?
কারণ ব্যাটারি স্লটে যেকোনো ব্যাটারি বসালেই কাজ করা উচিত। এটাই LSP।

যদি প্যারেন্ট ক্লাসের জায়গায় চাইল্ড ক্লাস বসালে কোড ক্রাশ করে বা অদ্ভুত আচরণ করে—তার মানে আপনি LSP ভেঙে ফেলেছেন বা **"বাঁশ"** খেয়েছেন।

চলুন বিস্তারিত শিখি!

### LSP-এর প্রধান বিষয়বস্তু (Key Objects of LSP)

LSP বুঝতে হলে ৩টি টেকনিক্যাল বিষয় বা "শর্ত" মানতে হয়। এগুলোকে আমরা "বাপ-ছেলের চুক্তি" বলতে পারি।

#### ১. Preconditions (শর্ত বা ইনপুট)

**What (এটা কী):**
প্যারেন্ট ক্লাস কোনো কাজ শুরু করার আগে যে শর্ত দেয়, চাইল্ড ক্লাস সেই শর্তকে আরও কঠিন (Strict) করতে পারবে না।

**Bangla Example:**
বাবা (Parent) বললেন: "আমাকে ১০০ টাকা দিলেই আমি বাজার করে দেব।"
ছেলে (Child) বলল: "না! আমাকে ৫০০ টাকার চকচকে নোট না দিলে আমি নড়ব না!"

এখানে ছেলে বাবার চেয়ে বেশি ডিমান্ডিং। এখন আপনি যদি বাবাকে সরিয়ে ছেলেকে পাঠান, কাজ হবে না কারণ আপনার পকেটে হয়তো ১০০ টাকাই ছিল। LSP ভায়োলেশন! ❌

**Rule:** চাইল্ড ক্লাসের ইনপুট শর্ত বাবার সমান বা তার চেয়ে সহজ হতে হবে, কঠিন হওয়া যাবে না।

#### ২. Postconditions (ফলাফল বা আউটপুট)

**What (এটা কী):**
প্যারেন্ট ক্লাস কাজ শেষে যা রিটার্ন করার কথা বলেছিল, চাইল্ড ক্লাসকে অবশ্যই সেই একই বা তার চেয়ে ভালো কিছু রিটার্ন করতে হবে। কম দেওয়া যাবে না।

**Bangla Example:**
বাবা বললেন: "বাজার শেষে আমি তোমাকে ফ্রেশ আপেল দেব।"
ছেলে বলল: "আমি তোমাকে পচা আপেল বা প্লাস্টিকের আপেল দেব।"

এখন আপনি যদি আপেল খাওয়ার আশায় থাকেন, আর ছেলে আপনাকে প্লাস্টিক দেয়—আপনার দাঁত ভাঙবে! LSP ভায়োলেশন! ❌

**Rule:** চাইল্ড ক্লাসকে অবশ্যই ভ্যালিড রেজাল্ট দিতে হবে, কোনো ধোঁকাবাজি (Null বা Exception) করা যাবে না।

#### ৩. Invariants (অপরিবর্তনীয় সত্য)

**What (এটা কী):**
ক্লাসের মূল বৈশিষ্ট্য বা ধর্ম, যেটা বদলানো যাবে না।

**Bangla Example:**
বাবা হলেন "পাখি" (Bird)। পাখির ধর্ম হলো তার ডানা আছে এবং সে ডিম পারে।
ছেলে হলো "পেঙ্গুইন"। সে যদি বলে "আমার ডানা নেই, আমি হাত দিয়ে চলি"—তাহলে সে আর পাখি থাকল না।

**Rule:** চাইল্ড ক্লাসকে ফ্যামিলির মূল নিয়ম মেনে চলতে হবে।

### সমস্যা ও কোড উদাহরণ (Problems with Code)

LSP না মানলে কী ভয়ানক সমস্যা হয়, তা আমরা একটা ক্লাসিক উদাহরণ দিয়ে দেখব।

#### ❌ The Problem: পাখি ও পেঙ্গুইন সমস্যা

ধরি, আমাদের একটা ক্লাস আছে `Bird` এবং তার মেথড `Fly()`।

```csharp
public class Bird
{
    public virtual void Fly()
    {
        Console.WriteLine("আমি আকাশে উড়ছি! 🦅");
    }
}

public class Parrot : Bird // টিয়া পাখি
{
    // টিয়া উড়তে পারে, তাই সমস্যা নেই
}

public class Penguin : Bird // পেঙ্গুইন
{
    public override void Fly()
    {
        // পেঙ্গুইন তো উড়তে পারে না! তাহলে কী হবে?
        throw new Exception("ও ভাই! আমি তো উড়তে পারি না! 🐧");
    }
}
```

**ব্যবহার (Usage):**
```csharp
List<Bird> birds = new List<Bird> { new Parrot(), new Penguin() };

foreach (var bird in birds)
{
    bird.Fly(); // যখন লুপ পেঙ্গুইনে আসবে, কোড ক্রাশ করবে! 💥
}
```
**কেন সমস্যা?**
আপনি জানেন সব `Bird` উড়তে পারে। তাই আপনি নিশ্চিন্তে `Fly()` কল করেছেন। কিন্তু `Penguin` সেই বিশ্বাস ভেঙে দিয়েছে। বাপ (Bird) বলেছিল উড়বে, ছেলে (Penguin) বলল পারব না। এটাই LSP ভায়োলেশন।

---

### সমাধান (Solution to the Problem) ✅

সমাধান হলো—জোর করে সম্পর্ক তৈরি করবেন না। পেঙ্গুইন পাখি ঠিকই, কিন্তু "উড়ন্ত পাখি" না। তাই ক্লাস ভাগ করুন।

```csharp
// ১. বেস ক্লাস (সাধারণ পাখি)
public class Bird 
{
    public void Eat() { /* সবাই খায় */ }
}

// ২. যারা উড়তে পারে তাদের জন্য আলাদা ক্লাস
public class FlyingBird : Bird
{
    public virtual void Fly() { /* উড়ার লজিক */ }
}

// ৩. এখন ভাগ করুন
public class Parrot : FlyingBird // টিয়া উড়তে পারে
{
    public override void Fly() { Console.WriteLine("টিয়া উড়ছে"); }
}

public class Penguin : Bird // পেঙ্গুইন শুধু পাখি, উড়ন্ত না
{
    // এখানে Fly মেথডই নেই, তাই ভুল করে কল করার চান্সও নেই!
}
```

এখন আর কোড ক্রাশ করবে না। কারণ আপনি `Penguin` এর কাছে `Fly` চাইতেই পারবেন না।

### কেন LSP গুরুত্বপূর্ণ? (Importance)

১. **বিশ্বাসযোগ্যতা (Reliability):** আপনি জানেন প্যারেন্ট ক্লাস যা করে, চাইল্ড ক্লাসও তাই করবে। কোড ক্রাশ করবে না।
২. **Maintainability:** নতুন ক্লাস (যেমন: উটপাখি) যোগ করলে পুরনো কোড ভাঙবে না।
৩. **Polymorphism:** OOP-এর পলিমরফিজম ঠিকঠাক কাজ করার জন্য LSP অক্সিজেন হিসেবে কাজ করে।

### বাস্তব জীবনের ব্যবহার (Real-World Uses)

**১. পেমেন্ট সিস্টেম:**
ধরুন `PaymentService` নামে একটা ক্লাস আছে যার মেথড `ProcessCardPayment()`.
*   `VisaCardService` (Child) -> ঠিক আছে।
*   `BkashService` (Child) -> ঠিক আছে।
*   `CashOnDeliveryService` (Child) -> **সমস্যা!** কারণ ক্যাশ পেমেন্টে কার্ড প্রসেসিং লাগে না।
*   **সমাধান:** `PaymentService` কে ভেঙে `OnlinePayment` এবং `OfflinePayment` এ ভাগ করা।

**২. ফাইল সিস্টেম:**
`File` ক্লাসে যদি `Write()` মেথড থাকে, আর আপনি `ReadOnlyFile` নামে একটা চাইল্ড ক্লাস বানান—তখন `Write()` কল করলে এরর খাবেন। তাই `ReadOnlyFile` কে `WritableFile` এর চাইল্ড বানানো যাবে না।

### সারসংক্ষেপ (Summary) 📝

বন্ধুরা, Liskov Substitution Principle (LSP)-এর মূল মন্ত্র হলো:

*   **Substitutability:** বাপকে সরিয়ে ছেলেকে বসালে যেন কেউ বুঝতে না পারে যে বাপ নেই। (Ghost Driver এর মতো! 👻)
*   **No Surprises:** চাইল্ড ক্লাস এমন কোনো কাজ করবে না যাতে ইউজার অবাক হয়ে যায় (যেমন: এরর দেওয়া বা উল্টাপাল্টা রেজাল্ট দেওয়া)।
*   **Is-a Relationship:** "পেঙ্গুইন ইজ আ বার্ড" এটা বায়োলজিতে সত্য হলেও, কোডিংয়ে যদি ফ্লাই মেথড থাকে তবে সেটা সত্য না।

**শেষ কথা:** জোর করে সম্পর্ক গড়বেন না। যদি দেখেন ছেলে বাপের মতো আচরণ করতে পারছে না, তবে জোর করে ইনহেরিটেন্স (Inheritance) চাপাবেন না। তাদের আলাদা করে দিন।

LSP মানুন, কোড ক্রাশ থেকে বাঁচুন! হ্যাপি কোডিং! 🚀😎

স্বাগতম **SOLID** সিরিজের সবচেয়ে কনফিউজিং কিন্তু মজার পর্বে। আজ আমরা শিখব **Liskov Substitution Principle (LSP)**।

নামটা শুনে মনে হচ্ছে কোনো রাশিয়ান বিজ্ঞানীর ফর্মুলা, তাই না? 😅 আসলে বারবারা লিসকভ (Barbara Liskov) নামের এক ভদ্রমহিলা এটা আবিষ্কার করেছেন। তবে আমি এটাকে বলি **"বাপ কা বেটা" (Like Father, Like Son)** প্রিন্সিপাল।

সহজ কথায় এর স্লোগান হলো:
**"বাপকে সরিয়ে ছেলেকে বসালে যদি কাজ না হয়, বা ভেজাল লাগে—তাহলে সেই ছেলে ত্যাজ্যপুত্র!"** 🤣

ভাবুন তো, আপনি দোকানে গিয়ে বললেন, "ভাই, একটা রিমোটের ব্যাটারি দেন।"
দোকানদার আপনাকে ব্যাটারির বদলে একটা **আলু** ধরিয়ে দিয়ে বলল, "ভাই, আলুর ভেতরেও তো এনার্জি আছে, কাজ চালিয়ে নেন।"
আপনি কি মানবেন? না! কারণ ব্যাটারি স্লটে আলু ফিট হয় না, আর রিমোটও চলবে না।
এখানে **ব্যাটারি** হলো প্যারেন্ট ক্লাস, আর **আলু** হলো দুষ্টু চাইল্ড ক্লাস যে ব্যাটারির জায়গা নিতে পারছে না। এটাই LSP ভায়োলেশন।

চলুন, কোড করে দেখি আলু আর ব্যাটারির এই সমস্যা কিভাবে সমাধান করা যায়!

### ২. কোডিং পর্ব: পাখি ও পেঙ্গুইন সমস্যা 🐧

আমরা সবাই জানি **পাখি (Bird)** উড়তে পারে। তাই আমরা একটা `Bird` ক্লাস বানাব যার `Fly()` মেথড আছে।

#### দৃশ্যপট ১: LSP না মানলে (দুর্ঘটনা) ❌

`Program.cs` ফাইলে নিচের কোডটি লিখুন:

```csharp
// ❌ BAD Code (Violating LSP)

// বাপ ক্লাস
public class Bird
{
    public virtual void Fly()
    {
        Console.WriteLine("আমি আকাশে ডানা মেলে উড়ছি! 🦅");
    }
}

// টিয়া পাখি (ভালো ছেলে)
public class Parrot : Bird
{
    // টিয়া উড়তে পারে, তাই বাপের Fly মেথড ব্যবহার করতে তার সমস্যা নেই।
}

// পেঙ্গুইন (সমস্যাযুক্ত ছেলে)
public class Penguin : Bird
{
    public override void Fly()
    {
        // পেঙ্গুইন তো উড়তে পারে না! 
        // কিন্তু জোর করে Bird থেকে ইনহেরিট করায় তাকে Fly মেথড রাখতেই হচ্ছে।
        throw new Exception("ওরে বাপরে! আমি তো উড়তে পারি না! আমাকে ছাদ থেকে ফেলে দিয়েন না! 😭");
    }
}

class Program
{
    static void Main(string[] args)
    {
        // আমরা পাখির লিস্ট বানাচ্ছি
        List<Bird> birds = new List<Bird>
        {
            new Parrot(),
            new Penguin()
        };

        foreach (var bird in birds)
        {
            Console.WriteLine($"Testing {bird.GetType().Name}...");
            // আমরা চোখ বন্ধ করে বিশ্বাস করেছি যে সব পাখিই উড়বে
            bird.Fly(); 
        }
    }
}
```

**কি ঘটবে?**
কোড রান করলে **Parrot** সুন্দর উড়বে, কিন্তু **Penguin** আসার সাথে সাথে প্রোগ্রাম **CRASH** করবে (Exception খাবে)।
**LSP রুল:** প্যারেন্ট ক্লাসের (`Bird`) জায়গায় চাইল্ড ক্লাস (`Penguin`) বসালে যদি কোড ফাটে, তবে LSP মানা হয়নি।

#### দৃশ্যপট ২: LSP মানলে (স্মার্ট সমাধান) ✅

আমরা জোর করে পেঙ্গুইনকে ওড়াব না। আমরা ক্লাসগুলোকে লজিক্যালি ভাগ করব।

```csharp
// ✅ GOOD Code (Applying LSP)

// ১. একদম বেসিক ক্লাস (যাদের ডানা আছে)
public class Bird
{
    public void Eat()
    {
        Console.WriteLine("আমি খাবার খাচ্ছি... 🐛");
    }
}

// ২. যারা উড়তে পারে, তাদের জন্য আলাদা গ্রুপ
public class FlyingBird : Bird
{
    public virtual void Fly()
    {
        Console.WriteLine("আমি আকাশে উড়ছি! ☁️");
    }
}

// ৩. যারা উড়তে পারে না (যেমন পেঙ্গুইন), তারা সরাসরি Bird বা RunningBird হবে
public class NonFlyingBird : Bird
{
    public void Walk()
    {
        Console.WriteLine("আমি হেলেদুলে হাঁটছি... 🐧");
    }
}

// --- এখন ইমপ্লিমেন্টেশন ---

public class Parrot : FlyingBird // টিয়া উড়ন্ত পাখি
{
    // সে Fly() মেথড ইনহেরিট করেছে
}

public class Penguin : NonFlyingBird // পেঙ্গুইন হাঁটা পাখি
{
    // এর কাছে Fly() মেথডই নেই, তাই ভুল করে ওড়ানোর চান্স নেই!
}

class Program
{
    static void Main(string[] args)
    {
        // যারা উড়তে পারে তাদের লিস্ট
        List<FlyingBird> flyingBirds = new List<FlyingBird>
        {
            new Parrot(),
            // new Penguin() // ❌ এখানে আপনি পেঙ্গুইন ঢোকাতেই পারবেন না! কম্পাইলার আগেই লাল দাগ দেবে।
        };

        foreach (var bird in flyingBirds)
        {
            bird.Fly(); // ১০০% গ্যারান্টি, কোড ফাটবে না।
        }

        // পেঙ্গুইন তার নিজের মতো হাঁটবে
        Penguin p = new Penguin();
        p.Eat();
        p.Walk();
    }
}
```

### ৩. লজিক ও ব্যাখ্যা (Logic Explanation) 🧠

**কেন আগের কোড ভুল ছিল?**
LSP বলে, চাইল্ড ক্লাসকে অবশ্যই প্যারেন্ট ক্লাসের সব আচরণের সাথে খাপ খাওয়াতে হবে। আগের কোডে `Penguin` কে জোর করে `Fly` করতে বলা হয়েছিল, যা সে পারে না। ফলে সে `Exception` থ্রো করেছে। এটা ইউজারের বিশ্বাসের সাথে বিশ্বাসঘাতকতা!

**নতুন কোডে কী করলাম?**
আমরা `Bird` কে ভেঙে দুটি ভাগে ভাগ করলাম:
১. `FlyingBird` (যারা ওড়ে)
২. `NonFlyingBird` (যারা ওড়ে না)

এখন `Parrot` হলে সে `FlyingBird` হবে, আর `Penguin` হলে `NonFlyingBird`। ফলে কেউ ভুল করেও পেঙ্গুইনকে ওড়াতে পারবে না। **বাপের জায়গায় ছেলে বসালে আর কোনো ভেজাল হবে না।**

### ৪. সমস্যা ও সমাধান (Common Problems & Resolutions) ⚠️

**সমস্যা ১: "NotImplementedException" এর ছড়াছড়ি**
আপনি যদি দেখেন আপনার কোডে অনেক মেথড আছে যেগুলোর ভেতরে লেখা `throw new NotImplementedException();`—তার মানে আপনি LSP ভায়োলেশন করছেন।
*   *উদাহরণ:* `CreditCard` ক্লাসে `WithdrawCash()` মেথড থাকা (ক্রেডিট কার্ড দিয়ে এটিএম থেকে ক্যাশ নাও তোলা যেতে পারে)।
*   **সমাধান:** ইন্টারফেস বা ক্লাস ভেঙে ছোট করুন। জোর করে মেথড চাপাবেন না।

**সমস্যা ২: Type Checking (is/as operator)**
যদি আপনাকে কোডে বারবার চেক করতে হয়—
`if (bird is Penguin) { // Don't fly } else { bird.Fly() }`
এটাও LSP ভায়োলেশন। প্যারেন্ট ক্লাস ব্যবহার করার সময় টাইপ চেক করা লাগার মানেই হলো আর্কিটেকচারে গলদ আছে।

### ৫. বাস্তব জীবনের উদাহরণ (Real-Life Scenario) 🌍

**ব্যাংকিং সিস্টেম (Account Type):**

ধরুন `BankAccount` নামে একটা ক্লাস আছে।
*   `FixedDepositAccount` (Child)
*   `SavingsAccount` (Child)

প্যারেন্ট ক্লাসে মেথড আছে `Withdraw()` (টাকা তোলা)।
এখন `FixedDepositAccount` এ মেয়াদ শেষ হওয়ার আগে টাকা তোলা যায় না।
যদি কেউ `FixedDepositAccount` কে `BankAccount` হিসেবে ব্যবহার করে `Withdraw()` কল দেয় এবং এরর খায়—সেটা LSP ভায়োলেশন।

**সমাধান:**
`Withdraw()` মেথডটা `WithdrawableAccount` নামক আলাদা ক্লাসে রাখা উচিত। `FixedDepositAccount` শুধু `Deposit()` মেথড সাপোর্ট করবে।

### ৬. সারাংশ (Summary) 📝

আজকের ক্লাসের মূল কথা:

1.  **LSP (Liskov Substitution Principle):** সাব-ক্লাস (Child) যেন সুপার-ক্লাস (Parent) এর পরিপূর্ণ বিকল্প হয়।
2.  **No Surprises:** চাইল্ড ক্লাস এমন কিছু করবে না যাতে প্রোগ্রাম ক্রাশ করে (যেমন: "আমি এটা পারি না" বলে Exception দেওয়া)।
3.  **Inheritance is dangerous:** বুঝে শুনে ইনহেরিটেন্স ব্যবহার করুন। "বাপের সম্পত্তি পেলেই বাপের মতো হওয়া যায় না"—এটা মনে রাখবেন।

**গুরুত্ব:**
LSP মানলে আপনার কোড হবে **Robust** (মজবুত)। রানটাইমে অদ্ভুত সব এরর আসবে না এবং আপনি নিশ্চিন্তে ঘুমাতে পারবেন।
