### ১. পটভূমি: SimUDuck অ্যাপের গল্প (The Scenario)

ধরুন, আপনি একটা কোম্পানি **"SimUDuck"**-এ কাজ করেন। তারা হাঁস (Duck) নিয়ে একটা গেম বানাচ্ছে। শুরুতে কোডটা খুব সিম্পল ছিল।

**আগের ডিজাইন (Inheritance):**
ডেভেলপাররা একটা `Duck` (সুপারক্লাস) বানিয়েছিল। সব হাঁস (যেমন: `MallardDuck`, `RedheadDuck`) এই ক্লাসকে **Inherit** করত।
*   `quack()` (প্যাক প্যাক করা)
*   `swim()` (সাঁতার কাটা)
*   `display()` (দেখতে কেমন)

**সমস্যা শুরু (The Problem):**
একদিন কোম্পানির বস এসে বলল, "মার্কেট খুব কম্পিটিটিভ! আমাদের হাঁসগুলোকে **উড়তে (Fly)** হবে!"
ডেভেলপার জো (Joe) ভাবল, "আরে এ তো ডাল-ভাত!" সে `Duck` সুপারক্লাসে একটা `fly()` মেথড যোগ করে দিল। সে ভাবল, যেহেতু সব হাঁস `Duck` ক্লাসকে ইনহেরিট করে, তাই সবাই এখন উড়তে পারবে। **Bingo!**

কিন্তু গেম রিলিজের পর দেখা গেল **Rubber Duck (খেলনা প্লাস্টিকের হাঁস)**-ও আকাশে উড়ছে! 😱

### ২. ইনহেরিটেন্সের বিপদ (Why Inheritance Failed)

**কি ঘটেছিল?**
কোডে `fly()` মেথড সুপারক্লাসে দেওয়ার ফলে, জীবন্ত হাঁসের পাশাপাশি প্লাস্টিকের হাঁস বা কাঠের হাঁসও (Decoy Duck) ওড়ার ক্ষমতা পেয়ে গেছে।

**কেন কাজ করেনি?**
*   ইনহেরিটেন্স ব্যবহার করলে অবাঞ্ছিত সাব-ক্লাসেও কোড চলে যায়।
*   কোডের মেইনটেনেন্স কঠিন হয়ে যায়। ভবিষ্যতে যদি এমন হাঁস আসে যা উড়তে পারে না কিন্তু ডাকে, তখন আবার `fly()` মেথডকে ওভাররাইড করে বন্ধ করতে হবে। এটা একটা **"প্যারা"**।

---

### ৩. ইন্টারফেস ব্যবহারের চেষ্টা (The Interface Attempt)

জো ভাবল, "ঠিক আছে, ইনহেরিটেন্স বাদ। আমি `Flyable` আর `Quackable` নামে দুটো **ইন্টারফেস (Interface)** বানাব। যারা উড়বে শুধু তারা `Flyable` ইমপ্লিমেন্ট করবে।"

**সমস্যা:**
*   **কোড ডুপ্লিকেশন (Code Duplication):** ধরুন ৫০ রকমের হাঁস উড়তে পারে। আপনাকে ৫০ বার ওড়ার কোড লিখতে হবে (কারণ জাভা ইন্টারফেসে কোনো কোড বডি থাকে না - *Java 8 এর আগের কথা চিন্তা করুন*)।
*   **পরিবর্তন কঠিন:** যদি ওড়ার স্টাইল একটু চেঞ্জ করতে হয়, তবে ৫০টা ক্লাসে গিয়ে কোড ঠিক করতে হবে। জীবন তেজপাতা হয়ে যাবে!

---

### ৪. ডিজাইন প্রিন্সিপাল ১: যা পরিবর্তনশীল, তাকে আলাদা করো (Encapsulate What Varies)

**থিওরি:**
আপনার অ্যাপলিকেশনের যে অংশটা বারবার পরিবর্তন হয়, সেটাকে মূল কোড থেকে বের করে আলাদা করে ফেলুন।

**এখানে প্রয়োগ:**
হাঁসের `fly()` এবং `quack()` আচরণগুলো হাঁস ভেদে আলাদা। তাই এগুলোকে `Duck` ক্লাস থেকে বের করে আলাদা ক্লাসে নিয়ে যেতে হবে।

---

### ৫. ডিজাইন প্রিন্সিপাল ২: ইন্টারফেসের মাধ্যমে কোড করা (Program to an Interface)

**থিওরি:**
আমরা কনক্রিট ক্লাস (Concrete Class) এর ওপর নির্ভর করব না। আমরা ইন্টারফেস বা সুপার টাইপের ওপর নির্ভর করব।

**এখানে প্রয়োগ:**
আমরা দুটো ইন্টারফেস বানাব:
১. `FlyBehavior`
2. `QuackBehavior`

এখন আমরা বিভিন্ন ক্লাস বানাব যা এই ইন্টারফেসগুলো ইমপ্লিমেন্ট করবে। যেমন:
*   `FlyWithWings` (ডানা দিয়ে ওড়ে)
*   `FlyNoWay` (উড়তে পারে না)
*   `Quack` (জোরে ডাকে)
*   `Squeak` (খেলনা হাঁসের মত শব্দ করে)

**সুবিধা:**
এখন আমরা নতুন কোনো ওড়ার স্টাইল যোগ করতে চাইলে `Duck` ক্লাসে হাত দিতে হবে না। শুধু নতুন একটা ক্লাস বানালেই হবে।

---

### ৬. ডিজাইন প্রিন্সিপাল ৩: কম্পোজিশন > ইনহেরিটেন্স (Favor Composition over Inheritance)

**সবচেয়ে গুরুত্বপূর্ণ পার্ট!**
আগে আমরা ভাবতাম "হাঁস **হলো** একটা পাখি" (Duck **IS-A** Bird)।
এখন আমরা ভাবব "হাঁসের **আছে** ওড়ার ক্ষমতা" (Duck **HAS-A** FlyBehavior)।

আমরা `Duck` ক্লাসের ভেতরে `FlyBehavior` এবং `QuackBehavior` টাইপের দুটো ভেরিয়েবল রাখব। হাঁস নিজে উড়বে না, সে এই ভেরিয়েবলগুলোকে বলবে কাজটা করে দিতে। একে বলে **ডেলিগেশন (Delegation)**।

**সহজ উদাহরণ (Bangla):**
ধরুন আপনি নিজে গাড়ি মেরামত করতে পারেন না। কিন্তু আপনার একজন "মেকানিক" আছে। গাড়ি নষ্ট হলে আপনি নিজে সেটা ঠিক করেন না, মেকানিককে বলেন, "ভাই, ঠিক করে দে।" এখানে আপনি কাজের দায়িত্ব মেকানিকের ওপর ডেলিগেট (Delegate) করলেন।

### ৭. স্ট্র্যাটেজি প্যাটার্ন (The Strategy Pattern)

এতক্ষণ আমরা যা করলাম, এটাই হলো **Strategy Pattern**।

**সংজ্ঞা:**
স্ট্র্যাটেজি প্যাটার্ন অ্যালগরিদমগুলোর একটি ফ্যামিলি তৈরি করে (যেমন: ওড়ার বিভিন্ন স্টাইল), সেগুলোকে আলাদা ক্লাসে বন্দি (Encapsulate) করে এবং সেগুলোকে অদল-বদল (Interchangeable) করার সুযোগ দেয়।

**বাস্তব কোড স্ট্রাকচার (সহজ বাংলায়):**

```java
// ১. ইন্টারফেস (Interface)
interface FlyBehavior {
    void fly();
}

// ২. অ্যালগরিদম ১ (বাস্তব ওড়া)
class FlyWithWings implements FlyBehavior {
    public void fly() {
        System.out.println("আমি ডানা দিয়ে উড়ছি!");
    }
}

// ৩. অ্যালগরিদম ২ (উড়তে না পারা)
class FlyNoWay implements FlyBehavior {
    public void fly() {
        System.out.println("আমি উড়তে পারি না ভাই!");
    }
}

// ৪. মূল ক্লাস (Client)
abstract class Duck {
    FlyBehavior flyBehavior; // HAS-A সম্পর্ক (Composition)

    public void performFly() {
        flyBehavior.fly(); // ডেলিগেশন (Delegation)
    }
    
    // ডায়নামিক্যালি বিহেভিয়র সেট করার জন্য মেথড
    public void setFlyBehavior(FlyBehavior fb) {
        this.flyBehavior = fb;
    }
}

// ৫. আসল হাঁস (Implementation)
class MallardDuck extends Duck {
    public MallardDuck() {
        flyBehavior = new FlyWithWings(); // জন্মগতভাবে উড়তে পারে
    }
}
```

### ৮. ডায়নামিক বিহেভিয়র (Setting Behavior Dynamically)

স্ট্র্যাটেজি প্যাটার্নের সবচেয়ে বড় মজা হলো **Run-time** এ আচরণ পরিবর্তন করা।

**Scenario:**
ধরুন আপনার গেমে একটা হাঁস উড়তে পারত না। কিন্তু সে একটা "রকেট বুস্টার" পাওয়ার আপ (Power-up) খেল। এখন সে রকেটের গতিতে উড়বে!

**Code:**
```java
Duck modelDuck = new ModelDuck(); // শুরুতে উড়তে পারে না
modelDuck.performFly(); // আউটপুট: আমি উড়তে পারি না ভাই!

// গেমের মাঝখানে রকেট লাগিয়ে দিলাম
modelDuck.setFlyBehavior(new FlyRocketPowered()); 
modelDuck.performFly(); // আউটপুট: আমি রকেটের গতিতে উড়ছি! 🚀
```

**কেন এটা গুরুত্বপূর্ণ?**
ইনহেরিটেন্স দিয়ে এটা করা অসম্ভব। কারণ একবার কোড কম্পাইল হলে আপনি হাঁসের ওড়ার কোড পাল্টাতে পারতেন না। কিন্তু কম্পোজিশন ও সেটার (Setter) মেথড দিয়ে গেম চলাকালীন সময়েই হাঁসের চরিত্র বদলে দেওয়া যাচ্ছে।

### ৯. সারাংশ (Summary & Key Takeaways)

চ্যাপ্টার ১ থেকে আমরা যা শিখলাম:

1.  **OOP Basics জানাই যথেষ্ট নয়:** শুধু Abstraction, Encapsulation বা Polymorphism জানলেই ভালো ডিজাইনার হওয়া যায় না।
2.  **Encapsulate what varies:** কোডের যে অংশ ভবিষ্যতে চেঞ্জ হতে পারে, তাকে আলাদা করে ফেলুন।
3.  **Program to an interface:** কনক্রিট ক্লাসের ওপর নির্ভর না করে ইন্টারফেসের ওপর নির্ভর করুন। এতে কোড ফ্লেক্সিবল হয়।
4.  **Favor Composition over Inheritance:** ক্লাসের ক্ষমতা বাড়াতে ইনহেরিটেন্সের চেয়ে কম্পোজিশন (অন্য ক্লাসের অবজেক্ট ব্যবহার করা) অনেক বেশি শক্তিশালী।
5.  **Strategy Pattern:** এটি এমন একটি প্যাটার্ন যা আপনাকে অ্যালগরিদম পরিবর্তন করতে দেয় ক্লায়েন্ট কোড পরিবর্তন না করেই।

**বাস্তব জীবনে ব্যবহার:**
*   গেম ডেভেলপমেন্টে (যেমন চরিত্রের অস্ত্র পরিবর্তন করা - তলোয়ার থেকে বন্দুক)।
*   পেমেন্ট সিস্টেমে (বিকাশ, নগদ, বা কার্ড - ইউজার রানটাইমে পেমেন্ট মেথড সিলেক্ট করে)।
*   ডাটা সেভিং (পিডিএফ, টেক্সট বা জেপিজি ফরম্যাটে সেভ করা)।

আশা করি স্ট্র্যাটেজি প্যাটার্ন এবং হাঁসের এই গল্প আপনার কাছে পরিষ্কার হয়েছে! হ্যাপি কোডিং! 🦆🚀

### 🦆 আসল ঘটনা (The Scenario)

ধরুন, আপনি একটা কোম্পানি **SimUDuck**-এ কাজ করেন। তারা একটা হাঁসের গেম বানাচ্ছে। শুরুতে কোড ছিল খুব সিম্পল। একটা `Duck` সুপারক্লাস ছিল, আর বাকিরা সেটাকে ইনহেরিট করত।

হঠাৎ বস এসে বলল, **"গেমটা বোরিং হয়ে গেছে। হাঁসগুলোকে ওড়াতে হবে (Fly)!"**

আপনি ভাবলেন, "এ আর এমন কি! `Duck` ক্লাসে একটা `Fly()` মেথড লিখে দিলেই তো সব হাঁস উড়বে।" আপনি কোড লিখে বাসায় গিয়ে ঘুমালেন।

পরদিন অফিসে এসে দেখলেন হুলুস্থুল কাণ্ড! 😱 গেমের মধ্যে **Rubber Duck (প্লাস্টিকের হাঁস)** এবং **Decoy Duck (কাঠের হাঁস)**-ও আকাশে উড়ছে! 

**সমস্যাটা বুঝলেন?** ইনহেরিটেন্সের (Inheritance) অপব্যবহার। আপনি প্যারেন্ট ক্লাসে ওড়ার ক্ষমতা দিয়েছেন, তাই প্লাস্টিকের হাঁসও (যেটা ওড়ার কথা না) সেটা পেয়ে গেছে।

### 💡 সমাধান: Strategy Pattern (স্ট্র্যাটেজি প্যাটার্ন)

এখন আমরা **Strategy Pattern** ব্যবহার করব। সহজ বাংলায় এর মানে হলো:
> "যে জিনিসটা বারবার পরিবর্তন হয় (যেমন: ওড়া বা ডাকা), সেটাকে মূল ক্লাস থেকে বের করে আলাদা ক্লাসে নিয়ে যাও এবং দরকার মতো সেটা ব্যবহার করো।"

এতে আপনার `Duck` ক্লাস হবে ক্লিন, আর প্লাস্টিকের হাঁস আর উড়বে না!

### 💻 .NET (C#) কোড ইমপ্লিমেন্টেশন

চলুন কোড করে দেখি। আমরা হাঁসের ওড়া (Fly) এবং ডাকা (Quack) বিহেভিয়ার আলাদা করে ফেলব।

#### ১. ইন্টারফেস তৈরি (The Interfaces)
প্রথমে আমরা ডিফাইন করব—ওড়া এবং ডাকা আসলে কী।

```csharp
// ওড়ার জন্য ইন্টারফেস
public interface IFlyBehavior
{
    void Fly();
}

// ডাকার জন্য ইন্টারফেস
public interface IQuackBehavior
{
    void Quack();
}
```

#### ২. কনক্রিট বিহেভিয়র (Concrete Behaviors)
এখন আমরা ঠিক করব কে কীভাবে উড়বে বা ডাকবে।

```csharp
// যারা সত্যি উড়তে পারে
public class FlyWithWings : IFlyBehavior
{
    public void Fly()
    {
        Console.WriteLine("আমি আকাশে ডানা মেলে উড়ছি! 🦅");
    }
}

// যারা উড়তে পারে না (যেমন: প্লাস্টিকের হাঁস)
public class FlyNoWay : IFlyBehavior
{
    public void Fly()
    {
        Console.WriteLine("আমি উড়তে পারি না ভাই, মাফ করো। ❌");
    }
}

// যারা সত্যি ডাকতে পারে
public class QuackLoud : IQuackBehavior
{
    public void Quack()
    {
        Console.WriteLine("প্যাক! প্যাক! 🦆");
    }
}

// যারা শব্দ করে না (Mute)
public class MuteQuack : IQuackBehavior
{
    public void Quack()
    {
        Console.WriteLine("<< নিস্তব্ধতা >> 🤫");
    }
}
```

#### ৩. ডাক ক্লাস (The Context / Client)
এবার আমাদের মূল `Duck` ক্লাস। খেয়াল করুন, এখানে আমরা সরাসরি কোড না লিখে ইন্টারফেসের রেফারেন্স রাখছি।

```csharp
public abstract class Duck
{
    // Composition: হাঁসের নিজস্ব বিহেভিয়র ভেরিয়েবল হিসেবে আছে
    protected IFlyBehavior _flyBehavior;
    protected IQuackBehavior _quackBehavior;

    public Duck() { }

    public abstract void Display();

    public void PerformFly()
    {
        // ডেলিগেশন: হাঁস নিজে উড়ছে না, সে _flyBehavior কে বলছে উড়তে
        _flyBehavior.Fly();
    }

    public void PerformQuack()
    {
        _quackBehavior.Quack();
    }

    public void Swim()
    {
        Console.WriteLine("সব হাঁস ভাসে, এমনকি কাঠের হাঁসও!");
    }

    // রানটাইমে ক্ষমতা পরিবর্তনের জাদুকরী মেথড (Setter Injection)
    public void SetFlyBehavior(IFlyBehavior fb)
    {
        _flyBehavior = fb;
    }
}
```

#### ৪. হাঁসের প্রকারভেদ (Concrete Ducks)

```csharp
// আসল হাঁস
public class MallardDuck : Duck
{
    public MallardDuck()
    {
        // কনস্ট্রাক্টরে বলে দিচ্ছি এর স্বভাব কেমন হবে
        _flyBehavior = new FlyWithWings();
        _quackBehavior = new QuackLoud();
    }

    public override void Display()
    {
        Console.WriteLine("আমি দেখতে আসল ম্যালার্ড হাঁসের মতো।");
    }
}

// খেলনা হাঁস (Model Duck)
public class ModelDuck : Duck
{
    public ModelDuck()
    {
        _flyBehavior = new FlyNoWay(); // জন্মগতভাবে উড়তে পারে না
        _quackBehavior = new QuackLoud();
    }

    public override void Display()
    {
        Console.WriteLine("আমি একটা মডেল ডাক (খেলনা)।");
    }
}
```

#### ৫. রকেট পাওয়ার! (Adding New Behavior)
হঠাৎ গেমে একটা রকেট পাওয়ার আসল। আমরা কি কোড ভাঙব? না! নতুন একটা ক্লাস বানাব।

```csharp
public class FlyRocketPowered : IFlyBehavior
{
    public void Fly()
    {
        Console.WriteLine("রকেটের গতিতে উড়ছিইইইই! 🚀");
    }
}
```

#### ৬. মেইন মেথড (Testing it all)

```csharp
class Program
{
    static void Main(string[] args)
    {
        // ১. সাধারণ হাঁস
        Duck mallard = new MallardDuck();
        mallard.Display();
        mallard.PerformQuack();
        mallard.PerformFly();

        Console.WriteLine("------------------");

        // ২. খেলনা হাঁস এবং ডায়নামিক চেঞ্জ
        Duck model = new ModelDuck();
        model.Display();
        model.PerformFly(); // আউটপুট: উড়তে পারি না

        // খেলা চলাকালীন সময়েই আমরা তাকে রকেট লাগিয়ে দিলাম!
        Console.WriteLine(">> খেলনা হাঁসে রকেট লাগানো হচ্ছে...");
        model.SetFlyBehavior(new FlyRocketPowered());
        
        model.PerformFly(); // আউটপুট: রকেটের গতিতে উড়ছি!
    }
}
```

### 🤔 লজিক এবং গুরুত্ব (Logic & Why it Works)

১. **Composition over Inheritance:** আমরা হাঁসকে `FlyWithWings` ইনহেরিট করাইনি। বরং হাঁসের পেটের ভেতর (Variable হিসেবে) `IFlyBehavior` রেখেছি। একে বলে **Composition**। এর ফলে হাঁস এবং ওড়ার ক্ষমতা দুটো আলাদা জিনিস হিসেবে থাকে।
2.  **Program to Interface:** `Duck` ক্লাসে আমরা `FlyWithWings` বা `FlyNoWay` টাইপ ব্যবহার করিনি। আমরা ব্যবহার করেছি `IFlyBehavior`। এর মানে হলো, ভবিষ্যতে যদি সুপারম্যানের মতো ওড়ার স্টাইল আসে, আমাদের `Duck` ক্লাসের কোড এক ফোঁটাও বদলাতে হবে না।

### ⚠️ সাধারণ সমস্যা ও সমাধান (Common Problems)

*   **সমস্যা:** ক্লাস এক্সপ্লোশন (Class Explosion)।
    *   **কারণ:** প্রতিটা আলাদা আচরণের জন্য আলাদা ক্লাস বানাতে হচ্ছে। ছোট প্রজেক্টে এটা বিরক্তিকর মনে হতে পারে।
    *   **সমাধান:** যদি প্রজেক্ট ছোট হয় এবং ভবিষ্যতে বড় হওয়ার সম্ভাবনা না থাকে, তবে সাধারণ ইনহেরিটেন্স ব্যবহার করাই ভালো। প্যাটার্ন হলো জটিল সমস্যার সমাধান, সহজ কাজের জন্য প্যাটার্ন ব্যবহার করা হলো মশা মারতে কামান দাগার মতো।

*   **সমস্যা:** সব লজিক ছড়িয়ে ছিটিয়ে থাকা।
    *   **সমাধান:** ফোল্ডার স্ট্রাকচার সুন্দর রাখুন। `Behaviors` ফোল্ডারে সব ইন্টারফেস এবং ইমপ্লিমেন্টেশন রাখুন।

### 🌍 বাস্তব জীবনের উদাহরণ (Real-World Scenario: Payment System)

হাঁস বাদ দেন, চলুন ই-কমার্সে যাই। বাংলাদেশে পেমেন্ট সিস্টেম কেমন হতে পারে?

*   **Context:** `PaymentProcessor` ক্লাস।
*   **Strategy Interface:** `IPaymentStrategy` (মেথড: `Pay(amount)`).
*   **Concrete Strategies:**
    *   `BkashPayment` (বিকাশ এপিআই কল করে)
    *   `NagadPayment` (নগদ এপিআই কল করে)
    *   `CreditCardPayment` (ব্যাংক গেটওয়ে কল করে)

**ব্যবহার:** ইউজার যখন চেকআউট পেজে "বিকাশ" সিলেক্ট করবে, তখন রানটাইমে আমরা `PaymentProcessor`-এ `BkashPayment` অবজেক্ট সেট করে দেব। কোডের বাকি অংশের জানার দরকারই নেই পেমেন্ট কীভাবে হচ্ছে, সে শুধু জানে `Pay()` করলেই টাকা কেটে নেবে।

### 📝 একনজরে সারাংশ (Summary)

এই চ্যাপ্টার থেকে আমরা ৩টি গোল্ডেন রুল শিখলাম:

১. **Encapsulate what varies:** অ্যাপের যে অংশটা পরিবর্তনশীল (যেমন ওড়ার স্টাইল), সেটাকে আলাদা করো।
২. **Program to an interface, not an implementation:** ভেরিয়েবলের টাইপ সবসময় ইন্টারফেস বা অ্যাবস্ট্রাক্ট ক্লাস রাখো, কনক্রিট ক্লাস না।
৩. **Favor Composition over Inheritance:** ইনহেরিটেন্সের চেয়ে কম্পোজিশন (Has-A relationship) কোডকে বেশি ফ্লেক্সিবল করে।

**Strategy Pattern**-এর মূল মন্ত্রই হলো: অ্যালগরিদমগুলোর একটা ফ্যামিলি বানাও, সেগুলোকে আলাদা ক্লাসে বন্দি করো এবং রানটাইমে একটার বদলে আরেকটা ব্যবহার করার সুযোগ দাও।
