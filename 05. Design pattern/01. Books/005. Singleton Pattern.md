
হ্যালো ফিউচার সফটওয়্যার আর্কিটেক্টস! 🏛️ **Head First Design Patterns**-এর **পঞ্চম অধ্যায়ে (Chapter 5)** আপনাদের স্বাগতম।

আজকের টপিকটা একটু অন্যরকম। আগের চ্যাপ্টারগুলোতে আমরা শিখেছি কিভাবে অনেক ফ্লেক্সিবল অবজেক্ট বানাতে হয়। কিন্তু আজ আমরা শিখব— **"কিভাবে নিশ্চিত করা যায় যে পুরো দুনিয়ায় একটা ক্লাসের মাত্র একটাই অবজেক্ট (Instance) থাকবে!"** ☝️

এই চ্যাপ্টারের নাম: **The Singleton Pattern (One-of-a-Kind Objects)**।
সহজ বাংলায়: **"এক বনে দুই বাঘ থাকে না, তেমনি আমার অ্যাপেও এই অবজেক্ট দুইটা হবে না!"** 🐅

---

### ১. সমস্যা: কেন আমাদের মাত্র ১টি অবজেক্ট দরকার? (Why Single Instance?) 🤔

ধরুন, আপনি একটি চকলেট তৈরির ফ্যাক্টরি চালাচ্ছেন (বইয়ের উদাহরণ: **Choc-O-Holic**)। সেখানে একটা বড় বয়লার (Boiler) আছে যেখানে দুধ আর চকলেট মিক্স করে গরম করা হয়।

এখন যদি ভুল করে কোডের কারণে **দুইটা** বয়লার অবজেক্ট তৈরি হয়ে যায় এবং দুইটা আলাদা আলাদা নির্দেশ পায় (একটা বলছে "গরম করো", আরেকটা বলছে "খালি করো"), তাহলে কি হবে?
ফ্যাক্টরি ভেসে যাবে চকলেটের বন্যায়! 🍫🌊

কিছু কিছু জিনিস সিস্টেমে এক পিস থাকাই ভালো। যেমন:
*   **Registry Settings:** উইন্ডোজের রেজিস্ট্রি সেটিংস একটাই থাকে।
*   **Logger:** লগ ফাইলে লেখার জন্য ১০টা অবজেক্ট থাকলে ফাইল করাপ্ট হতে পারে।
*   **Printer Spooler:** প্রিন্টারে কমান্ড পাঠানোর ম্যানেজার একটাই হওয়া উচিত।

**চ্যালেঞ্জ:** কিভাবে নিশ্চিত করব যে `new MyClass()` কল করলেও দ্বিতীয় কোনো অবজেক্ট তৈরি হবে না?

---

### ২. সাধারণ কোডিং বনাম সিঙ্গেলটন (The Transformation) 🛠️

সাধারণত আমরা অবজেক্ট বানাই এভাবে:
```java
MyClass obj = new MyClass(); // পাবলিক কনস্ট্রাক্টর
```
কিন্তু সিঙ্গেলটনে আমরা **কনস্ট্রাক্টরকে প্রাইভেট (Private)** করে ফেলি। মানে বাইরের কেউ `new` কি-ওয়ার্ড দিয়ে অবজেক্ট বানাতেই পারবে না!

তা হলে অবজেক্ট পাবো কিভাবে? 🤔
ক্লাসের ভেতরে একটা **চোরকুঠুরি (Static Method)** রাখব, যেটা দিয়ে অবজেক্ট বের করা যাবে।

---

### ৩. ক্লাসিক সিঙ্গেলটন ইমপ্লিমেন্টেশন (Lazy Initialization)

এখানে আমরা **"Lazy"** অ্যাপ্রোচ নিব। মানে, "যতক্ষণ না কেউ অবজেক্ট চাইছে, ততক্ষণ বানাবো না।"

```java
public class Singleton {
    // ১. একটা স্ট্যাটিক ভেরিয়েবল যা একমাত্র অবজেক্টকে ধরে রাখবে
    private static Singleton uniqueInstance;

    // ২. প্রাইভেট কনস্ট্রাক্টর (বাইরে থেকে কেউ কল করতে পারবে না)
    private Singleton() {}

    // ৩. গ্লোবাল এক্সেস পয়েন্ট
    public static Singleton getInstance() {
        // যদি অবজেক্ট না থাকে, তবেই নতুন বানাও
        if (uniqueInstance == null) {
            uniqueInstance = new Singleton();
        }
        // আর থাকলে পুরানোটাই ফেরত দাও
        return uniqueInstance;
    }
}
```

**কেন এটা কাজ করে?**
কারণ `uniqueInstance` স্ট্যাটিক, তাই এটি মেমোরিতে একবারই থাকে। প্রথমবার `null` থাকে, তাই অবজেক্ট তৈরি হয়। পরেরবার কল করলে আগের তৈরি করা অবজেক্টটাই রিটার্ন করে।

---

### ৪. সমস্যা: মাল্টিথ্রেডিং-এর ভুত (The Multithreading Nightmare) 👻

সবই ভালো চলছিল, কিন্তু হঠাৎ **Multithreading** এসে সব তছনছ করে দিল।

ধরুন, **থ্রেড A** এবং **থ্রেড B** একই সময়ে `getInstance()` মেথডে ঢুকল।
1. **থ্রেড A** দেখল `uniqueInstance` নাল (খালি)। সে অবজেক্ট বানানোর প্রস্তুতি নিল।
2. ঠিক সেই মুহূর্তেই **থ্রেড B** ঢুকল এবং সেও দেখল `uniqueInstance` নাল (কারণ A এখনো বানিয়ে শেষ করেনি)।
3. ফলাফল: **দুইটা আলাদা অবজেক্ট তৈরি হয়ে গেল!** 😱

আমাদের "এক বনে এক বাঘ" থিওরি ফেইল! চকলেট ফ্যাক্টরিতে বন্যা!

---

### ৫. সমাধানসমূহ (Solutions to Multithreading) 🛡️

বইটিতে এই সমস্যা সমাধানের ৩টি উপায় বলা হয়েছে:

#### সমাধান ১: Synchronized Method (সবচেয়ে সহজ কিন্তু ধীরগতি) 🐢
আমরা `getInstance` মেথডকে `synchronized` করে দিব। মানে একবারে একজনই ঢুকতে পারবে।

```java
public static synchronized Singleton getInstance() {
    if (uniqueInstance == null) {
        uniqueInstance = new Singleton();
    }
    return uniqueInstance;
}
```
*   **সমস্যা:** এটা কোডকে ১০০ গুণ স্লো করে দিতে পারে! প্রতিবার অবজেক্ট চাইতে গেলেই লাইনে দাঁড়াতে হবে, যেটা পারফরম্যান্সের জন্য খারাপ।

#### সমাধান ২: Eager Instantiation (তড়িঘড়ি পদ্ধতি) 🏃‍♂️
আমরা অলসতা (Lazy) বাদ দিয়ে ক্লাস লোড হওয়ার শুরুতেই অবজেক্ট বানিয়ে রাখব।

```java
public class Singleton {
    // আগেই বানিয়ে রাখলাম
    private static Singleton uniqueInstance = new Singleton();

    private Singleton() {}

    public static Singleton getInstance() {
        return uniqueInstance; // রেডিমেড মাল, নিয়ে যাও
        // কোনো if-else চেক নেই, তাই থ্রেডিং সমস্যা নেই
    }
}
```
*   **সমস্যা:** যদি এই অবজেক্টটা মেমোরিতে অনেক জায়গা খায় এবং কেউ এটা ব্যবহার না করে, তবে অকারণে মেমোরি নষ্ট হবে।

#### সমাধান ৩: Double-Checked Locking (স্মার্ট পদ্ধতি) 🧠
আমরা শুধু **প্রথমবার** সিঙ্ক্রোনাইজ করব, পরেরবার আর চেক করব না।

```java
public class Singleton {
    // volatile কি-ওয়ার্ড নিশ্চিত করে যে সব থ্রেড লেটেস্ট ভ্যালু দেখছে
    private volatile static Singleton uniqueInstance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (uniqueInstance == null) { // প্রথম চেক
            synchronized (Singleton.class) {
                if (uniqueInstance == null) { // দ্বিতীয় চেক (লক করার পর)
                    uniqueInstance = new Singleton();
                }
            }
        }
        return uniqueInstance;
    }
}
```
*   **সুবিধা:** এটা পারফরম্যান্স ঠিক রাখে এবং থ্রেড সেফ। তবে কোডটা একটু জটিল।

---

### ৬. বোনাস: Enum দিয়ে সিঙ্গেলটন (The Best Way) 🏆

বইয়ের শেষের দিকে বলা হয়েছে, জাভাতে সিঙ্গেলটন বানানোর সবচেয়ে সহজ এবং নিরাপদ উপায় হলো **Enum** ব্যবহার করা।

```java
public enum Singleton {
    UNIQUE_INSTANCE;
    
    // আপনার মেথড
    public void doSomething() {
        System.out.println("I am doing something!");
    }
}
```
*   **কেন সেরা?** এটা অটোমেটিক্যালি থ্রেড সেফ, সিরিয়ালাইজেশন (Serialization) সমস্যা হ্যান্ডেল করে এবং কোড খুবই কম।

---

### ৭. বাস্তব জীবনের উদাহরণ (Bangla Analogy) 🏠

ধরুন, আপনার বাসার **"মেইন সুইচ" (Main Switch)**।
বাসায় ১০ জন সদস্য (10 Threads) থাকতে পারে। সবাই লাইট জ্বালাতে বা ফ্যান চালাতে পারে। কিন্তু মেইন সুইচ একটাই। যদি বাসায় দুইটা মেইন সুইচ থাকে এবং দুইটা দুই রকম নির্দেশ দেয়, তবে শর্ট সার্কিট হয়ে আগুন ধরে যাবে।

সিঙ্গেলটন প্যাটার্ন নিশ্চিত করে যে, পুরো বাসায় একটাই মেইন সুইচ থাকবে এবং সবাই সেটাকেই এক্সেস করবে।

---

### ৮. একনজরে সারাংশ (Summary of Key Points) 📝

1.  **Singleton Pattern:** নিশ্চিত করে একটি ক্লাসের একটিই ইনস্ট্যান্স বা অবজেক্ট থাকবে এবং গ্লোবাল এক্সেস পয়েন্ট প্রদান করে।
2.  **Private Constructor:** সিঙ্গেলটনের কনস্ট্রাক্টর সবসময় `private` হয় যাতে বাইরে থেকে `new` করা না যায়।
3.  **Lazy vs Eager:**
    *   **Lazy:** যখন দরকার তখন বানাব (মেমোরি বাঁচে, কিন্তু থ্রেডিং রিস্ক থাকে)।
    *   **Eager:** শুরুতেই বানিয়ে রাখব (থ্রেড সেফ, কিন্তু মেমোরি নষ্ট হতে পারে)।
4.  **Double-Checked Locking:** মাল্টিথ্রেডিং সমস্যা সমাধানের জন্য `volatile` এবং `synchronized` ব্লক ব্যবহার করা।
5.  **Enum:** জাভাতে সিঙ্গেলটন বানানোর সবচেয়ে আধুনিক ও নিরাপদ উপায়।

ব্যাস! এখন আপনি জানেন কিভাবে চকলেট ফ্যাক্টরিকে বন্যার হাত থেকে বাঁচাতে হয়। 🍫 সিঙ্গেলটন প্যাটার্ন সাবধানে ব্যবহার করবেন, কারণ বেশি ব্যবহার করলে কোড টেস্টিং কঠিন হয়ে যায়! হ্যাপি কোডিং! 😎👨‍💻

আজকের টপিকটা হলো **"এক বনে দুই বাঘ না থাকার গল্প"**। মানে, আমরা এমন একটা ক্লাস বানাবো, যার **মাত্র একটাই অবজেক্ট (Instance)** পুরো দুনিয়াতে থাকবে। আপনি চাইলেও দ্বিতীয়টা বানাতে পারবেন না।

### 🍫 আসল ঘটনা (The Scenario): চকলেট ফ্যাক্টরি

বইয়ের বিখ্যাত উদাহরণটা দেই। ধরুন, আপনার একটা **চকলেট বয়লার (Chocolate Boiler)** আছে। এটাতে দুধ আর চকলেট মিক্স করে গরম করা হয়।

এখন, এই বয়লার কন্ট্রোল করার জন্য একটা ক্লাস আছে `ChocolateBoiler`।
**সমস্যা:** যদি ভুল করে কোডের কারণে **দুইটা** বয়লার অবজেক্ট তৈরি হয়ে যায়, তাহলে কি হবে?
*   অবজেক্ট ১ বলবে: "বয়লার খালি, দুধ ঢাল!"
*   অবজেক্ট ২ বলবে: "আরে বয়লার তো ভরা, আগুন জ্বala!"

ফলাফল? **বুম!** 💥 অথবা ফ্যাক্টরি ভেসে যাবে চকলেটের বন্যায়। তাই আমাদের নিশ্চিত করতে হবে যেন `ChocolateBoiler` ক্লাসের **একটাই** অবজেক্ট থাকে।

### 💻 .NET (C#) কোড: দ্য নাইভ (Naive) সিঙ্গেলটন

প্রথমে দেখি সাধারণ ভুলটা মানুষ কোথায় করে এবং কিভাবে আটকানো যায়।

#### ১. কনস্ট্রাক্টর প্রাইভেট করা (সবচেয়ে জরুরি ধাপ)
সাধারণত আমরা `new ClassName()` দিয়ে অবজেক্ট বানাই। কিন্তু কনস্ট্রাক্টর যদি **Private** করে দেই, তাহলে বাইরের কেউ আর `new` ডাকতে পারবে না। তখন অবজেক্ট বানানোর দায়িত্ব ক্লাসের নিজের কাঁধেই নিতে হবে।

```csharp
public class ChocolateBoiler
{
    // ১. একটা স্ট্যাটিক ভেরিয়েবল, যেটা একমাত্র অবজেক্টকে ধরে রাখবে
    private static ChocolateBoiler _uniqueInstance;

    // ২. প্রাইভেট কনস্ট্রাক্টর! (বাইরের কেউ আর new ChocolateBoiler() ডাকতে পারবে না)
    private ChocolateBoiler() 
    {
        Console.WriteLine("চকলেট বয়লার তৈরি হচ্ছে... (একবারই দেখার কথা)");
    }

    // ৩. গ্লোবাল এক্সেস পয়েন্ট (দরজা)
    public static ChocolateBoiler GetInstance()
    {
        // যদি অবজেক্ট না থাকে, তবেই বানাও (Lazy Initialization)
        if (_uniqueInstance == null)
        {
            _uniqueInstance = new ChocolateBoiler();
        }
        // আর থাকলে পুরানোটাই ফেরত দাও
        return _uniqueInstance;
    }

    public void Fill()
    {
        Console.WriteLine("বয়লারে দুধ আর চকলেট ভরা হচ্ছে...");
    }
}
```

**ব্যবহার:**
```csharp
class Program
{
    static void Main(string[] args)
    {
        // ChocolateBoiler boiler = new ChocolateBoiler(); // ❌ এটা কাজ করবে না! লাল বাতি জ্বলবে।
        
        ChocolateBoiler boiler1 = ChocolateBoiler.GetInstance();
        ChocolateBoiler boiler2 = ChocolateBoiler.GetInstance();

        // প্রমাণ যে দুইটা একই অবজেক্ট
        if (boiler1 == boiler2)
        {
            Console.WriteLine("সাবাস! দুইটা ভেরিয়েবল একই বয়লারকে পয়েন্ট করছে।");
        }
    }
}
```

### ⚠️ সমস্যা: মাল্টিথ্রেডিং-এর গণ্ডগোল (The Threading Nightmare)

উপরের কোডটা ততক্ষণই ভালো, যতক্ষণ আপনার অ্যাপে **একটাই থ্রেড (Single Thread)** চলছে। কিন্তু মাল্টিথ্রেডিং এনভায়রনমেন্টে (যেমন ওয়েব সার্ভারে) একটা ভয়ংকর ঘটনা ঘটতে পারে।

**ঘটনা:**
১. **থ্রেড A** চেক করল `_uniqueInstance == null`। সে বলল, "আচ্ছা, আমি বানাতে যাচ্ছি।"
২. ঠিক সেই মুহূর্তে **থ্রেড B** আসল। সেও দেখল `_uniqueInstance` এখনো নাল (কারণ A এখনো বানানো শেষ করেনি)। সেও বলল, "আমিও বানাব!"
৩. ফলাফল: **দুইটা আলাদা বয়লার তৈরি হয়ে গেল!** 😱 সিঙ্গেলটনের বারোটা বেজে গেল।

### 🛡️ সমাধান: থ্রেড সেফ সিঙ্গেলটন (Thread Safety)

C# এ এই সমস্যা সমাধানের বস উপায় হলো `lock` ব্যবহার করা অথবা .NET এর বিল্ট-ইন `Lazy<T>` ব্যবহার করা।

#### উপায় ১: লক ব্যবহার করা (Double-Checked Locking)
আমরা একটা তালা মেরে দিব, যাতে একবারে একজনই অবজেক্ট বানাতে ঢুকতে পারে।

```csharp
public class ThreadSafeBoiler
{
    private static ThreadSafeBoiler _uniqueInstance;
    
    // লক করার জন্য একটা ডামি অবজেক্ট
    private static readonly object _lock = new object();

    private ThreadSafeBoiler() { }

    public static ThreadSafeBoiler GetInstance()
    {
        // ডাবল চেক লকিং (Double-Checked Locking)
        if (_uniqueInstance == null)
        {
            lock (_lock) // তালা মারলাম!
            {
                if (_uniqueInstance == null) // আবার চেক করলাম (শিওর হওয়ার জন্য)
                {
                    _uniqueInstance = new ThreadSafeBoiler();
                }
            }
        }
        return _uniqueInstance;
    }
}
```

#### উপায় ২: দ্য মডার্ন C# ওয়ে `(Lazy<T>) - **Recommended** ⭐
C# ডেভেলপাররা এতো কোড লিখতে পছন্দ করে না। তাই .NET আমাদের জন্য `Lazy<T>` ক্লাস দিয়ে রেখেছে। এটা অটোমেটিক্যালি থ্রেড সেফ এবং লেজি লোডিং নিশ্চিত করে।

```csharp
public sealed class ModernBoiler // sealed দেওয়া ভালো, যাতে কেউ ইনহেরিট না করে
{
    // Lazy<T> নিজেই থ্রেড সেফটি হ্যান্ডেল করে, আমাদের টেনশন নাই
    private static readonly Lazy<ModernBoiler> _lazy = 
        new Lazy<ModernBoiler>(() => new ModernBoiler());

    public static ModernBoiler Instance { get { return _lazy.Value; } }

    private ModernBoiler()
    {
        Console.WriteLine("মডার্ন বয়লার রেডি!");
    }
    
    public void Boil()
    {
        Console.WriteLine("টগবগ করে ফুটছে!");
    }
}
```

### 🌍 বাস্তব জীবনের উদাহরণ (Real-World Scenario): Logger

ভাবুন আপনি একটা অ্যাপ বানিয়েছেন যেখানে সব এরর (Error) একটা টেক্সট ফাইলে সেভ হয় (**Logging**)।
এখন যদি ১০টা থ্রেড ১০টা আলাদা লগার অবজেক্ট বানিয়ে একই ফাইলে একসাথে লেখার চেষ্টা করে, তাহলে ফাইল করাপ্ট হয়ে যাবে বা উইন্ডোজ এরর দিবে ("File is being used by another process")।

এখানে **Singleton** বাঞ্ছনীয়। একজনই লগার থাকবে, সবাই তাকেই কল দিবে।

```csharp
public sealed class Logger
{
    private static readonly Lazy<Logger> _lazy = new Lazy<Logger>(() => new Logger());
    public static Logger Instance { get { return _lazy.Value; } }

    private Logger() { }

    public void Log(string message)
    {
        // বাস্তবে এখানে ফাইল রাইটিং কোড থাকবে
        Console.WriteLine($"[LOG]: {DateTime.Now} - {message}");
    }
}

// ব্যবহার:
// অ্যাপের যেকোনো জায়গা থেকে আপনি এটা কল করতে পারবেন
Logger.Instance.Log("System crashed! (Just kidding)");
Logger.Instance.Log("User logged in.");
```

### 📝 একনজরে সারাংশ (Summary)

১. **Singleton Pattern:** নিশ্চিত করে যে একটি ক্লাসের **মাত্র একটিই অবজেক্ট** তৈরি হবে এবং গ্লোবাললি সেটা এক্সেস করা যাবে।
২. **Private Constructor:** সিঙ্গেলটনের প্রাণভোমরা। এটা ছাড়া বাইরে থেকে অবজেক্ট বানানো আটকানো যাবে না।
৩. **Thread Safety:** মাল্টিথ্রেডিং অ্যাপে সাধারণ সিঙ্গেলটন কাজ করে না। C#-এ `lock` অথবা `Lazy<T>` ব্যবহার করে এটা সমাধান করতে হয়।
৪. **ব্যবহার:** ডাটাবেস কানেকশন পুল, লগিং সিস্টেম, কনফিগারেশন সেটিংস—যেখানে রিসোর্স শেয়ার করা জরুরি এবং একটাই কপি থাকা দরকার।
