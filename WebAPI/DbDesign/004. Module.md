### 🎓 Lesson 31: Views - ভার্চুয়াল টেবিল

**সহজ বাংলা ব্যাখ্যা:**
View (ভিউ) হলো আসলে একটা **সংরক্ষিত কুয়েরি (Saved Query)**।
এটি দেখতে হুবহু টেবিলের মতো, এর রো এবং কলাম আছে, তুমি একে `SELECT` করতে পারো। কিন্তু মজার ব্যাপার হলো—এর নিজের কোনো ডেটা বা শরীর নেই! এটি আসল টেবিল থেকে ডেটা ধার করে এনে তোমাকে দেখায়।

**🤣 Funny Real-life Analogy:**
**মিউজিক প্লেলিস্ট (Playlist)!** 🎵
- তোমার মোবাইলের মেমোরি কার্ডে ১০০০ গান আছে (**Real Table**)।
- তুমি "Best of Arijit Singh" নামে একটা প্লেলিস্ট বানালে (**View**)।
- প্লেলিস্টে কি গানগুলো নতুন করে কপি বা ডাউনলোড হয়? না!
- প্লেলিস্ট শুধু মেমোরি কার্ডের গানগুলোকে পয়েন্ট করে রাখে।
- যদি মেমোরি কার্ড থেকে গান ডিলিট করো, প্লেলিস্ট থেকেও গান গায়েব হয়ে যাবে। ভিউ ঠিক এভাবেই কাজ করে।

**আরেকটি উদাহরণ:**
তোমার জানালার **কাচ (Glass)**।
তুমি কাচের ভেতর দিয়ে বাইরের গাছপালা দেখো। গাছপালা কিন্তু তোমার ঘরে নেই, বাইরেই আছে। কাচটা হলো `VIEW`—যা তোমাকে আসল ডেটা দেখার সুযোগ দিচ্ছে।

**ASCII Example:**

**Real Table: Employee (Highly Confidential)**

| ID | Name | Salary (Secret) | Password (Secret) |
| :--- | :--- | :--- | :--- |
| 1 | Boss | 500,000 | 123456 |
| 2 | Rahim | 20,000 | abcdef |

*(এই টেবিল সবাইকে দেখানো বিপদজনক!)*

**Create View: vw_PublicEmployee**
*(আমরা স্যালারি আর পাসওয়ার্ড বাদ দিয়ে ভিউ বানাব)*

| ID | Name |
| :--- | :--- |
| 1 | Boss |
| 2 | Rahim |

*(এখন ইন্টার্নরা এই ভিউ দেখবে, আসল টেবিল দেখবে না)*

**SQL Example:**

**১. ভিউ তৈরি করা:**
```sql
CREATE VIEW vw_EmployeeBasic AS
SELECT Name, Department
FROM Employee;
-- এখানে স্যালারি কলাম রাখলাম না
```

**২. ভিউ ব্যবহার করা:**
ঠিক সাধারণ টেবিলের মতোই!
```sql
SELECT * FROM vw_EmployeeBasic;
```

**৩. জটিল জয়েনকে ভিউ বানানো:**
```sql
-- বারবার বিশাল জয়েন লেখার দরকার নেই
CREATE VIEW vw_OrderDetails AS
SELECT Customers.Name, Orders.Item, Orders.Price
FROM Customers
JOIN Orders ON Customers.CustID = Orders.CustID;

-- ব্যবহারের সময় শুধু এইটুকু লিখলেই হবে
SELECT * FROM vw_OrderDetails;
```

**When/Why to use:**
১. **Security (নিরাপত্তা):** সেনসিটিভ ডেটা (পাসওয়ার্ড, বেতন) লুকিয়ে রাখার জন্য। নির্দিষ্ট ইউজারকে শুধু নির্দিষ্ট কলাম দেখানোর জন্য।
২. **Simplicity (সরলতা):** বিশাল জটিল কোড বা জয়েন বারবার না লিখে, একবার ভিউ বানিয়ে রেখে দেওয়া।

**Best Practice:**
ভিউ-এর নামের আগে `vw_` বা `v_` ব্যবহার করবে (যেমন: `vw_Students`)। এতে দেখলেই বোঝা যায় কোনটা আসল টেবিল আর কোনটা ভিউ।

**Common Mistake (The Performance Trap):**
ভিউ-এর ওপর ভিউ, তার ওপর আবার ভিউ বানানো (**Nested Views**)।
এটা করলে ডেটাবেস পাগল হয়ে যায় আসল ডেটা খুঁজে বের করতে! কোড স্লো হয়ে যায়। চেষ্টা করবে সরাসরি টেবিল থেকে ভিউ বানাতে।

**Mini Task:**
তোমার `Students` টেবিলে `Name`, `Phone`, এবং `HomeAddress` আছে।
স্কুলের নোটিশ বোর্ডে ঝোলানোর জন্য একটা ভিউ বানাও (`vw_NoticeBoard`), যেখানে ছাত্রের `HomeAddress` দেখা যাবে না (প্রাইভেসি), শুধু নাম আর ফোন দেখা যাবে। SQL-টা খাতায় লেখো।

---

স্বাগতম **Lesson 32**-এ! 🛠️

আগের লেসনে আমরা **View** শিখেছি, যেটা ছিল অনেকটা **জানালার কাচ**—শুধু ডেটা দেখার জন্য।
কিন্তু যদি তুমি ডেটাবেসকে দিয়ে কাজ করাতে চাও (যেমন: ডেটা ঢোকানো, লজিক চেক করা, হিসাব করা), তখন তোমার দরকার **Stored Procedure (SP)**। এটা হলো ডেটাবেসের আসল **ইঞ্জিন বা জাদুর কাঠি**!

চলো শিখে ফেলি।

### 🎓 Lesson 32: Stored Procedures (SP) - কোড সেভ করে রাখা

**সহজ বাংলা ব্যাখ্যা:**
Stored Procedure (সংক্ষেপে SP) হলো অনেকগুলো SQL কুয়েরির একটা প্যাকেট বা বান্ডিল, যা সার্ভারে সেভ করা থাকে।
তুমি বারবার ১০-২০ লাইনের কোড না লিখে, সেই কোডগুলো একটা SP-র ভেতর রেখে দাও। পরে শুধু SP-র নাম ধরে ডাক দিলেই কাজ হয়ে যায়। এটি ইনপুট (Parameters) নিতে পারে এবং আউটপুট দিতে পারে।

**🤣 Funny Real-life Analogy:**
**কফি মেশিন!** ☕
তুমি যখন কফি মেশিনে কফি বানাও, তুমি কি মেশিনের ভেতরে ঢুকে পানি গরম করো, বিনস গুঁড়ো করো, দুধ মেশাও? না!
- তুমি শুধু একটা **বোতামে চাপ দাও** (SP Call)।
- মাঝে মাঝে ইনপুট দাও: "চিনি ২ চামচ" (Parameters)।
- মেশিন ভেতরে সব প্রসেস (Logic) শেষ করে তোমাকে রেডি কফি দেয়।

এই মেশিনটাই হলো `Stored Procedure`। আর ম্যানুয়ালি হাতে কফি বানানো হলো সাধারণ SQL Query।

**SQL Example:**

**১. সাধারণ কুয়েরি (বারবার লিখতে হয়):**
```sql
SELECT * FROM Customers WHERE City = 'Dhaka';
SELECT * FROM Customers WHERE City = 'Chittagong';
```

**২. Stored Procedure তৈরি করা (একবার বানাব):**
```sql
CREATE PROCEDURE usp_GetCustomersByCity
    @CityName varchar(50)  -- এটা হলো ইনপুট বা প্যারামিটার
AS
BEGIN
    -- ভেতরের লজিক
    SELECT * 
    FROM Customers 
    WHERE City = @CityName;
END;
```

**৩. ব্যবহার করা (ম্যাজিক!):**
```sql
EXEC usp_GetCustomersByCity 'Dhaka';      -- ঢাকাবাসীকে দেখাও
EXEC usp_GetCustomersByCity 'Sylhet';     -- সিলেটবাসীকে দেখাও
```

*(দেখো, কত সহজে শুধু নাম আর শহরের নাম বলেই কাজ শেষ!)*

**Why/When to use:**
1.  **Performance (গতি):** SP একবার কম্পাইল হলে সার্ভারের মেমোরিতে থেকে যায়, তাই সাধারণ কুয়েরির চেয়ে অনেক দ্রুত কাজ করে।
2.  **Security (নিরাপত্তা):** হ্যাকাররা সহজে `SQL Injection` অ্যাটাক করতে পারে না। তুমি ইউজারকে টেবিল দেখার পারমিশন না দিয়ে শুধু SP চালানোর পারমিশন দিতে পারো।
3.  **Maintenance:** যদি লজিক বদলাতে হয়, শুধু SP আপডেট করলেই হবে। হাজার হাজার লাইন কোড ঘাঁটতে হবে না।

**Best Practice:**
SP-এর নামের শুরুতে `usp_` (User Stored Procedure) ব্যবহার করা ভালো।
*টিপস:* SP-এর ভেতরে `SET NOCOUNT ON;` লিখলে পারফরম্যান্স আরও বাড়ে (কারণ এটি "5 rows affected" - এই অপ্রয়োজনীয় মেসেজটা বন্ধ করে দেয়)।

**Common Mistake:**
নামের শুরুতে `sp_` ব্যবহার করা (যেমন: `sp_GetCustomer`)।
*কেন ভুল?* কারণ SQL Server-এর নিজস্ব সিস্টেম প্রসিডিউরগুলো `sp_` দিয়ে শুরু হয়। তুমি সেইম নাম দিলে সিস্টেম কনফিউজড হয়ে একটু স্লো হয়ে যাবে। তাই সবসময় `usp_` বা অন্য কিছু ব্যবহার করবে।

**Mini Task:**
তোমার `Employee` টেবিলে নতুন কর্মী নিয়োগ দেওয়ার জন্য একটা SP বানাও (`usp_AddEmployee`)।
এটি ইনপুট হিসেবে `Name` আর `Salary` নেবে এবং `INSERT` কুয়েরি চালাবে।

কোডটা অনেকটা এমন হবে:
`CREATE PROCEDURE... @Name... @Salary... AS... INSERT INTO...`
(চেষ্টা করো খাতায় লিখতে!)

আমরা আগের লেসনে **Stored Procedure (SP)** শিখেছি, যেটা ছিল "কফি মেশিন"—বোতাম চাপলে কাজ করে।
এখন শিখব **User Defined Function (UDF)**। অনেকে SP আর Function-এর মধ্যে গুলিয়ে ফেলে। সহজ কথায়:
- **SP:** অ্যাকশন হিরো (Action Hero)। সে ডেটা ইনসার্ট করে, ডিলিট করে, ইমেইল পাঠায়—সব করে।
- **Function:** গণিতবিদ (Mathematician)। সে শুধু **হিসাব** করে একটা **ফলাফল ফেরত (Return)** দেয়। সে ডেটাবেসের কোনো পরিবর্তন (Insert/Update) করতে পারে না।

### 🎓 Lesson 33: Functions (User Defined) - নিজের ফর্মুলা বানানো

**সহজ বাংলা ব্যাখ্যা:**
SQL-এ আগে থেকেই `SUM()`, `AVG()`, `COUNT()` ফাংশন আছে। কিন্তু তোমার যদি নিজের কোনো লজিক লাগে? যেমন: ভ্যাট (VAT) বের করা, বা কারো বয়স বের করা। তখন তুমি নিজের ফাংশন বানাতে পারো।
ফাংশন ইনপুট নেয় (প্যারামিটার) এবং প্রসেস করে **একটি ভ্যালু** অথবা **একটি টেবিল** রিটার্ন করে।

**🤣 Funny Real-life Analogy:**
**জুস ব্লেন্ডার!** 🍹
- **Input:** তুমি আম বা কমলা দাও (Parameter)।
- **Process:** ভেতরে ব্লেন্ড হয় (Logic)।
- **Output:** জুস বেরিয়ে আসে (Return Value)।
ব্লেন্ডার কিন্তু তোমার রান্নাঘরের দেয়াল ভাঙে না বা নতুন ফ্রিজ কিনে আনে না (No Database Change)। সে শুধু ইনপুট নিয়ে আউটপুট দেয়।

---

### ✌️ Two Practical Examples

ফাংশন প্রধানত দুই প্রকার:
১. **Scalar Function:** যেটা একটি মাত্র ভ্যালু রিটার্ন করে (যেমন: ট্যাক্সের টাকা)।
২. **Table-Valued Function:** যেটা পুরো একটা টেবিল রিটার্ন করে (প্যারামিটারসহ ভিউ-এর মতো)।

#### **Example 1: Scalar Function (ট্যাক্স ক্যালকুলেটর)** 💵

ধরি, তোমার কোম্পানিতে নিয়ম হলো—যাদের বেতন ৫০,০০০-এর বেশি, তাদের ১০% ট্যাক্স দিতে হবে। আর বাকিদের ০%। এটা বের করার জন্য আমরা একটা ফাংশন বানাব।

**SQL Code:**
```sql
CREATE FUNCTION fn_CalculateTax (@Salary decimal)
RETURNS decimal  -- বলে দিতে হবে আউটপুট কী টাইপের হবে
AS
BEGIN
    DECLARE @TaxAmount decimal;

    -- লজিক বসানো হচ্ছে
    IF @Salary > 50000
        SET @TaxAmount = @Salary * 0.10; -- ১০% ট্যাক্স
    ELSE
        SET @TaxAmount = 0; -- গরিবদের ট্যাক্স মাফ

    RETURN @TaxAmount; -- রেজাল্ট ফেরত পাঠাও
END;
```

**ব্যবহার করব যেভাবে (Use within SELECT):**
ফাংশনকে আমরা `SELECT` কুয়েরির ভেতরেই ব্যবহার করতে পারি (SP এটা পারে না)।

```sql
SELECT Name, Salary, dbo.fn_CalculateTax(Salary) AS Tax_Due
FROM Employee;
```

#### **Example 2: Table-Valued Function (ফিল্টার করা বন্ধু তালিকা)** 📋

মনে আছে **View**? ভিউ-তে আমরা `WHERE` কন্ডিশন ফিক্সড করে দিতাম। কিন্তু ফাংশন দিয়ে আমরা ডাইনামিক ভিউ বানাতে পারি।
আমরা এমন একটা ফাংশন বানাব, যেখানে সিটির নাম দিলেই সেই সিটির বন্ধুদের লিস্ট চলে আসবে।

**SQL Code:**
```sql
CREATE FUNCTION fn_GetFriendsByCity (@CityName varchar(50))
RETURNS TABLE
AS
RETURN (
    SELECT Name, Phone, Address
    FROM Friends
    WHERE City = @CityName
);
```

**ব্যবহার করব যেভাবে:**
এটাকে ঠিক একটা টেবিলের মতোই ব্যবহার করা যায়!

```sql
-- ঢাকাবাসীদের দেখাও
SELECT * FROM dbo.fn_GetFriendsByCity('Dhaka');

-- সিলেটবাসীদের দেখাও
SELECT * FROM dbo.fn_GetFriendsByCity('Sylhet');
```

### 🛡️ SP vs Function (ইন্টারভিউতে ধরবেই!)

| Stored Procedure (SP) | User Defined Function (UDF) |
| :--- | :--- |
| ইনপুট এবং আউটপুট দুটোই নিতে/দিতে পারে। | অবশ্যই একটি ভ্যালু বা টেবিল **RETURN** করতেই হবে। |
| `INSERT`, `UPDATE`, `DELETE` করতে পারে। | সাধারণ ফাংশন ডেটা মডিফাই করতে পারে না (শুধু `SELECT` বা হিসাব)। |
| ডাকতে হয় `EXEC` দিয়ে। | ব্যবহার হয় `SELECT` বা `WHERE` ক্লজের ভেতরে। |
| **কাজ:** কিছু একটা ঘটাতে (Action)। | **কাজ:** কিছু একটা হিসাব করতে (Calculation)। |

---

**Mini Task:**
একটা ফাংশন বানাও `fn_FullName` নামে।
এটি দুটি ইনপুট নেবে: `@FirstName` এবং `@LastName`।
আউটপুট হিসেবে দুই নাম জোড়া লাগিয়ে পুরো নাম ফেরত দেবে (মাঝখানে একটা স্পেসসহ)।
Hint: `RETURN @FirstName + ' ' + @LastName;`

34. Triggers - অটোমেটিক অ্যাকশন।

অবশ্যই! SQL Server-এ **Trigger** বিষয়টি অনেকটা "অটোমেটিক রিয়েকশন" বা "গোপন গোয়েন্দা"-র মতো। চলুন, সহজ বাংলায় এবং একটু মজার উদাহরণের মাধ্যমে স্টেপ-বাই-স্টেপ বিষয়টি বুঝে নিই।

---

### 🤔 Trigger আসলে কী? (The Fun Concept)

সহজ কথায়, **Trigger** হলো এমন একধরণের কোড যা আপনি কল (Call) করেন না, সে একাই কল হয়।

মজার উদাহরণ:

মনে করুন, আপনার একজন খুব কড়া সিকিউরিটি গার্ড আছে। আপনি তাকে বলে রেখেছেন, "যখনই আমার বাড়িতে নতুন কেউ ঢুকবে (INSERT), তুমি তার নাম একটা খাতায় লিখে রাখবে।"

এখানে:

- **বাড়ি** = Database Table
    
- **নতুন কেউ ঢোকা** = INSERT Action
    
- **সিকিউরিটি গার্ড** = **Trigger**
    

আপনাকে বারবার গার্ডকে বলতে হবে না। কেউ ঢুকলেই সে _অটোমেটিক_ নাম লিখে রাখবে। এটাই ট্রিগারের কাজ!

---

### 🚦 Trigger কত ধরণের হয়?

SQL Server-এ প্রধানত দুই ধরণের ট্রিগার বেশি ব্যবহার হয়:

১. **AFTER Trigger (ঘটনার পরে):**

- আগে কাজ হবে, তারপর ট্রিগার ফায়ার হবে।
    
- _উদাহরণ:_ আপনি চড় খেলেন (Action), তারপর কাঁদলেন (Trigger)।
    

২. **INSTEAD OF Trigger (পরিবর্তে):**

- আসল কাজটা না হয়ে, ট্রিগার যা বলবে তাই হবে।
    
- _উদাহরণ:_ আপনি দোকানে সিগারেট চাইলেন (Action), কিন্তু দোকানদার আপনার বাবার ভয়ে সিগারেটের বদলে আপনাকে লজেন্স ধরিয়ে দিল (Trigger)।
    

---

### 🛠️ চলুন হাতে-কলমে (Step-by-Step) শিখি

আমরা একটা "AFTER Trigger" বানাবো।

ধরুন, আমাদের একটা Employee টেবিল আছে। যখনই এখানে নতুন কোনো এমপ্লয়ি যোগ (INSERT) করা হবে, একটা Audit_Log টেবিলে অটোমেটিক সেভ হয়ে যাবে যে, "অমুক সময়ে একটা নতুন এমপ্লয়ি যোগ হয়েছে"।

#### ধাপ ১: মেইন টেবিল তৈরি করা

প্রথমে আমরা `Employee` টেবিল বানাই।

SQL

``` SQL
CREATE TABLE Employee (
    ID INT PRIMARY KEY,
    Name VARCHAR(50),
    Salary INT
);
```

#### ধাপ ২: লগ (Log) টেবিল তৈরি করা

যেখানে আমাদের "গোয়েন্দা" (Trigger) খবর জমা রাখবে।



``` SQL
CREATE TABLE Employee_Log (
    LogID INT IDENTITY(1,1) PRIMARY KEY,
    Message VARCHAR(100),
    LogTime DATETIME
);
```

#### ধাপ ৩: জাদুকরী Trigger তৈরি করা 🧙‍♂️

এখন আমরা সেই অটোমেটিক কোডটি লিখব।



``` sql
CREATE TRIGGER trg_AfterInsert
ON Employee  -- কোন টেবিলের ওপর নজর রাখবে?
AFTER INSERT -- কখন অ্যাকশন নেবে? (INSERT এর পরে)
AS
BEGIN
    -- ট্রিগারের কাজ শুরু
    DECLARE @EmpName VARCHAR(50);

    -- 'inserted' হলো একটা ম্যাজিক টেবিল যা সদ্য ঢোকানো ডাটা ধরে রাখে
    SELECT @EmpName = Name FROM inserted;

    -- লগ টেবিলে খবর পাঠিয়ে দাও
    INSERT INTO Employee_Log (Message, LogTime)
    VALUES ('New Employee Added: ' + @EmpName, GETDATE());
    
    PRINT ' সাবধান! গোয়েন্দা সব দেখে ফেলেছে!';
END
```

> **💡 মনে রাখবেন:** ট্রিগারের ভেতর `inserted` এবং `deleted` নামে দুটি **Virtual Magic Table** থাকে।
> 
> - `inserted`: নতুন ডাটা ঢোকালে এখানে জমা থাকে।
>     
> - `deleted`: ডাটা ডিলিট করলে এখানে জমা থাকে।
>     

#### ধাপ ৪: টেস্ট করা (মজাটা দেখুন)

এখন আমরা শুধু `Employee` টেবিলে ডাটা ঢোকাবো, `Employee_Log` টেবিলে হাতও দেব না।

SQL

``` SQL
INSERT INTO Employee (ID, Name, Salary) 
VALUES (1, 'Rahim', 50000);
```

আউটপুট:

আপনি দেখবেন মেসেজ এসেছে: "সাবধান! গোয়েন্দা সব দেখে ফেলেছে!"

এখন চেক করুন লগ টেবিলটি:

SQL

```SQL
SELECT * FROM Employee_Log;
```

**ফলাফল:** দেখবেন সেখানে অটোমেটিক লেখা হয়ে গেছে— _"New Employee Added: Rahim"_ এবং সময়টাও রেকর্ড হয়ে গেছে!

### ⚠️ কখন Trigger ব্যবহার করবেন?

১. Audit Trail: কে কখন ডাটা চেঞ্জ করলো, তার হিসাব রাখতে (যেমনটা আমরা উপরে করলাম)।

২. Validation: ধরুন আপনি চান না কারো বেতন ১০০০ টাকার কম হোক। কেউ ১০০০-এর কম দিলেই ট্রিগার সেটা আটকে দেবে (Rollback)।

৩. Complex Calculation: স্টক ম্যানেজমেন্টে, যখনই কোনো প্রোডাক্ট বিক্রি হবে (INSERT), অটোমেটিক মেইন স্টক থেকে সেই পরিমাণ কমে যাবে (UPDATE)।

### 🚫 সাবধানতা (Warning)

ট্রিগার হলো "লুকানো" কোড। বেশি ট্রিগার বানালে ডাটাবেস স্লো হয়ে যেতে পারে, কারণ একটা ছোট্ট ইনসার্ট করতে গিয়ে তাকে পেছনের অনেকগুলো কাজ করতে হয়। তাই খুব প্রয়োজন ছাড়া ট্রিগার ব্যবহার না করাই ভালো।

---
চমৎকার! তাহলে চলুন দেখি কীভাবে **"INSTEAD OF"** ট্রিগার ব্যবহার করে ডাটা ডিলিট হওয়া আটকানো যায়।

এটা অনেকটা **"স্মার্ট সিকিউরিটি গার্ড"**-এর মতো, যে গেটের সামনে দাঁড়িয়ে থাকে। আপনি যদি বোমা (DELETE command) নিয়ে বাড়িতে ঢুকতে চান, সে আপনাকে গেটেই আটকে দেবে এবং ভেতরে ঢুকতে দেবে না।

---

### 🛡️ মিশন: "বস (Boss)"-কে বাঁচানো

ধরুন, আপনার `BossList` নামে একটা টেবিল আছে। ভুল করেও যদি কেউ বসের নাম ডিলিট করে ফেলে, তাহলে তো চাকরি শেষ! তাই আমরা একটা **INSTEAD OF DELETE** ট্রিগার সেট করব। কেউ ডিলিট করতে চাইলেও, ট্রিগার সেটা হতে দেবে না।

#### ধাপ ১: টেবিল তৈরি ও ডাটা ভরা

প্রথমে বসের টেবিলটা বানাই।



``` SQL
-- ১. টেবিল তৈরি
CREATE TABLE BossList (
    ID INT PRIMARY KEY,
    Name VARCHAR(50),
    Designation VARCHAR(50)
);

-- ২. ডাটা ইনসার্ট (আমাদের প্রিয় বস)
INSERT INTO BossList (ID, Name, Designation) 
VALUES (1, 'Mr. Jolil', 'The Big Boss');
```

#### ধাপ ২: বডিগার্ড (Trigger) তৈরি করা 💂‍♂️

এখন আমরা সেই জাদুকরী ট্রিগারটি লিখব। লক্ষ্য করুন, এখানে আমরা `AFTER DELETE` নয়, `INSTEAD OF DELETE` ব্যবহার করছি।

SQL

```SQL
CREATE TRIGGER trg_StopDelete
ON BossList
INSTEAD OF DELETE -- ডিলিট করার "পরিবর্তে" এই কোড চলবে
AS
BEGIN
    -- ডিলিট করার বদলে একটা ওয়ার্নিং দাও
    PRINT '❌ খবরদার! বসকে ডিলিট করার চেষ্টা করবেন না! চাকরি থাকবে না!';
    
    -- আসল ডিলিট কমান্ড এখানে লেখা হয়নি, তাই ডাটা ডিলিট হবে না।
END
```

#### ধাপ ৩: ডিলিট করার চেষ্টা করা (Test) 🔥

এখন চলুন দুষ্টামি করে বসকে ডিলিট করার চেষ্টা করি।

SQL

```SQL
DELETE FROM BossList 
WHERE ID = 1;
```

আউটপুট:

SQL Server আপনাকে মেসেজ দেবে:

> _"❌ খবরদার! বসকে ডিলিট করার চেষ্টা করবেন না! চাকরি থাকবে না!"_

#### ধাপ ৪: বস বেঁচে আছেন কি না চেক করা

আসলেই কি ডিলিট আটকে গেছে? চলুন দেখি:

SQL

``` SQL
SELECT * FROM BossList;
```

ফলাফল:

দেখবেন Mr. Jolil বহাল তবিয়তে টেবিলে বসে আছেন! ট্রিগারটি ডিলিট কমান্ডকে বাইপাস করে দিয়েছে।

---

### 🧠 আসলে কী ঘটল? (Behind the Scenes)

১. আপনি যখন DELETE কমান্ড দিলেন, SQL Server ট্রিগারের কাছে গেল।

২. ট্রিগার দেখল এটা INSTEAD OF DELETE।

৩. সে বলল: "দাঁড়ান ভাই, আসল টেবিল থেকে ডিলিট করার দরকার নেই। আমি ভেতরে যা কোড লেখা আছে (শুধু PRINT করা), সেটাই করব।"

৪. ফলে আসল ডিলিট অ্যাকশনটি কখনোই ঘটল না।

### 💡 বোনাস টিপস:

আপনি চাইলে এই ট্রিগারের ভেতর লজিক বসাতে পারেন। যেমন:

- _"যদি সাধারণ এমপ্লয়ি হয় তবে ডিলিট করো, কিন্তু বস হলে ডিলিট আটকে দাও।"_
    
- এটি করার জন্য `deleted` টেবিল ব্যবহার করে চেক করতে হবে যে কাকে ডিলিট করা হচ্ছে।

আমরা `INSTEAD OF UPDATE` ব্যবহার করব। অর্থাৎ, যখনই কেউ `UPDATE` চালাবে, আমাদের ট্রিগার আসল আপডেটের বদলে নিজের খুশিমতো আপডেট করবে।

#### ধাপ ১: স্যালারি টেবিল তৈরি ও বেচারা এমপ্লয়ি যোগ করা

প্রথমে টেবিল বানিয়ে "Kuddus" নামের একজনকে অ্যাড করি।

SQL

``` SQL
-- ১. টেবিল বানানো
CREATE TABLE MySalary (
    ID INT PRIMARY KEY,
    Name VARCHAR(50),
    Salary INT
);

-- ২. কুদ্দুস সাহেবের বর্তমান বেতন ২০,০০০ টাকা
INSERT INTO MySalary (ID, Name, Salary) 
VALUES (101, 'Kuddus', 20000);
```

#### ধাপ ২: সেই "দুষ্টু" ট্রিগার তৈরি করা 🧙‍♂️

এখন ট্রিগার লিখব। লজিকটা হলো:

- কেউ যদি বেতন বাড়াতে চায় (New Salary > Old Salary), তবে বেতন বাড়বে না, উল্টো ৫০০ টাকা কমে যাবে।
    

SQL

``` SQL
CREATE TRIGGER trg_AntiIncrement
ON MySalary
INSTEAD OF UPDATE -- আপডেট করার চেষ্টা করলেই আমি ধরব!
AS
BEGIN
    DECLARE @NewSalary INT;
    DECLARE @OldSalary INT;
    DECLARE @EmpID INT;

    -- 'inserted' টেবিলে থাকে নতুন যে বেতনটা ইউজার দিতে চেয়েছে
    SELECT @NewSalary = Salary, @EmpID = ID FROM inserted;

    -- 'deleted' টেবিলে থাকে পুরনো যে বেতনটা আগে থেকেই ছিল
    SELECT @OldSalary = Salary FROM deleted;

    -- লজিক চেক: বেতন কি বাড়ানোর সাহস করেছে?
    IF @NewSalary > @OldSalary
    BEGIN
        -- শাস্তি: বেতন বাড়বে না, উল্টো ৫০০ টাকা মাইনাস!
        UPDATE MySalary 
        SET Salary = @OldSalary - 500 
        WHERE ID = @EmpID;
        
        PRINT '😡 সাহস তো কম না! বেতন বাড়ানোর শাস্তি হিসেবে ৫০০ টাকা জরিমানা!';
    END
    ELSE
    BEGIN
        -- যদি বেতন সমান থাকে বা কমায়, তাহলে সমস্যা নেই, আপডেট করো
        UPDATE MySalary 
        SET Salary = @NewSalary 
        WHERE ID = @EmpID;
        
        PRINT '✅ আপডেট সফল হয়েছে।';
    END
END
```

> **Note:** আপডেট ট্রিগারের ভেতর `inserted` (নতুন ভ্যালু) এবং `deleted` (পুরনো ভ্যালু)—এই দুটো টেবিলই একসঙ্গে পাওয়া যায়। এটা দিয়েই আমরা তুলনা করি।

#### ধাপ ৩: বেতন বাড়ানোর চেষ্টা করা (Disaster!) 💣

এখন কুদ্দুস সাহেব চুপিসারে ডাটাবেজে ঢুকে নিজের বেতন **২০,০০০** থেকে বাড়িয়ে **৫০,০০০** করতে চাইলেন।

SQL

``` SQL
UPDATE MySalary

WHERE ID = 101;
```

এখন দেখি কুদ্দুস সাহেবের অ্যাকাউন্টে কত টাকা আছে।

# Indexes (Clustered & Non-Clustered) - সার্চ ফাস্ট করা।

অবশ্যই! **Index** হলো ডাটাবেসের **"GPS বা ম্যাপ"**। এটা ছাড়া SQL Server হলো একজন অন্ধ মানুষের মতো, যে হাতড়ে হাতড়ে ডাটা খোঁজে। আর ইনডেক্স থাকলে সে সুপারম্যানের মতো উড়ে গিয়ে ডাটা ধরে ফেলে! 🚀

চলুন সহজ এবং মজার উদাহরণের মাধ্যমে **Clustered** এবং **Non-Clustered** ইনডেক্স বুঝি।

---

### 📚 সমস্যাটা কোথায়? (The Problem)

ধরুন, আপনার কাছে ১০০০ পৃষ্ঠার একটা **"রান্নার বই" (Cookbook)** আছে। কিন্তু বইতে কোনো সূচিপত্র (Index) নেই এবং পেজ নম্বরও এলোমেলো।

এখন আমি যদি বলি: "ভাই, 'কাচ্চি বিরিয়ানি' রেসিপিটা বের করুন তো!"

আপনাকে কী করতে হবে?

- **Table Scan:** আপনাকে ১ নম্বর পৃষ্ঠা থেকে ১০০০ নম্বর পৃষ্ঠা পর্যন্ত সব উল্টে উল্টে দেখতে হবে কোথায় 'কাচ্চি' লেখা আছে। এটা খুবই **Slow** এবং বিরক্তিকর! 🐢
    

এই সমস্যা মেটাতেই আসে **Index**।

---

### ১. Clustered Index (বইয়ের পৃষ্ঠা নম্বর)

**Clustered Index** মানে হলো ডাটাগুলো ফিজিক্যালি ওই অর্ডারে সাজানো থাকে।

- উদাহরণ: ডিকশনারি (Dictionary)।
    
    ডিকশনারিতে শব্দগুলো A, B, C... এই অর্ডারে সাজানো থাকে। আপনি যদি 'Apple' খুঁজতে চান, আপনি জানেন এটা শুরুতেই থাকবে। আপনাকে পুরো ডিকশনারি খুঁজতে হবে না।
    
- **নিয়ম (Rule):** একটা টেবিলে **মাত্র ১টি** Clustered Index থাকতে পারে।
    
    - _কেন?_ কারণ, একটা আলমারিতে আপনি কাপড়গুলো হয় "কালার অনুযায়ী" সাজাতে পারেন, অথবা "সাইজ অনুযায়ী"। একই সাথে দুইভাবে তো ফিজিক্যালি সাজানো সম্ভব না!
        

### ২. Non-Clustered Index (বইয়ের পেছনের নির্ঘণ্ট)

**Non-Clustered Index** হলো আলাদা একটা লিস্ট, যা বলে দেয় আসল ডাটা কোথায় আছে।

- উদাহরণ: পাঠ্যবইয়ের পেছনের Index।
    
    বইয়ের শেষে লেখা থাকে:
    
    - Newton's Law ..... Page 50
        
    - Relativity ......... Page 95
        
    
    এখানে ডাটা (Law) পেছনের পেজে নেই, শুধু বলা আছে "কত নম্বর পেজে" গেলে ডাটা পাবে।
    
- **সুবিধা:** একটা টেবিলে অনেকগুলো (৯৯৯টি পর্যন্ত) Non-Clustered Index থাকতে পারে।

### 🛠️ কোড দিয়ে হাতে-কলমে শিখি (Code Example)

ধরুন আমাদের একটা লাইব্রেরি টেবিল আছে।

#### ধাপ ১: টেবিল তৈরি (কোনো ইনডেক্স ছাড়া)

এটা একটা এলোমেলো ঘর। বইগুলো ছড়ানো ছিটানো।

SQL

```SQL
CREATE TABLE LibraryBooks (
    BookID INT,
    BookName VARCHAR(100),
    Category VARCHAR(50)
);

-- কিছু বই এলোমেলোভাবে রাখি
INSERT INTO LibraryBooks VALUES (5, 'Harry Potter', 'Fiction');
INSERT INTO LibraryBooks VALUES (1, 'Learn SQL', 'Education');
INSERT INTO LibraryBooks VALUES (3, 'Himu', 'Novel');
INSERT INTO LibraryBooks VALUES (2, 'Physics', 'Science');
```

এখন যদি `SELECT * FROM LibraryBooks WHERE BookID = 2` দেন, SQL Server পুরো টেবিল খুঁজবে (**Table Scan**)।

#### ধাপ ২: Clustered Index তৈরি করা (সাজানো ঘর)

আমরা `BookID` দিয়ে বইগুলো সাজিয়ে ফেলি।



```SQL
-- Clustered Index তৈরি করছি (সাধারণত Primary Key দিলেই এটা অটো হয়ে যায়)
CREATE CLUSTERED INDEX IX_Library_BookID
ON LibraryBooks(BookID);
```

এখন কী হলো?

টেবিলের ডাটাগুলো অটোমেটিক BookID অনুযায়ী ১, ২, ৩, ৫... সিরিয়ালে সেভ হয়ে গেল। এখন BookID = 2 খুঁজলে SQL চোখের পলকে সেটা পেয়ে যাবে।

#### ধাপ ৩: Non-Clustered Index তৈরি করা (শর্টকাট লিস্ট)

ধরুন, মানুষ আইডি দিয়ে বই খোঁজে না, নাম দিয়ে খোঁজে (`BookName`)। কিন্তু বইগুলো তো আইডি দিয়ে সাজানো। তাহলে?

আমরা নামের ওপর একটা Non-Clustered Index বানাব। এটা আলাদা একটা লিস্ট বানাবে যেখানে নাম আর তার ঠিকানা (Address) থাকবে।

SQL

```SQL
-- নামের ওপর ইনডেক্স বানালাম
CREATE NONCLUSTERED INDEX IX_Library_BookName
ON LibraryBooks(BookName);
```

এখন কী হবে?

কেউ যদি 'Harry Potter' খোঁজে, SQL Server মেইন টেবিলে না গিয়ে, পেছনের ইনডেক্স পেজে যাবে। দেখবে 'Harry Potter' কোথায় আছে, তারপর সরাসরি সেই রো-তে জাম্প করবে। একে বলে Index Seek (সুপার ফাস্ট! 🚀)।

### 🥊 Clustered vs Non-Clustered: আসল পার্থক্য

|**বৈশিষ্ট্য**|**Clustered Index**|**Non-Clustered Index**|
|---|---|---|
|**আসল ডাটা**|ডাটা নিজেই সাজানো থাকে।|ডাটা এক জায়গায়, ইনডেক্স আরেক জায়গায়।|
|**সংখ্যা**|প্রতি টেবিলে **১টি** মাত্র।|প্রতি টেবিলে **অনেকগুলো** হতে পারে।|
|**স্টোরেজ**|আলাদা কোনো জায়গার দরকার নেই।|আলাদা স্টোরেজ স্পেস লাগে (এক্সট্রা লিস্ট রাখার জন্য)।|
|**গতি**|সবচেয়ে ফাস্ট।|ফাস্ট, তবে Clustered-এর চেয়ে সামান্য কম।|
|**উদাহরণ**|ডিকশনারি।|পাঠ্যবইয়ের শেষের ইনডেক্স।|

### ⚠️ মজার সতর্কতা (Funny Warning)

ইনডেক্স ভালো, কিন্তু **"বেশি ইনডেক্স"** আবার বিপদ! 😵‍💫

ধরুন, আপনি একটা নতুন বই কিনলেন (INSERT)।

- যদি ইনডেক্স না থাকে, আপনি জাস্ট বইটা টেবিলে ফেলে দিলেন। (খুবই ফাস্ট)।
    
- যদি ৫টা ইনডেক্স থাকে, আপনাকে ৫টা আলাদা খাতায় নাম লিখে আপডেট করতে হবে যে নতুন বই এসেছে।
    

তাই:

- **SELECT (Search)** করার জন্য ইনডেক্স ভালো।
    
- **INSERT/UPDATE/DELETE** করার জন্য ইনডেক্স স্লো করে দেয় (কারণ সব লিস্ট আপডেট করতে হয়)।
    

---

হা হা! অবশ্যই। **Index** বিষয়টি আরেকটু জম্পেশ করে বোঝার জন্য চলুন আমাদের দৈনন্দিন জীবনের কিছু **মজার এবং করুণ** পরিস্থিতি কল্পনা করি। 😂

### ১. Clustered Index: "ব্যাচেলর ছেলের রুম vs আম্মুর গুছানো রুম"

পরিস্থিতি (Scenario):

ধরুন, আপনি একজন ব্যাচেলর। আপনার রুমে খাট, টেবিল, ফ্লোর—সব জায়গায় কাপড়, বই, পিজ্জার বক্স ছড়ানো ছিটানো। একে বলে "Heap Table" (কোনো ইনডেক্স ছাড়া টেবিল)।

ঘটনা:

হঠাৎ আপনার গার্লফ্রেন্ড ফোন দিয়ে বলল, "৫ মিনিটের মধ্যে ভিডিও কলে আসছি, নীল শার্টটা পরে আসো।"

- **ইনডেক্স ছাড়া (Table Scan):** আপনি পাগলের মতো পুরো রুম তছনছ করছেন। খাটের নিচে, বালিশের নিচে, বাথরুমের হ্যাঙ্গারে... সব জায়গায় খুঁজছেন। ৫ মিনিট শেষ, শার্ট পেলেন না, গার্লফ্রেন্ডও রেগে আগুন! 🔥
    
- Clustered Index (আম্মুর টাচ):
    
    আপনার আম্মু এসে রুমটা গুছিয়ে দিলেন। তিনি আলমারিতে সব কাপড় "ধরন অনুযায়ী" (Category wise) ফিজিক্যালি সাজিয়ে রাখলেন।
    
    - তাক ১: শার্ট
        
    - তাক ২: প্যান্ট
        
    - তাক ৩: মোজা
        
    
    এখন আপনি জানেন "শার্ট" মানেই ১ নম্বর তাকে যেতে হবে। খোঁজাখুঁজির দরকার নেই। সোজা গিয়ে শার্ট বের করলেন। এটাই **Clustered Index**—যেখানে ডাটা নিজেই সাজানো থাকে।

### ২. Non-Clustered Index: "বিয়ে বাড়ির দাওয়াত" 🍛

পরিস্থিতি (Scenario):

একটা বিশাল বিয়ে বাড়ি। ৫০০০ মেহমান। সবাই টেবিল-চেয়ারে বসে আছে (ডাটা সাজানো আছে)।

Clustered Index (Primary Key):

চেয়ারগুলোতে ১, ২, ৩... করে নম্বর দেওয়া আছে। আপনি যদি জানেন আপনার বন্ধুর সিট নম্বর "৫০৫", আপনি সোজা হেঁটে গিয়ে তাকে খুঁজে পাবেন।

সমস্যা:

আপনি সিট নম্বর জানেন না। আপনি শুধু জানেন আপনার বন্ধুর নাম "বল্টু"।

Non-Clustered Index (রিসেপশনের লোক):

গেটে একজন লোক একটা ল্যাপটপ বা লিস্ট নিয়ে বসে আছে।

আপনি তাকে বললেন: "ভাই, বল্টু কোথায়?"

সে লিস্ট চেক করে বলল: "বল্টু বসে আছে ১০২ নম্বর টেবিলে।" (সে আপনাকে ঠিকানা বা Address দিল)।

এখানে রিসিপশনের ওই লিস্টটা হলো **Non-Clustered Index**। সে নিজে "বল্টু" না, কিন্তু সে জানে বল্টু ঠিক কোন জায়গায় বসে আছে।

### ৩. ইনডেক্সের সাইড ইফেক্ট: "লাইব্রেরিয়ান এর কান্না" 😭

ইনডেক্স সার্চ ফাস্ট করে, কিন্তু **INSERT** বা **UPDATE** স্লো করে দেয়। কেন?

মজার উদাহরণ:

ধরুন, একটা স্কুলে ৫টা নোটিশ বোর্ড (Index) আছে:

১. ভালো ছাত্রদের লিস্ট

২. লম্বা ছাত্রদের লিস্ট

৩. ক্রিকেট প্লেয়ারদের লিস্ট

৪. ঢাকায় থাকে এমন ছাত্রদের লিস্ট

৫. চশমা পরা ছাত্রদের লিস্ট

নতুন ছাত্র (INSERT Action):

এখন "রফিক" নামে একজন নতুন ছাত্র ভর্তি হলো। সে ভালো ছাত্র, লম্বাও, ক্রিকেটও খেলে, ঢাকায় থাকে আবার চশমাও পরে!

বেচারা পিওন (SQL Server)-কে এখন কী করতে হবে?

সে শুধু রফিককে ক্লাসে বসিয়ে দিয়েই খালাস না। তাকে দৌড়ে দৌড়ে গিয়ে ৫টা নোটিশ বোর্ডেই রফিকের নাম লিখতে হবে।

- একবার মেইন খাতায় নাম তোলো।
    
- দৌড়ে গিয়ে ক্রিকেট লিস্ট আপডেট করো।
    
- দৌড়ে গিয়ে চশমা লিস্ট আপডেট করো...
    

এজন্যই, **বেশি ইনডেক্স থাকলে নতুন ডাটা ঢোকাতে (Insert) গেলে SQL Server এর জিভ বেরিয়ে যায়!** 🥵

### 📝 কোড দিয়ে উদাহরণ (The Funny Code)

চলুন একটা `BachelorsRoom` টেবিল বানাই।



``` SQL
CREATE TABLE BachelorsRoom (
    ItemID INT PRIMARY KEY,      -- Clustered Index (জিনিসপত্রের আইডি)
    ItemName VARCHAR(50),        -- জিনিসের নাম
    Location VARCHAR(50)         -- কোথায় আছে
);

-- ইনডেক্স ছাড়া খোঁজা (Table Scan)
-- SQL: "ভাই থাম, আমি খাটের তলা থেকে শুরু করে সব খুঁজছি..."
SELECT * FROM BachelorsRoom WHERE ItemName = 'Blue Shirt';

-- Non-Clustered Index বানালাম (আম্মুর চিরকুটে লেখা লিস্ট)
CREATE NONCLUSTERED INDEX IX_Find_Item_Fast
ON BachelorsRoom (ItemName);

-- ইনডেক্স বানানোর পর (Index Seek)
-- SQL: "ওহ! নীল শার্ট? লিস্টে দেখছি... হ্যাঁ, এটা আলমারির ২য় তাকে আছে।" (এক সেকেন্ডে কাজ শেষ!)
SELECT * FROM BachelorsRoom WHERE ItemName = 'Blue Shirt';
```

---

**উপসংহার (Conclusion):**

- **Clustered Index:** আলমারিতে কাপড় সাজানো (ফিজিক্যাল)।
    
- **Non-Clustered Index:** গেটের দারোয়ানের কাছে মেহমানদের লিস্ট (লজিক্যাল পয়েন্টার)।
    
- **Too Many Indexes:** পিওনের দৌড়াদৌড়ি বেড়ে যাওয়া (Insert/Update স্লো)।

 # Transactions (ACID Properties) - সব হবে অথবা কিছুই হবে না।

অবশ্যই! **Transaction** হলো ডাটাবেসের **"সবল ও বিশ্বস্ত বন্ধু"**। এর মূল মন্ত্র হলো: **"হয় এসপার, নয় ওসপার!"** (All or Nothing)। মাঝপথে ঝুলে থাকা এর স্বভাবে নেই।

চলুন, একটা খুব কমন এবং ভয়ংকর পরিস্থিতি দিয়ে বিষয়টি বুঝি।

---

### 😱 পরিস্থিতি: বিকাশে (Bkash) টাকা পাঠানো

ধরুন, আপনি আপনার বন্ধু "বল্টু"-কে ৫০০ টাকা পাঠাচ্ছেন। এখানে দুটো ঘটনা ঘটতে হবে:

১. আপনার অ্যাকাউন্ট থেকে ৫০০ টাকা কাটবে।

২. বল্টুর অ্যাকাউন্টে ৫০০ টাকা যোগ হবে।

ভয়ংকর সিনারিও (Transaction ছাড়া):

আপনার অ্যাকাউন্ট থেকে ৫০০ টাকা কাটল (Step 1 Complete)... ঠিক সেই মুহূর্তে ডাটাবেসের কারেন্ট চলে গেল বা সার্ভার ক্র্যাশ করল! 💥

- ফলাফল: আপনার টাকা গায়েব, বল্টুও টাকা পেল না। টাকা এখন **"হাওয়াই মিঠাই"** হয়ে গেল! 😭
    

এই সমস্যা ঠেকানোর জন্যই **Transaction**। সে বলে: _"হয় দুটো কাজই সফল হবে, আর যদি মাঝপথে কোনো সমস্যা হয়, তবে আমি আপনার কাটা টাকা ফেরত দিয়ে আগের অবস্থায় (Rollback) নিয়ে যাব।"_

---

### 🧪 ACID প্রপার্টিজ (মজার ব্যাখ্যা)

Transaction ঠিকঠাক কাজ করার জন্য **ACID** নামের ৪টি কঠিন নিয়ম মেনে চলে।

| **অক্ষর** | **পূর্ণরূপ**    | **মজার মানে (Funny Meaning)**                                                                                                                                    |
| --------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A**     | **Atomicity**   | **"এক যাত্রায় দুই ফল, না হলে যাত্রা বাতিল।"**<br><br><br>হয় পুরো কাজ হবে (Commit), না হলে কিছুই হবে না (Rollback)। মাঝপথে কিছু হবে না।                          |
| **C**     | **Consistency** | **"কড়া হেডমাস্টার।"**<br><br><br>লেনদেনের আগে ও পরে টাকার মোট হিসাব মিলতেই হবে। ডাটাবেসের কোনো নিয়ম ভাঙা যাবে না।                                                |
| **I**     | **Isolation**   | **"টয়লেটের দরজা।"** 🚽<br><br>  <br>একজন ভেতরে থাকলে অন্যজন ঢুকতে পারবে না। আমি যখন টাকা পাঠাচ্ছি, তখন অন্য কেউ আমার ব্যালেন্স চেক করতে পারবে না। লাইন ধরো মিয়া! |
| **D**     | **Durability**  | **"পাথরে খোদাই করা।"** 🗿<br><br><br>একবার ট্রানজেকশন সফল (Commit) হলে, ভূমিকম্প হয়ে সার্ভার পুড়ে গেলেও ওই ডাটা আর মুছবে না। সেভ মানে সেভ!                       |

### 💻 কোড দিয়ে হাতে-কলমে (Code Example)

চলুন আমরা SQL Server-এ একটা ব্যাংকিং সিস্টেম বানাই এবং দেখি Transaction কীভাবে আমাদের বাঁচায়।

#### ধাপ ১: টেবিল সেটআপ



``` SQL
CREATE TABLE BankAccounts (
    AccountID INT PRIMARY KEY,
    OwnerName VARCHAR(50),
    Balance DECIMAL(10, 2)
);

-- আমার এবং বল্টুর অ্যাকাউন্ট
INSERT INTO BankAccounts VALUES (1, 'Me', 1000.00);
INSERT INTO BankAccounts VALUES (2, 'Boltu', 500.00);
```

#### ধাপ ২: টাকা পাঠানো (Transaction সহ) ✅

আমরা ৫০০ টাকা পাঠাব। `BEGIN TRANSACTION` দিয়ে শুরু করব, আর সব ঠিক থাকলে `COMMIT` করব।

SQL

``` SQL
BEGIN TRY
    -- ১. ট্রানজেকশন শুরু (বিসমিল্লাহ...)
    BEGIN TRANSACTION;

        -- ধাপ ক: আমার টাকা কাটো
        UPDATE BankAccounts 
        SET Balance = Balance - 500 
        WHERE AccountID = 1;

        -- ধাপ খ: বল্টুকে টাকা দাও
        UPDATE BankAccounts 
        SET Balance = Balance + 500 
        WHERE AccountID = 2;

    -- ২. সব ঠিক থাকলে সেভ করো (Final Save)
    COMMIT TRANSACTION;
    PRINT '✅ টাকা পাঠানো সফল! টেনশন নাই।';
END TRY
BEGIN CATCH
    -- ৩. যদি কোনো এরর বা ঘাপলা হয়, সব বাতিল করো!
    ROLLBACK TRANSACTION;
    PRINT '❌ সমস্যা হয়েছে! টাকা ফেরত নেওয়া হচ্ছে (Rollback)।';
END CATCH;
```

#### ধাপ ৩: মজা দেখা (Error Scenario) ❌

ধরুন, আমরা ইচ্ছাকৃত একটা ভুল করব। আমার টাকা কাটবে, কিন্তু বল্টুকে দেওয়ার সময় একটা ভুল হবে। দেখি `ROLLBACK` হয় কি না।

SQL

``` SQL
BEGIN TRY
    BEGIN TRANSACTION;

        -- ধাপ ক: আমার টাকা কাটো (১০০০ - ৫০০ = ৫০০)
        UPDATE BankAccounts 
        SET Balance = Balance - 500 
        WHERE AccountID = 1;

        -- ধাপ খ: এখানে একটা ভেজাল বা এরর করলাম (শূন্য দিয়ে ভাগ!)
        DECLARE @Bug INT = 1/0; 

        -- ধাপ গ: বল্টুকে টাকা দাও (এই লাইন আর কাজ করবে না)
        UPDATE BankAccounts 
        SET Balance = Balance + 500 
        WHERE AccountID = 2;

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    -- এরর খাওয়ার সাথে সাথে এখানে চলে আসবে
    ROLLBACK TRANSACTION;
    PRINT '❌ ওরে বাবা! এরর খেয়েছি, তাই সব আগের মতো করে দিলাম।';
END CATCH;
```

**ফলাফল চেক করুন:**

SQL

``` SQL
SELECT * FROM BankAccounts;
```

আপনি দেখবেন:

- আপনার ব্যালেন্স এখনো **১০০০**-ই আছে।
    
- যদিও প্রথম আপডেটটি চলেছিল, কিন্তু `ROLLBACK` কমান্ড সেটাকে মেমোরি থেকে মুছে দিয়েছে যেন কিছুই হয়নি! যাদু! 🎩

### 📝 এক কথায় সারসংক্ষেপ

- **BEGIN TRANSACTION:** খেলা শুরু।
    
- **COMMIT:** সব ঠিক আছে, লক করে দাও।
    
- **ROLLBACK:** ভেজাল হয়েছে, পেছনের দিকে দৌড় দাও (Undo)।

## Error Handling (Try/Catch).

অবশ্যই! **Try/Catch** হলো কোডিং জগতের **"প্যারাশুট"** বা **"ব্যাকআপ প্ল্যান"**। 🪂

কোড রান করার সময় হুট করে যদি লাল রঙের ভয়ংকর এরর (Error) আসে, তাহলে পুরো সফটওয়্যার ক্র্যাশ করতে পারে। এটা অনেকটা বাইক চালাতে গিয়ে আছাড় খাওয়ার মতো। কিন্তু আপনি যদি হেলমেট আর নি-গার্ড (Try/Catch) পরে থাকেন, তবে আছাড় খেলেও হাড় ভাঙবে না, আপনি উঠে দাঁড়িয়ে বলতে পারবেন—_"আরে, কিছু হয়নি! আমি ঠিক আছি।"_

চলুন মজার উদাহরণের মাধ্যমে শিখি।

---

### 🤣 মজার উদাহরণ: "কাচ্চি রান্না ও মানসম্মান"

ধরুন, আপনি আপনার শ্বশুরবাড়ির লোকজনকে দাওয়াত দিয়েছেন এবং নিজের হাতে **কাচ্চি বিরিয়ানি** রান্না করার সিদ্ধান্ত নিলেন।

- BEGIN TRY (চেষ্টা করা):
    
    আপনি হাড়িপাতিল নিয়ে রান্না শুরু করলেন। এটা হলো রিস্কি জোন। এখানে যেকোনো দুর্ঘটনা ঘটতে পারে (মাংস পুড়ে যেতে পারে, লবণ বেশি হতে পারে)।
    
    - _যদি রান্না ঠিক হয়:_ সবাই খেয়ে প্রশংসা করবে।
        
    - _যদি রান্না পুড়ে ছাই হয়ে যায় (Error):_ শ্বশুরবাড়ির সামনে মানসম্মান শেষ! 😱
        
- BEGIN CATCH (ব্যাকআপ প্ল্যান):
    
    আগেই আপনি বুদ্ধি করে আপনার বন্ধুকে বলে রেখেছেন— "দোস্ত, যদি আমার রান্না নষ্ট হয়, তুই জলদি রেস্টুরেন্ট থেকে ৫ প্যাকেট বিরিয়ানি কিনে পেছনের দরজা দিয়ে ঢুকিয়ে দিবি।"
    
    ফলে, রান্না নষ্ট হওয়ার পর (Error ঘটার পর), আপনি মেহমানদের বুঝতেও দিলেন না। আপনি রেস্টুরেন্টের বিরিয়ানি টেবিলে দিয়ে দিলেন। **এটাই Catch ব্লকের কাজ—এরর হ্যান্ডেল করা বা পরিস্থিতি সামাল দেওয়া।**

### 🛠️ কোড দিয়ে হাতে-কলমে (Step-by-Step)

আমরা SQL Server-এ একটা "নিষিদ্ধ কাজ" করব। আমরা কোনো সংখ্যাকে **০ (শূন্য)** দিয়ে ভাগ করার চেষ্টা করব। গণিতের ভাষায় এটা অসম্ভব (Undefined), তাই SQL সাধারণত এরর দিয়ে ক্র্যাশ করে। কিন্তু আমরা Try/Catch দিয়ে সেটা সামলাব।

#### ১. Try/Catch ছাড়া (বিপদ!) ❌



``` SQL
SELECT 100 / 0; -- ১০ টাকা ০ জনের মধ্যে ভাগ করে দাও
```

আউটপুট:

SQL একটা লাল রঙের ধমক দেবে:

> Msg 8134, Level 16... Divide by zero error encountered.
> 
> (মানে: প্রোগ্রাম ক্র্যাশ!)

#### ২. Try/Catch সহ (স্মার্ট সলিউশন) ✅

এবার আমরা কোডটাকে একটা সুরক্ষাবলয়ের মধ্যে রাখব।

SQL

``` SQL
BEGIN TRY
    -- ১. চেষ্টা করো (Risky Code)
    PRINT 'চেষ্টা করছি ভাগ করার...';
    
    DECLARE @Result INT;
    SET @Result = 100 / 0; -- এখানে এসেই এক্সিডেন্ট হবে!
    
    PRINT 'ভাগফল হলো: ' + CAST(@Result AS VARCHAR);
    -- এই লাইন আর প্রিন্ট হবে না, কারণ আগেই এরর হয়েছে।
END TRY
BEGIN CATCH
    -- ২. যদি কোনো সমস্যা হয়, এখানে চলে আসবে (Rescue Team)
    PRINT '⚠️ ভাই, শূন্য দিয়ে কি ভাগ করা যায়? গণিত বই পড়েন নাই?';
    PRINT 'Error Message: ' + ERROR_MESSAGE(); -- আসল এররটা কী ছিল?
END CATCH;
```

আউটপুট:

এবার আর লাল রঙের এরর আসবে না। আউটপুট আসবে:

> চেষ্টা করছি ভাগ করার...
> 
> ⚠️ ভাই, শূন্য দিয়ে কি ভাগ করা যায়? গণিত বই পড়েন নাই?
> 
> Error Message: Divide by zero error encountered.

---

### 🕵️‍♂️ গোয়েন্দাগিরি: Error-এর নাড়ি-নক্ষত্র বের করা

Catch ব্লকের ভেতর আপনি কিছু স্পেশাল ফাংশন ব্যবহার করে জানতে পারেন ঠিক কী ঘটেছিল:

|**ফাংশন**|**কাজ (Bangla)**|
|---|---|
|`ERROR_MESSAGE()`|আসলে কী এরর হয়েছিল? (যেমন: Divide by zero)|
|`ERROR_LINE()`|কত নম্বর লাইনে কোড ফেটেছে?|
|`ERROR_NUMBER()`|এররের একটা আইডি নম্বর থাকে, সেটা কত?|
|`ERROR_SEVERITY()`|এররটা কতটা মারাত্মক? (সিরিয়াসনেস লেভেল)|

**উদাহরণ:**

SQL

```SQL
BEGIN TRY
    SELECT 1/0;
END TRY
BEGIN CATCH
    SELECT 
        ERROR_LINE() AS [কোন লাইনে মরেছে],
        ERROR_MESSAGE() AS [কেন মরেছে];
END CATCH
```

---

### 📝 সারসংক্ষেপ (Recap)

১. BEGIN TRY: এখানে আপনার মেইন কোড লিখবেন। যদি সব ঠিক থাকে, কোড রান করে শেষ হয়ে যাবে। CATCH-এ যাবেই না।

২. Error: TRY-এর ভেতর কোনো এরর হলে, সাথে সাথে কাজ বন্ধ হয়ে CATCH-এ জাম্প করবে।

৩. BEGIN CATCH: এখানে আপনি এরর মেসেজ প্রিন্ট করতে পারেন, অথবা এডমিনকে মেইল পাঠাতে পারেন, অথবা ট্রানজেকশন ROLLBACK করতে পারেন।

## আসুন **Cursor**-এর বিষয়টি সহজ এবং মজার একটি উদাহরণের মাধ্যমে বুঝে নিই।

SQL Server সাধারণত কাজ করতে পছন্দ করে "Set-based" বা দলগতভাবে (একসাথে অনেক ডাটা)। কিন্তু **Cursor** কাজ করে **Row-by-Row** বা একটা একটা করে।

### 🤣 মজার উদাহরণ: বিয়ের দাওয়াত

ধরুন, আপনি আপনার ৫০০ জন বন্ধুকে বিয়ের দাওয়াত দিয়েছেন এবং তাদের খাওয়াতে হবে।

১. সাধারণ SQL (Set-based):

আপনি "বুফে" (Buffet) সিস্টেম চালু করলেন। খাবার টেবিলে রাখা আছে, সবাই একসাথে গিয়ে খাবার নিয়ে নিল। কাজ শেষ মাত্র ৩০ মিনিটে! 🚀

২. Cursor (Row-by-Row):

আপনি ঠিক করলেন আপনি নিজের হাতে সবাইকে খাওয়াবেন, কিন্তু আপনার কাছে চামচ আছে মাত্র একটি! 🥄

- আপনি প্রথম বন্ধুর কাছে গেলেন → এক চামচ বিরিয়ানি খাওয়ালেন → মুখ মুছিয়ে দিলেন।
    
- তারপর দ্বিতীয় বন্ধুর কাছে গেলেন → আবার একই কাজ।
    
- এভাবে ৫০০ জন বন্ধুকে খাওয়াতে আপনার ৩ দিন লেগে যাবে! 🐢
    

এজন্যই প্রোগ্রামাররা Cursor এড়িয়ে চলতে চান কারণ এটি বেশ স্লো। তবে কখনো কখনো (যেমন খুব জটিল ক্যালকুলেশনে) প্রতিটি ডাটা আলাদাভাবে চেক করার জন্য আমাদের এই "এক চামচ" বা Cursor-এর দরকার হয়।



১. Cursor-এর জীবনচক্র (Lifecycle): Cursor ব্যবহারের ৫টি ধাপ কী কী?

২. Cursor-এর প্রকারভেদ: সব চামচ কি একই রকম? (Static, Dynamic, etc.)



____
আসুন, কার্সরের এই ৫টি ধাপ একটি উদাহরণের মাধ্যমে কোডসহ দেখে নিই।

আমরা সেই **"বিরিয়ানি খাওয়া"** বা চামচের উদাহরণটিই এখানে ব্যবহার করব, যাতে মনে রাখা সহজ হয়।

### কার্সরের ৫টি ধাপ (Lifecycle)

|**ধাপ**|**SQL কমান্ড**|**কাজ ও উদাহরণ (Analogy) 🥄**|
|---|---|---|
|**১. ঘোষণা করা**|`DECLARE`|**চামচ ঠিক করা:** আপনি ঠিক করলেন কোন টেবিলের ডাটা (কোন হাড়ির খাবার) নিয়ে কাজ করবেন।|
|**২. খোলা**|`OPEN`|**হাড়ি খোলা:** ডাটাবেস মেমোরিতে ডাটা লোড করে প্রস্তুত করে। খাওয়ার জন্য হাড়ির ঢাকনা খোলার মতো।|
|**৩. তুলে আনা**|`FETCH`|**এক চামচ তোলা:** এটি একটি একটি করে রো (Row) বা ডাটা তুলে আনে। এটি লুপের মধ্যে বারবার চলে।|
|**৪. বন্ধ করা**|`CLOSE`|**ঢাকনা লাগানো:** কাজ শেষ, তাই কার্সর বন্ধ করা হয়। তবে মেমোরিতে চামচটি (Structure) তখনো থাকে।|
|**৫. মুছে ফেলা**|`DEALLOCATE`|**চামচ ধুয়ে রাখা:** মেমোরি থেকে কার্সরটি পুরোপুরি ডিলিট করে দেওয়া। এটি না করলে মেমোরি জ্যাম হয়ে থাকতে পারে।|

### কোড উদাহরণ (Code Example)

নিচের কোডটি `Employee` টেবিল থেকে একে একে সব নাম প্রিন্ট করবে:

SQL

``` Sql
-- ডাটা রাখার জন্য একটি ভেরিয়েবল নিলাম
DECLARE @EmpName NVARCHAR(50);

-- ১. DECLARE: কার্সর ঘোষণা (চামচ ঠিক করা)
DECLARE myCursor CURSOR FOR
SELECT Name FROM Employee;

-- ২. OPEN: কার্সর খোলা (হাড়ি খোলা - মেমোরিতে লোড হলো)
OPEN myCursor;

-- ৩. FETCH: প্রথম ডাটা বা রো তুলে আনা (প্রথম চামচ খাওয়া)
FETCH NEXT FROM myCursor INTO @EmpName;

-- লুপ চালানো: যতক্ষণ ডাটা পাওয়া যাবে (@@FETCH_STATUS = 0 মানে সব ঠিক আছে)
WHILE @@FETCH_STATUS = 0
BEGIN
    -- ডাটা নিয়ে কাজ করা (এখানে শুধু প্রিন্ট করছি)
    PRINT 'Employee Name: ' + @EmpName;

    -- লুপের ভেতরে পরবর্তী ডাটা বা রো তুলে আনা (পরের চামচ)
    FETCH NEXT FROM myCursor INTO @EmpName;
END

-- ৪. CLOSE: কার্সর বন্ধ করা (খাওয়া শেষ, ঢাকনা লাগাও)
CLOSE myCursor;

-- ৫. DEALLOCATE: মেমোরি থেকে মুছে ফেলা (চামচ সরিয়ে রাখো)
DEALLOCATE myCursor;
```

লক্ষ্য করুন, কোডের ভেতরে `FETCH NEXT` কমান্ডটি আমরা **দুইবার** ব্যবহার করেছি (একবার লুপের ঠিক আগে, আরেকবার লুপের একদম শেষে)।

আপনার কি মনে হয়, লুপের ভেতরে শেষের ওই `FETCH NEXT` লাইনটি যদি আমরা না লিখতাম, তাহলে কোডটি রান করার পর কী ঘটত? (ইঙ্গিত: লুপটি কি থামত?)

দারুণ প্রশ্ন! ঠিক যেমন বিরিয়ানি খাওয়ার জন্য আমরা সাধারণ চামচ ব্যবহার করি, কিন্তু সুপ খাওয়ার জন্য গোল চামচ—তেমনি ডাটাবেসেও কাজের ধরণ অনুযায়ী **৪ ধরণের** কার্সর (চামচ) আছে।

আসুন আমাদের "খাওয়ার উদাহরণ" দিয়েই এদের পার্থক্য বুঝি:

### ১. Static Cursor (টিফিন বক্স 🍱)

এটা হলো বাসা থেকে টিফিন বক্সে ভরে আনা খাবারের মতো।

- **কাজ:** আপনি যখন কার্সর ওপেন করেন, সে ডাটার একটা **Temp Copy** (TempDB-তে) আলাদা করে রাখে।
    
- **বৈশিষ্ট্য:** আপনি খাওয়ার সময় যদি মেইন হাড়িতে কেউ নতুন মাংস দেয় বা ডাটা পরিবর্তন করে, আপনার টিফিন বক্সের খাবারে তার **কোনো প্রভাব পড়বে না**। আপনি পুরনো ডাটায় কাজ করবেন।
    

### ২. Dynamic Cursor (সরাসরি হাড়ি থেকে 🍲)

এটা হলো সরাসরি চুলায় বসানো হাড়ি থেকে খাওয়া।

- **কাজ:** এটি ডাটার কোনো কপি করে না, সরাসরি মেইন টেবিলের দিকে তাকিয়ে থাকে।
    
- **বৈশিষ্ট্য:** আপনি খাওয়ার সময় অন্য কেউ যদি টেবিলে নতুন ডাটা দেয় বা ডিলিট করে, আপনি পরের চামচ তোলার সময় সেটা **সাথে সাথে দেখতে পাবেন**। এটি রিয়েল-টাইম ডাটা দেখায়।
    

### ৩. Fast_Forward Cursor (ওয়ান-টাইম প্লাস্টিক চামচ 🥄)

এটা সবচেয়ে ফাস্ট এবং সবচেয়ে বেশি ব্যবহৃত হয়।

- **কাজ:** এটি শুধু **সামনের দিকে** (Next) যেতে পারে।
    
- **বৈশিষ্ট্য:** আপনি একবার খেয়ে ফেললে আর পেছনে (Previous) ফিরে যেতে পারবেন না। এটি খুব হালকা এবং দ্রুত কাজ করে। একে `Read Only` কার্সরও বলা যায়।
    

### ৪. Keyset Cursor (টোকেন সিস্টেম 🎫)

এটি ডাটার পুরো কপি রাখে না, শুধু ডাটার চাবি (Key/ID) কপি করে রাখে।

- **বৈশিষ্ট্য:** যদি কেউ ডাটা **আপডেট** করে, আপনি তা দেখবেন। কিন্তু কেউ **নতুন ডাটা (Insert)** দিলে আপনি তা দেখবেন না, কারণ আপনার কাছে নতুন চাবি নেই।

### কোড উদাহরণ (Code Example)

SQL-এ শুধু `DECLARE` করার সময় টাইপ বলে দিতে হয়। বাকি সব নিয়ম (Open, Fetch, Close) একই থাকে।



``` SQL
-- ১. Static Cursor (Snapshot)
DECLARE cur_Static CURSOR STATIC FOR
SELECT Name FROM Employee;

-- ২. Dynamic Cursor (Real-time)
DECLARE cur_Dynamic CURSOR DYNAMIC FOR
SELECT Name FROM Employee;

-- ৩. Fast_Forward Cursor (Super Fast & Default)
DECLARE cur_Fast CURSOR FAST_FORWARD FOR
SELECT Name FROM Employee;
```

আপনার জন্য প্রশ্ন:

ধরুন, আপনি একটি রিপোর্ট বানাচ্ছেন যেখানে ডাটা খুবই দ্রুত পড়া দরকার এবং আপনার পেছনে ফিরে (Previous Row-তে) যাওয়ার কোনো দরকার নেই। সেক্ষেত্রে ওপরের ৩টির মধ্যে কোন "চামচটি" বা কার্সরটি বেছে নেওয়া সবচেয়ে বুদ্ধিমানের কাজ হবে? 🤔


____
দারুণ নির্বাচন! হাতে-কলমে কোড রান করে দেখাটাই শেখার সেরা উপায়। 👨‍💻

আগের প্রশ্নের উত্তরটা দিয়ে নিই—রিপোর্টের জন্য **Fast_Forward Cursor**-ই সেরা, কারণ এটি দ্রুত কাজ করে এবং মেমোরি কম খায়।

চলুন, এবার একটি পূর্ণাঙ্গ কোড দেখি। এখানে আমরা একটি ছোট টেবিল বানিয়ে সেখানে কার্সর চালিয়ে এক এক করে ডাটা পড়ব। আপনি এই কোডটি কপি করে সরাসরি SQL Server-এ রান করতে পারেন।

### 💻 কার্সর প্র্যাকটিস কোড



``` sql
-- ধাপ ১: প্র্যাকটিসের জন্য একটি অস্থায়ী টেবিল ও কিছু ডাটা তৈরি
CREATE TABLE #MyProducts (ID INT, ProductName VARCHAR(50));
INSERT INTO #MyProducts VALUES (1, 'Laptop'), (2, 'Smart Watch'), (3, 'Headphone');

-- ডাটা রাখার জন্য ভেরিয়েবল
DECLARE @PName VARCHAR(50);

-- ধাপ ২: কার্সর ঘোষণা (Fast_Forward ব্যবহার করছি স্পিডের জন্য)
DECLARE product_cursor CURSOR FAST_FORWARD FOR
SELECT ProductName FROM #MyProducts;

-- ধাপ ৩: কার্সর খোলা (মেমোরি লোড)
OPEN product_cursor;

-- ধাপ ৪: প্রথম ডাটা বা রো তুলে আনা
FETCH NEXT FROM product_cursor INTO @PName;

-- ধাপ ৫: লুপ চালানো (যতক্ষণ ডাটা পাওয়া যাবে)
WHILE @@FETCH_STATUS = 0
BEGIN
    -- বর্তমান ডাটা দিয়ে কাজ করা (আমরা শুধু প্রিন্ট করছি)
    PRINT 'Processing Item: ' + @PName;
    
    -- ⚠️ গুরুত্বপূর্ণ: পরবর্তী ডাটা বা রো তুলে আনা
    FETCH NEXT FROM product_cursor INTO @PName;
END

-- ধাপ ৬: সবশেষে কার্সর বন্ধ করা ও মুছে ফেলা
CLOSE product_cursor;
DEALLOCATE product_cursor;

-- প্র্যাকটিস শেষে টেবিল মুছে ফেলা
DROP TABLE #MyProducts;
```

আউটপুট:

কোডটি রান করলে আপনি Messages ট্যাবে দেখতে পাবেন:

- Processing Item: Laptop
    
- Processing Item: Smart Watch
    
- Processing Item: Headphone
    

---

এবার একটু চিন্তা করুন: 🧠

কোডের WHILE লুপের ভেতরে দেখুন আমরা PRINT করার পর আবার FETCH NEXT লাইনটি লিখেছি।

যদি আমরা লুপের ভেতরের ওই **দ্বিতীয় `FETCH NEXT` লাইনটি** লিখতে ভুলে যেতাম, তাহলে প্রোগ্রামটি রান করার পর কী ঘটত বলে আপনার মনে হয়?


___

## **Dynamic SQL** হলো SQL Server-এর **"জাদুকরী কাস্টমাইজেশন টুল"**! 🎩 এটা অনেকটা "Blank Cheque" (ফাঁকা চেক) এর মতো—আপনি যা ইচ্ছে লিখে ক্যাশ করতে পারেন।

বিষয়টি সহজ এবং মজার একটি উদাহরণের মাধ্যমে দেখা যাক:

### 🍔 উদাহরণ: রেস্টুরেন্ট অর্ডার

১. Static SQL (ফিক্সড মেনু):

আপনি ওয়েটারকে বললেন: "আমাকে এক প্লেট কাচ্চি দাও।"

এখানে অর্ডার ফিক্সড। আপনি চাইলেও রান্নার মাঝখানে বলতে পারবেন না যে "আলু দিও না"।

২. Dynamic SQL (কাস্টম অর্ডার):

আপনি ওয়েটারকে বললেন: "আমি একটা কাগজ দিচ্ছি। ওখানে যা লেখা থাকবে, তাই রান্না করে আনবে।"

রান্নার ঠিক আগ মুহূর্তে আপনি কাগজে লিখে দিলেন: "কাচ্চি + বোরহানি - আলু"।

ওয়েটার সেই কাগজ পড়ে তারপর রান্না বসাল। এটাই Dynamic SQL—যেখানে কোড আগে থেকে লেখা থাকে না, রান করার সময় তৈরি হয়।

---

আমরা এই বিষয়টি ৩টি ধাপে শিখব, যাতে আপনি জিরো থেকে হিরো হতে পারেন:

১. Basic: কীভাবে লেখে? (EXEC কমান্ড)

২. Danger: হ্যাকাররা কীভাবে বাঁশ দেয়? (SQL Injection - ভয়ংকর বিপদ! 💀)

৩. Advanced: বাঁশ থেকে বাঁচার উপায় (sp_executesql - সেফটি গার্ড 🛡️)।

___


**Dynamic SQL** লেখার সবচেয়ে সহজ ও আদিম উপায় হলো `EXEC` (বা `EXECUTE`) কমান্ড ব্যবহার করা।

এটাকে আমাদের রেস্টুরেন্ট উদাহরণের সাথে মিলিয়ে ভাবুন:

১. কাগজ (Variable): প্রথমে একটা ভেরিয়েবল নিতে হবে যেখানে আপনি কোডটি লিখবেন।

২. লেখা (String): সেই ভেরিয়েবলের ভেতর SQL কুয়েরিটি টেক্সট (String) হিসেবে লিখবেন।

৩. অর্ডার দেওয়া (Execution): সবশেষে EXEC বলে সেই ভেরিয়েবলটি চালিয়ে দেবেন।

নিচে একটি খুব সাধারণ উদাহরণ দেওয়া হলো:

SQL

``` sql
-- ১. কাগজ নেওয়া (ভেরিয়েবল ডিক্লেয়ার)
DECLARE @MyOrder NVARCHAR(MAX);

-- ২. কাগজে অর্ডার লেখা (কুয়েরি সেট করা)
-- খেয়াল করুন, পুরো কুয়েরিটা কিন্তু একটা টেক্সট বা String!
SET @MyOrder = 'SELECT * FROM Employee';

-- ৩. ওয়েটারকে কাগজ দেওয়া (কুয়েরি রান করা)
EXEC(@MyOrder);
```

এটা রান করলে SQL Server `Employee` টেবিলের সব ডাটা দেখাবে, ঠিক যেমনটা `SELECT * FROM Employee` লিখলে দেখাত।

আপনার জন্য প্রশ্ন: 🧠

ধরুন, আমরা এই কুয়েরিটাকে একটু ডাইনামিক করতে চাই। আমি চাই কুয়েরিটি শুধুমাত্র সেই এমপ্লয়িদের দেখাবে যাদের ID = 5।

তাহলে `SET @MyOrder = ...` এর লাইনে আপনি কোডটি কীভাবে লিখবেন? (উত্তরে শুধু ওই লাইনটি লিখলেই হবে)।

___
চমৎকার! হ্যাকিং বা **SQL Injection** বিষয়টি বোঝা খুবই জরুরি, বিশেষ করে যখন আপনি ডাইনামিক SQL ব্যবহার করছেন। এটা অনেকটা নিজের বাড়ির চাবি চোরের হাতে তুলে দেওয়ার মতো। 🏠🔓

চলুন আমাদের সেই **রেস্টুরেন্ট এনালজি** দিয়েই বিষয়টি বুঝি।

### 🍔 রেস্টুরেন্টে হ্যাকিং (Analogy)

মনে আছে? আপনি ওয়েটারকে একটা কাগজে লিখে দিয়েছিলেন: _"কাচ্চি + বোরহানি - আলু"_।

এখন ধরুন, একজন দুষ্টু কাস্টমার (হ্যাকার) কাগজে লিখল:

"এক গ্লাস পানি দাও; এবং ক্যাশ বাক্সের সব টাকা আমাকে দিয়ে দাও!" 😈

যেহেতু ওয়েটার (SQL Server) অন্ধভাবে কাগজে যা লেখা আছে তাই পালন করে (Dynamic SQL), সে পানিও দেবে আবার ক্যাশ বাক্সের টাকাও দিয়ে দেবে! এটাই **SQL Injection**।

---

### 💻 কোড দিয়ে হ্যাকিং (The Attack)

ধরুন, আপনার ওয়েবসাইটে লগিন করার জন্য নিচের মত একটি ডাইনামিক কুয়েরি লেখা আছে:

SQL

``` sql
DECLARE @UserName NVARCHAR(100);
DECLARE @Query NVARCHAR(MAX);

-- ১. হ্যাকার ইনপুট বক্সে এই অদ্ভুত লেখাটি লিখল:
SET @UserName = 'Admin'' OR ''1''=''1'; 

-- ২. আপনার কোড (ভুল পদ্ধতিতে লেখা)
SET @Query = 'SELECT * FROM Users WHERE Name = ''' + @UserName + '''';

-- ৩. চলুন দেখি আসলে কী কুয়েরি তৈরি হলো
PRINT @Query; -- আউটপুট: SELECT * FROM Users WHERE Name = 'Admin' OR '1'='1'

EXEC(@Query);
```

### ⚠️ বিপদটা কোথায়?

সাধারণত কুয়েরিটি চেক করে নাম 'Admin' কি না। কিন্তু হ্যাকার `OR '1'='1'` অংশটি জুড়ে দিয়েছে।

গণিতে `1 = 1` কথাটি **সবসময় সত্য (True)**।

আমার প্রশ্ন হলো: SQL-এ `OR` কন্ডিশন থাকলে এবং তার একপাশ যদি "সবসময় সত্য" (Always True) হয়, তাহলে ডাটাবেস কি শুধু 'Admin'-কে খুঁজবে, নাকি **টেবিলের সব ইউজারকে** ফেরত দিয়ে দেবে? আপনার কী মনে হয়? 🤔

___
স্বাগতম **সেফ জোন (Safe Zone)**-এ! 🛡️

`sp_executesql` হলো SQL Server-এর সেই স্মার্ট সিকিউরিটি গার্ড, যে ইনপুটকে কেবল **"ডাটা"** হিসেবে দেখে, **"কোড"** হিসেবে নয়।

### 🔒 এটি কীভাবে কাজ করে? (The Concept)

আগেরবার আমরা `EXEC` দিয়ে স্ট্রিং জোড়াতালি দিয়েছিলাম (String Concatenation), তাই হ্যাকার তার কোড ঢুকিয়ে দিতে পেরেছিল।

কিন্তু `sp_executesql` ব্যবহার করলে আমরা **"প্যারামিটার" (Parameter)** ব্যবহার করি।

- **আগে:** "নামের জায়গায় যা লেখা আছে, তাই এক্সিকিউট করো।"
    
- **এখন:** "নামের জায়গায় যা লেখা আছে, সেটা দিয়ে শুধুই **মানুষ খুঁজবে**। খবরদার! অন্য কোনো লজিক চালাবে না।"
    

### 💻 কোড দিয়ে দেখা যাক (The Solution)

নিচের কোডটি দেখুন। এখানে হ্যাকার আগের মতোই আক্রমণ করার চেষ্টা করছে, কিন্তু এবার আমরা `sp_executesql` ব্যবহার করছি।

SQL

``` sql
DECLARE @SQL NVARCHAR(MAX);
DECLARE @MyParams NVARCHAR(MAX);
DECLARE @HackerInput NVARCHAR(100);

-- হ্যাকার আবার সেই দুষ্টু ইনপুট দিল
SET @HackerInput = 'Admin'' OR ''1''=''1';

-- ১. কুয়েরি লিখলাম (কিন্তু ভ্যালু সরাসরি বসালাম না, একটা প্লেসহোল্ডার @Name দিলাম)
SET @SQL = N'SELECT * FROM Users WHERE Name = @Name';

-- ২. প্যারামিটার ডিফাইন করলাম (গার্ডকে চিনেয়ে দেওয়া যে @Name আসলে কী)
SET @MyParams = N'@Name NVARCHAR(100)';

-- ৩. নিরাপদে রান করা (sp_executesql)
EXEC sp_executesql @SQL, @MyParams, @Name = @HackerInput;
```

### 🧠 আপনার জন্য প্রশ্ন:

এই কোডটি রান করার পর SQL Server এখন `Users` টেবিলে কী খুঁজবে?

১. সে কি টেবিলের সব ডাটা দেখাবে (কারণ 1=1 সত্য)?

২. নাকি সে এমন একজন ইউজারকে খুঁজবে যার নাম আক্ষরিক অর্থেই "Admin' OR '1'='1"?

Temporary Table বা টেম্পোরারি টেবিল হলো SQL-এর "কাঁচা খাতা" বা "নোটপ্যাড"-এর মতো।

চলো একটা সহজ এবং মজার উদাহরণ দিয়ে বিষয়টা বুঝি।

মজার উদাহরণ (Funny Analogy): 🖐️

ধরুন আপনি পরীক্ষার হলে হাতের তালুতে কিছু সূত্র (Formula) লিখে নিয়ে গেলেন (যদিও এটা করা ঠিক না! 😉)। যতক্ষণ পরীক্ষা চলছে, ততক্ষণ ওটা আপনার কাজে লাগছে। কিন্তু পরীক্ষা শেষ হওয়ার পর আপনি হাত ধুয়ে ফেললেন, আর লেখাগুলো ভ্যানিশ!

Temporary Table-ও ঠিক তাই।

- **Permanent Table:** আপনার বাসার লকার, যেখানে জিনিস সবসময় থাকে।
    
- **Temporary Table:** আপনার হাতের তালু বা পকেটের চিরকুট। যতক্ষণ আপনি SQL Server-এ লগ-ইন করা আছেন (Session অন আছে), ততক্ষণ এটা থাকবে। উইন্ডো বন্ধ করলেই সব গায়েব!
    

কোড উদাহরণ (Code Example):

SQL-এ টেম্পোরারি টেবিল চেনার সবচেয়ে সহজ উপায় হলো এর নামের আগে একটা হ্যাশ (#) চিহ্ন থাকে।


```sql
-- ১. টেবিল বানানো (নামের আগে # চিহ্ন খেয়াল করুন)
CREATE TABLE #SecretNotes (
    NoteID int,
    SecretMessage varchar(100)
);

-- ২. কিছু গোপন তথ্য রাখা
INSERT INTO #SecretNotes VALUES (1, 'Boss is coming!');
INSERT INTO #SecretNotes VALUES (2, 'Hide the snacks!');

-- ৩. তথ্য দেখা
SELECT * FROM #SecretNotes;
```

এখন আপনার কাছে আমার একটা প্রশ্ন:

যদি আমরা এখন SQL-এর এই উইন্ডোটা (Session) বন্ধ করে দিই এবং আবার ওপেন করি, তাহলে কি `#SecretNotes` টেবিলটা আর খুঁজে পাওয়া যাবে? আপনার কী মনে হয়?

___
SQL-এ **Temporary Table** (অস্থায়ী টেবিল) হলো এমন একটি টেবিল যা আমরা অল্প সময়ের জন্য বা সাময়িক কোনো ক্যালকুলেশনের জন্য তৈরি করি। এটি ডেটাবেসে স্থায়ীভাবে সেভ হয় না।

সহজ করে বললে, এটি একটি **"রাফ খাতা"** (Rough Notebook)-এর মতো। যতক্ষণ তুমি কাজ করছ (Session চালু আছে), ততক্ষণ এটি থাকবে। কাজ শেষ করে ডেটাবেস কানেকশন বন্ধ করলে এটি অটোমেটিক মুছে যাবে।

চলো আমরা দুই ধরণের Temporary Table নিয়ে ধাপে ধাপে কাজ করি।

### ১. Local Temporary Table (লোকাল টেম্পোরারি টেবিল)

এটি শুধুমাত্র **তোমার বর্তমান উইন্ডো বা সেশনে** কাজ করবে। অন্য কেউ বা অন্য কোনো নতুন উইন্ডো থেকে এটি দেখা যাবে না। এর নামের আগে একটি হ্যাশ (`#`) চিহ্ন ব্যবহার করতে হয়।

**উদাহরণ ১:** ধরো, আমরা কিছু স্টুডেন্টের মার্কস নিয়ে সাময়িকভাবে কাজ করতে চাই।

```SQL
-- ১. টেবিল তৈরি (নামের আগে # চিহ্ন লক্ষ্য করো)
CREATE TABLE #StudentRough (
    StudentID INT,
    MathScore INT
);

-- ২. ডেটা প্রবেশ করানো
INSERT INTO #StudentRough (StudentID, MathScore)
VALUES (101, 85), (102, 90), (103, 78);

-- ৩. ডেটা দেখা
SELECT * FROM #StudentRough;
```

এই কোডটি রান করার পর তুমি টেবিলের ডেটা দেখতে পাবে।

এখন তোমার কাছে আমার একটি প্রশ্ন: তুমি যদি বর্তমান SQL উইন্ডোটি (Query Window) বন্ধ করে দিয়ে নতুন একটি উইন্ডো খোলো এবং `SELECT * FROM #StudentRough` কোডটি আবার রান করো, তাহলে কি টেবিলটি খুঁজে পাওয়া যাবে?
