### 🚫 **Lesson 6: নাল বনাম নট-নাল (NULL vs NOT NULL)**

**🗣️ সহজ বাংলা:**
সবার আগে বুঝতে হবে **NULL** জিনিসটা কী।
মনে রাখবে: `NULL` মানে **শূন্য (0)** না, `NULL` মানে **খালি স্ট্রিং ('')**-ও না।
`NULL` মানে হলো— **"আমি জানি না" (Unknown)** অথবা **"তথ্য নাই" (Missing Data)**।

টেবিল বানানোর সময় যদি কোনো কলামের পাশে `NOT NULL` লিখে দাও, তার মানে হলো—"মামা, এই ঘরে ডাটা তোমাকে দিতেই হবে, ফাঁকা রাখা চলবে না!"

**🤣 ফানি এনালজি (Real-life):**
*   **Zero (0):** তোমার পকেটে মানিব্যাগ আছে, কিন্তু টাকা নেই (০ টাকা)।
*   **NULL:** তোমার পকেটেই নাই! টাকা আছে কি নাই, সেটাই অজানা।

*আরেকটা উদাহরণ:* পরীক্ষার খাতায় কিছু লিখে ০ পাওয়া আর পরীক্ষা দিতে না আসা (Absence) এক জিনিস না। `Absence` হলো NULL।

**🎨 ASCII Table Example:**
Table: `Users`

| ID | Name (NOT NULL) | Phone (NULL allowed) |
| :--- | :--- | :--- |
| 1 | Rahim | 017... |
| 2 | Karim | **NULL** (ফোন নাই, সমস্যা নাই) |
| 3 | **ERROR!** | 018... |
*(৩ নম্বর রো ঢুকবে না, কারণ নাম ফাঁকা রাখা নিষেধ)*

**💻 SQL Example:**
```sql
CREATE TABLE Users (
    ID int PRIMARY KEY,
    UserName varchar(50) NOT NULL, -- নাম দিতেই হবে
    Email varchar(50) NULL         -- ইমেইল না দিলেও চলবে
);
```

**🤔 কখন/কেন ব্যবহার করব?**
*   যে তথ্যগুলো সিস্টেমের জন্য ক্রিটিকাল (যেমন: ইউজারনেম, পাসওয়ার্ড, জন্মতারিখ)—সেগুলোতে `NOT NULL` দিবে।
*   যেগুলো অপশনাল (যেমন: শখের নাম, দ্বিতীয় ফোন নম্বর)—সেগুলোতে `NULL` এলাউ করবে।

**✅ Best Practice:**
*   যত বেশি সম্ভব `NOT NULL` ব্যবহার করা ভালো। ডাটাবেসে `NULL` থাকলে কুয়েরি লিখতে গিয়ে মাঝে মাঝে ঝামেলা হয়।

**❌ Common Mistakes:**
*   ভাবা যে `NULL` এবং `0` একই জিনিস। এটা ডাটাবেস পাপ!

**🏆 Mini Practice Task:**
তোমার ফেসবুক প্রোফাইলের কথা ভাবো। `First Name`, `Last Name`, `Phone/Email`, `Bio` (নিজের সম্পর্কে)। এর মধ্যে কোনগুলো `NOT NULL` আর কোনগুলো `NULL` হবে?

### 🦄 **Lesson 7: ইউনিক কনস্ট্রেইন্ট (Unique Constraint)**

**🗣️ সহজ বাংলা:**
`Primary Key` এর ছোট ভাই হলো `Unique Key`।
এটার কাজ হলো—এই কলামে **ডুপ্লিকেট** ডাটা ঢুকতে দিবে না। সবাই আলাদা (Unique) হতে হবে।
পার্থক্য হলো: একটা টেবিলে `Primary Key` একটাই থাকে, কিন্তু `Unique Key` অনেকগুলো থাকতে পারে।

**🤣 ফানি এনালজি (Real-life):**
ক্লাসে "Roll Number" হলো **Primary Key** (সবার আলাদা, থাকতেই হবে)।
কিন্তু "Mobile Number" হলো **Unique Key**। দুইজনের মোবাইল নম্বর এক হতে পারবে না। তবে কারো মোবাইল না-ও থাকতে পারে (Null এলাউড)।

**🎨 ASCII Example:**
Table: `Employees`

| ID (PK) | Email (Unique) 🦄 |
| :--- | :--- |
| 1 | a@gmail.com |
| 2 | b@gmail.com |
| 3 | a@gmail.com ❌ |
*(৩ নম্বর রো এরর খাবে, কারণ `a@gmail.com` আগেই আছে)*

**💻 SQL Example:**
```sql
CREATE TABLE Employees (
    EmpID int PRIMARY KEY,
    PassportNo varchar(20) UNIQUE, -- দুইজনের পাসপোর্ট এক হবে না
    Email varchar(50) UNIQUE       -- দুইজনের ইমেইল এক হবে না
);
```

**🤔 কখন/কেন ব্যবহার করব?**
*   যখন চাইবে ডাটা রিপিট না হোক। যেমন: ইমেইল, ফোন নম্বর, এনআইডি কার্ড, ইউজারনেম।

**✅ Best Practice:**
*   ইউজারদের `Email` বা `Username` কলামে সবসময় `UNIQUE` কনস্ট্রেইন্ট বসাবে, যাতে দুইজন ইউজার এক ইমেইল দিয়ে রেজিস্টার করতে না পারে।

**🏆 Mini Practice Task:**
একটা `Voters` টেবিল চিন্তা করো। সেখানে `VoterID` (PK), `NID` (Unique), `FingerPrint` (Unique) হতে পারে কি না ভাবো।

### 👮 **Lesson 8: চেক কনস্ট্রেইন্ট (CHECK Constraint)**

**🗣️ সহজ বাংলা:**
ইনি হলেন ডাটাবেসের **সিকিউরিটি গার্ড**। গেট দিয়ে ঢোকার সময় ইনি চেক করবেন তোমার যোগ্যতা আছে কি না।
তুমি কন্ডিশন দিয়ে দিবে, যদি ডাটা সেই কন্ডিশন মানে, তবেই ঢুকবে। না মানলে—"ভাগো এখান থেকে!"

**🤣 ফানি এনালজি (Real-life):**
বিয়ের জন্য পাত্রের বয়স অন্তত ২১ হতে হবে।
যদি ১০ বছরের কেউ বিয়ে করতে আসে, কাজী সাহেব (Database) তাকে বের করে দিবেন। এটাই `CHECK (Age >= 21)`।

**🎨 ASCII Art Example:**

```text
Data: Age = 15  ----> [ CHECK (Age >= 18) ] ----> 🚫 STOP! (Error)
Data: Age = 25  ----> [ CHECK (Age >= 18) ] ----> ✅ PASS! (Saved)
```

**💻 SQL Example:**
```sql
CREATE TABLE Persons (
    ID int PRIMARY KEY,
    Name varchar(50),
    Age int CHECK (Age >= 18),  -- ১৮ এর নিচে ডাটা ঢুকবে না
    Salary int CHECK (Salary > 0) -- বেতন নেগেটিভ হতে পারে না
);
```

**🤔 কখন/কেন ব্যবহার করব?**
*   লজিক্যাল ভুল আটকানোর জন্য। যেমন: ডিসকাউন্ট পার্সেন্টেজ ১০০-র বেশি হতে পারে না, কারো জন্মতারিখ আজকের দিনের চেয়ে ফিউচারে হতে পারে না।

**✅ Best Practice:**
*   Constraint এর একটা সুন্দর নাম দেওয়া উচিত। যেমন: `CK_Age_Min18`। তাহলে এরর আসলে বুঝতে সুবিধা হয় কেন এরর দিচ্ছে।

**❌ Common Mistakes:**
*   এমন কন্ডিশন দেওয়া যেটা ফিউচারে পাল্টাতে পারে। যেমন `CHECK (Salary < 50000)`। পরে প্রমোশন হলে ডাটা আপডেট করতে পারবে না।

**🏆 Mini Practice Task:**
একটা `Product` টেবিলে `Price` কলাম আছে। সেখানে এমন একটা চেক বসাও যাতে কেউ ভুলে নেগেটিভ প্রাইস (-500 টাকা) না দিতে পারে।

### 🔑 **Lesson 9: প্রাইমারি কি - বস ইজ অলওয়েজ রাইট (Primary Key Revisited)**

**🗣️ সহজ বাংলা:**
আমরা লেসন ৩-এ `Primary Key (PK)` নিয়ে কথা বলেছিলাম। এখানে একটু গভীরে যাব।
PK মূলত দুইটা কাজ একসাথে করে: `UNIQUE` + `NOT NULL`।
অর্থাৎ, সে ফাঁকাও থাকবে না, আবার ডুপ্লিকেটও হবে না। একটা টেবিলে **শুধুমাত্র একটি** প্রাইমারি কি থাকতে পারে।

তবে, **Composite Primary Key** নামে একটা জিনিস আছে। যখন এক কলাম দিয়ে ইউনিক করা যায় না, তখন দুইটা কলাম মিলে একটা বস (PK) হয়।

**🤣 ফানি এনালজি (Real-life):**
তোমার বাসার তালা (PK)। একটা রুমের একটাই মেইন তালা থাকে।
**Composite PK:** ব্যাংকের লকার। কাস্টমারের চাবি + ম্যানেজারের চাবি—দুইটা একসাথে দিলেই লকার খোলে। একা একা কেউ খুলতে পারে না।

**💻 SQL Example (Composite PK):**
ধরো একটা ছাত্র একাধিক কোর্সে ভর্তি হতে পারে।
```sql
CREATE TABLE StudentCourses (
    StudentID int,
    CourseID int,
    PRIMARY KEY (StudentID, CourseID) -- দুইজন মিলে এক বস
);
```
*ব্যাখ্যা: ১ জন ছাত্র একই কোর্স দুইবার নিতে পারবে না। কিন্তু ১ জন ছাত্র আলাদা কোর্স নিতে পারবে।*

**🤔 কখন/কেন ব্যবহার করব?**
*   প্রতিটা টেবিলেই PK থাকতে হবে। এটা ছাড়া ডাটা খুঁজে বের করা খড়ের গাদায় সুঁচ খোঁজার মতো।

**🏆 Mini Practice Task:**
তোমার মোবাইল নম্বরের কন্টাক্ট লিস্টে PK কে হতে পারে? নাম? না (এক নামে বহু লোক)। ফোন নম্বর? হ্যাঁ।

### 🤝 **Lesson 10: ফরেন কি - ঘটক পাখি ভাই (Foreign Key)**

**🗣️ সহজ বাংলা:**
ডাটাবেসের আসল মজা এখানেই! একটা টেবিলের সাথে আরেকটা টেবিলের সম্পর্ক বা রিলেশন তৈরি করে যে, তাকে বলে **Foreign Key (FK)**।
FK হলো অন্য টেবিলের `Primary Key`-র রেফারেন্স। এটা এনশিওর করে যে, "বাপ না থাকলে ছেলে হবে না"। অর্থাৎ, প্যারেন্ট টেবিলে ডাটা না থাকলে চাইল্ড টেবিলে সেই ডাটা ঢুকবে না।

**🤣 ফানি এনালজি (Real-life):**
এটা হলো **ভিসা স্পন্সরশিপ**।
আমেরিকায় (Child Table) তুমি তখনই যেতে পারবে যদি তোমার স্পন্সর (Parent Table) এর ডাটা ভ্যালিড থাকে। স্পন্সর যদি না থাকে বা মরে যায়, তোমার ভিসাও বাতিল (বা ঢুকতেই দিবে না)।

**🎨 ASCII Schema:**

```text
[ Customers Table ] (Parent)      [ Orders Table ] (Child)
+----+-------+                    +-----+----------+-----------+
| ID | Name  | <---(Link)-------  | OID | Product  | CustomerID| (FK)
+----+-------+                    +-----+----------+-----------+
|  1 | Rahim |                    | 101 | Laptop   |     1     | ✅
|  2 | Karim |                    | 102 | Mouse    |     5     | ❌ Error!
+----+-------+                    +-----+----------+-----------+
```
*(অর্ডার টেবিলে কাস্টমার আইডি ৫ ঢুকবে না, কারণ কাস্টমার টেবিলে আইডি ৫ নামে কেউ নাই)*

**💻 SQL Example:**
```sql
-- বাপ টেবিল
CREATE TABLE Customers (
    CustomerID int PRIMARY KEY,
    Name varchar(50)
);

-- ছেলে টেবিল
CREATE TABLE Orders (
    OrderID int PRIMARY KEY,
    OrderDate datetime,
    CustomerID int, -- এই কলামটা লিংক হবে
    FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID)
);
```

**🤔 কখন/কেন ব্যবহার করব?**
*   যখনই দুইটা টেবিলের মধ্যে সম্পর্ক থাকবে। যেমন: কোন কাস্টমার কোন অর্ডার দিয়েছে, কোন স্টুডেন্ট কোন ডিপার্টমেন্টে পড়ে।
*   এটা **Orphan Record** (এতিম ডাটা) আটকাতে সাহায্য করে।

**✅ Best Practice:**
*   FK ব্যবহার করলে ডাটাবেস স্লো হতে পারে যদি ইনডেক্স না থাকে (এটা আমরা পরে শিখব)। কিন্তু ডাটার শুদ্ধতার জন্য এটা মাস্ট।

**❌ Common Mistakes:**
*   আগে Child Table ডিলিট না করে Parent Table ডিলিট করতে যাওয়া। ডাটাবেস এরর দিবে "Reference Constraint Violation"। আগে অর্ডার মুছতে হবে, তারপর কাস্টমার।

**🏆 Mini Practice Task:**
খাতায় দুইটি বক্স আঁকো। ১. `Department` (DeptID, DeptName), ২. `Student` (ID, Name, DeptID).
তীর চিহ্ন দিয়ে দেখাও কে কাকে রেফার করছে। এখানে `Student` টেবিলের `DeptID` হলো Foreign Key.
