### ১. Strategy Design Pattern (স্ট্র্যাটেজি প্যাটার্ন)

**এটি কী:**
স্ট্র্যাটেজি প্যাটার্ন হলো এমন একটি টেকনিক যার মাধ্যমে আপনি রানটাইমে (অ্যাপ চলাকালীন) কোনো কাজের লজিক বা অ্যালগরিদম পরিবর্তন করতে পারেন।

**সহজ উদাহরণ (Google Maps):**
মনে করুন আপনি গুগল ম্যাপ ব্যবহার করছেন। গন্তব্যে যাওয়ার জন্য আপনি **গাড়ি**, **বাইক**, বা **পায়ে হাঁটা** সিলেক্ট করতে পারেন। গন্তব্য একই, কিন্তু যাওয়ার পদ্ধতি (Strategy) আলাদা।

**কোড উদাহরণ:**
ধরুন, আমরা একটি পেমেন্ট সিস্টেম বানাব। ইউজার **Bkash** বা **Nagad** দিয়ে পেমেন্ট করতে পারে।

```csharp
// ১. ইন্টারফেস (কন্ট্রাক্ট)
public interface IPaymentStrategy
{
    void Pay(double amount);
}

// ২. আলাদা আলাদা স্ট্র্যাটেজি
public class BkashPayment : IPaymentStrategy
{
    public void Pay(double amount) => Console.WriteLine($"Paid {amount} via Bkash.");
}

public class NagadPayment : IPaymentStrategy
{
    public void Pay(double amount) => Console.WriteLine($"Paid {amount} via Nagad.");
}

// ৩. কনটেক্সট (যে এটি ব্যবহার করবে)
public class Order
{
    private readonly IPaymentStrategy _paymentStrategy;

    // কনস্ট্রাক্টরে আমরা ইন্টারফেস নিচ্ছি (লজিক নয়)
    public Order(IPaymentStrategy paymentStrategy)
    {
        _paymentStrategy = paymentStrategy;
    }

    public void ProcessOrder(double amount)
    {
        _paymentStrategy.Pay(amount);
    }
}
```

**কেন এটি কাজ করে:**
*   আমরা `Order` ক্লাসের ভেতর `if (type == "Bkash")` জাতীয় কোড লিখিনি।
*   ভবিষ্যতে "Rocket" যোগ করতে হলে `Order` ক্লাস এডিট করতে হবে না (OCP - Open/Closed Principle)।

**বাস্তব ব্যবহার:**
*   বিভিন্ন ফরম্যাটে ডেটা এক্সপোর্ট করা (PDF, Excel, CSV)।
*   বিভিন্ন ডিসকাউন্ট লজিক অ্যাপ্লাই করা।

### ২. Abstract Factory Design Pattern (অ্যাবস্ট্রাক্ট ফ্যাক্টরি প্যাটার্ন)

**এটি কী:**
এটি এমন একটি প্যাটার্ন যা **সম্পর্কিত (Related) অবজেক্টের ফ্যামিলি** তৈরি করতে সাহায্য করে। এটি আপনাকে নির্দিষ্ট ক্লাসের নাম না জেনেই অবজেক্ট তৈরি করতে দেয়।

**সহজ উদাহরণ (ফার্নিচার দোকান):**
আপনি যদি **"Modern"** স্টাইলের ফার্নিচার চান, তবে আপনি মডার্ন চেয়ার এবং মডার্ন টেবিল পাবেন। যদি **"Victorian"** চান, তবে ভিক্টোরিয়ান চেয়ার ও টেবিল পাবেন। মডার্ন চেয়ারের সাথে ভিক্টোরিয়ান টেবিল মানাবে না। অ্যাবস্ট্রাক্ট ফ্যাক্টরি নিশ্চিত করে যে আপনি সঠিক সেট বা ফ্যামিলি পাচ্ছেন।

**কোড উদাহরণ:**

```csharp
// ১. ইন্টারফেস
public interface IVehicleFactory
{
    ICar CreateCar();
    IBike CreateBike();
}

// ২. কনক্রিট ফ্যাক্টরি (Honda ফ্যামিলি)
public class HondaFactory : IVehicleFactory
{
    public ICar CreateCar() => new HondaCivic();
    public IBike CreateBike() => new HondaCBR();
}

// ৩. কনক্রিট ফ্যাক্টরি (Toyota ফ্যামিলি)
public class ToyotaFactory : IVehicleFactory
{
    public ICar CreateCar() => new ToyotaCorolla();
    public IBike CreateBike() => new ToyotaR15(); // (কাল্পনিক)
}
```

**সমস্যা ও সমাধান:**
*   **সমস্যা:** যদি ইন্টারফেস অনেক বড় হয়ে যায় (যেমন ফ্যাক্টরিতে ১০ রকমের মেথড থাকে), তবে নতুন কিছু যোগ করা কঠিন হয় (Interface Segregation Principle ভাঙ্গে)।
*   **সমাধান:** ফ্যাক্টরি ছোট রাখুন। প্রয়োজন হলে একাধিক ছোট ফ্যাক্টরি তৈরি করুন।

**বাস্তব ব্যবহার:**
*   ক্রস-প্ল্যাটফর্ম UI (Windows-এ উইন্ডোজ বাটন, Mac-এ ম্যাক বাটন তৈরি করা)।
*   ডাটাবেস কানেকশন (SQL Server ফ্যামিলি বনাম Oracle ফ্যামিলি)।

### ৩. Singleton Design Pattern (সিঙ্গেলটন প্যাটার্ন)

**এটি কী:**
সিঙ্গেলটন প্যাটার্ন নিশ্চিত করে যে একটি ক্লাসের **পুরো অ্যাপ্লিকেশনে মাত্র একটিই ইনস্ট্যান্স (Instance/Object)** থাকবে এবং সেটি গ্লোবালি অ্যাক্সেস করা যাবে।

**কেন এটি কাজ করে:**
কিছু জিনিস অ্যাপে একবারই তৈরি হওয়া উচিত। যেমন: কনফিগারেশন লোডার বা ডাটাবেস কানেকশন পুল। বারবার তৈরি করলে মেমোরি নষ্ট হবে।

**সনাতন (Old) পদ্ধতি এবং সমস্যা:**
আগে আমরা `static` ভেরিয়েবল এবং `private constructor` ব্যবহার করে সিঙ্গেলটন বানাতাম।

```csharp
// ❌ এটি এখনকার দিনে Anti-pattern বা খারাপ প্র্যাকটিস হিসেবে ধরা হয়
public class DatabaseService
{
    private static DatabaseService _instance;
    private DatabaseService() { } // প্রাইভেট কনস্ট্রাক্টর

    public static DatabaseService Instance 
    {
        get 
        {
            if (_instance == null) _instance = new DatabaseService();
            return _instance;
        }
    }
}
```

**সমস্যা (Code Smell - Ambient Context):**
*   **Tightly Coupled:** আপনি যখন কোডের মধ্যে `DatabaseService.Instance.Save()` লিখবেন, তখন সেই কোডটি `DatabaseService`-এর ওপর পুরোপুরি নির্ভরশীল হয়ে যায়।
*   **Unit Testing:** স্ট্যাটিক গ্লোবাল অবজেক্ট হওয়ার কারণে এটি টেস্ট করা খুব কঠিন (Mock করা যায় না)।

**সমাধান (আধুনিক .NET পদ্ধতি):**
আমরা এখন ম্যানুয়ালি সিঙ্গেলটন কোড লিখি না। আমরা **Dependency Injection (DI)** কন্টেইনার ব্যবহার করি।

```csharp
// ✅ সঠিক উপায়: Program.cs ফাইলে লাইফটাইম বলে দেওয়া
builder.Services.AddSingleton<IDatabaseService, DatabaseService>();
```
এতে ASP.NET Core নিজেই নিশ্চিত করবে যে `DatabaseService`-এর একটিই কপি তৈরি হবে এবং যেখানে প্রয়োজন সেখানে ইনজেক্ট করবে।

### অধ্যায়ের সারসংক্ষেপ (Summary of Key Points)

১. **Strategy Pattern:** এটি `if-else` বা `switch` স্টেটমেন্ট দূর করে এবং রানটাইমে অ্যালগরিদম বদলানোর সুবিধা দেয়। এটি **OCP (Open/Closed Principle)** মেনে চলতে সাহায্য করে।

২. **Abstract Factory:** এটি সম্পর্কিত অবজেক্টের গ্রুপ বা ফ্যামিলি তৈরি করতে ব্যবহৃত হয়। এটি কোডকে নির্দিষ্ট ক্লাস থেকে মুক্ত রাখে (Loose Coupling)।

৩. **Singleton Pattern:** এটি নিশ্চিত করে একটি ক্লাসের একটাই অবজেক্ট থাকবে। তবে ম্যানুয়ালি `static` দিয়ে সিঙ্গেলটন বানানো এখন **Anti-pattern**। এর বদলে .NET-এর **DI Container (AddSingleton)** ব্যবহার করা উচিত।

এই প্যাটার্নগুলো আয়ত্ত করলে আপনি বুঝতে পারবেন কিভাবে কোডকে মডুলার এবং ফ্লেক্সিবল করা যায়, যা পরবর্তী অধ্যায়ের **Dependency Injection** বোঝার জন্য অত্যন্ত জরুরি।

### ২. Strategy Design Pattern (স্ট্র্যাটেজি প্যাটার্ন)

**সমস্যা (Scenario):**
ধরুন আমরা একটি ই-কমার্স সাইটের শিপিং কস্ট (Shipping Cost) ক্যালকুলেট করতে চাই। আমাদের দুই ধরনের শিপিং আছে:
১. **FedEx** (খরচ: ১০ টাকা)
২. **DHL** (খরচ: ২০ টাকা)

**সাধারণ কোড (ভুল পদ্ধতি):**
```csharp
public double CalculateShipping(string carrier)
{
    if (carrier == "FedEx") return 10.0;
    else if (carrier == "DHL") return 20.0;
    return 0;
}
```
*সমস্যা:* ভবিষ্যতে যদি আরও ১০টা কোম্পানি যোগ হয়, এই `if-else` অনেক বড় হয়ে যাবে।

**সমাধান (Strategy Pattern):**
আমরা প্রতিটা অ্যালগরিদমকে আলাদা ক্লাসে ভাগ করে ফেলব।

```csharp
// ১. ইন্টারফেস (Strategy)
public interface IShippingStrategy
{
    double CalculateCost();
}

// ২. কনক্রিট স্ট্র্যাটেজি (FedEx)
public class FedExShipping : IShippingStrategy
{
    public double CalculateCost() => 10.0;
}

// ৩. কনক্রিট স্ট্র্যাটেজি (DHL)
public class DHLShipping : IShippingStrategy
{
    public double CalculateCost() => 20.0;
}

// ৪. কনটেক্সট (Context)
public class ShippingContext
{
    private IShippingStrategy _strategy;

    // রানটাইমে স্ট্র্যাটেজি সেট করার মেথড
    public void SetStrategy(IShippingStrategy strategy)
    {
        _strategy = strategy;
    }

    public double ExecuteCalculation()
    {
        return _strategy.CalculateCost();
    }
}

// ব্যবহার (Program.cs):
var context = new ShippingContext();

// FedEx সিলেক্ট করলাম
context.SetStrategy(new FedExShipping());
Console.WriteLine($"Cost: {context.ExecuteCalculation()}"); // Output: 10

// DHL সিলেক্ট করলাম (রানটাইমে পরিবর্তন)
context.SetStrategy(new DHLShipping());
Console.WriteLine($"Cost: {context.ExecuteCalculation()}"); // Output: 20
```

**কেন এটি জরুরি:** এটি **OCP (Open/Closed Principle)** মেনে চলে। নতুন কোম্পানি যোগ করতে হলে আমাদের `ShippingContext` ক্লাসে হাত দিতে হবে না, শুধু নতুন ক্লাস বানালেই হবে।

### ৩. Abstract Factory Design Pattern

**সমস্যা (Scenario):**
মনে করুন আপনি একটি গেম বানাচ্ছেন। গেমে দুটি থিম আছে: **Fantasy** এবং **SciFi**।
*   Fantasy থিমে থাকবে: Sword (অস্ত্র) এবং Horse (বাহন)।
*   SciFi থিমে থাকবে: LaserGun (অস্ত্র) এবং Spaceship (বাহন)।

আপনি চান না যে SciFi গেমে কেউ ভুল করে Sword ব্যবহার করুক। অর্থাৎ, **Related Objects** একসাথে তৈরি হতে হবে।

**সমাধান (Abstract Factory):**

```csharp
// ১. প্রোডাক্ট ইন্টারফেস
public interface IWeapon { void Attack(); }
public interface IVehicle { void Drive(); }

// ২. কনক্রিট প্রোডাক্টস (Fantasy)
public class Sword : IWeapon { public void Attack() => Console.WriteLine("Swinging Sword!"); }
public class Horse : IVehicle { public void Drive() => Console.WriteLine("Riding Horse!"); }

// ৩. কনক্রিট প্রোডাক্টস (SciFi)
public class LaserGun : IWeapon { public void Attack() => Console.WriteLine("Shooting Laser!"); }
public class Spaceship : IVehicle { public void Drive() => Console.WriteLine("Flying Spaceship!"); }

// ৪. অ্যাবস্ট্রাক্ট ফ্যাক্টরি ইন্টারফেস
public interface IGameFactory
{
    IWeapon CreateWeapon();
    IVehicle CreateVehicle();
}

// ৫. কনক্রিট ফ্যাক্টরি (Fantasy)
public class FantasyFactory : IGameFactory
{
    public IWeapon CreateWeapon() => new Sword();
    public IVehicle CreateVehicle() => new Horse();
}

// ৬. কনক্রিট ফ্যাক্টরি (SciFi)
public class SciFiFactory : IGameFactory
{
    public IWeapon CreateWeapon() => new LaserGun();
    public IVehicle CreateVehicle() => new Spaceship();
}

// ৭. ক্লায়েন্ট কোড (Client)
public class Game
{
    private readonly IWeapon _weapon;
    private readonly IVehicle _vehicle;

    public Game(IGameFactory factory)
    {
        _weapon = factory.CreateWeapon();
        _vehicle = factory.CreateVehicle();
    }

    public void Play()
    {
        _vehicle.Drive();
        _weapon.Attack();
    }
}

// ব্যবহার (Program.cs):
IGameFactory factory = new FantasyFactory(); // অথবা SciFiFactory
var game = new Game(factory);
game.Play();
```

**কেন এটি জরুরি:** এটি নিশ্চিত করে যে একটি নির্দিষ্ট থিমের সব অবজেক্ট একে অপরের সাথে সামঞ্জস্যপূর্ণ।

### ৪. Singleton Design Pattern

**সমস্যা (Scenario):**
আমাদের অ্যাপে একটি `ConfigurationManager` ক্লাস আছে যা ফাইল থেকে কনফিগারেশন লোড করে। আমরা চাই না প্রতিবার এটি নতুন করে তৈরি হোক, কারণ ফাইল রিড করা সময়সাপেক্ষ। আমরা চাই পুরো অ্যাপে এর একটাই কপি (Instance) থাকুক।

**সমাধান ১: ম্যানুয়াল সিঙ্গেলটন (Old Way - Not Recommended in Modern .NET):**
```csharp
public class ConfigurationManager
{
    private static ConfigurationManager _instance;
    private ConfigurationManager() { } // প্রাইভেট কনস্ট্রাক্টর

    public static ConfigurationManager Instance
    {
        get
        {
            if (_instance == null)
            {
                _instance = new ConfigurationManager();
            }
            return _instance;
        }
    }
}
```
*সমস্যা:* এটি থ্রেড-সেফ (Thread-safe) নয় এবং টেস্টিং করা কঠিন। বইটিতে একে **Anti-pattern** বলা হয়েছে।

**সমাধান ২: ডিপেন্ডেন্সি ইনজেকশন (Modern Way - Recommended):**
আধুনিক .NET-এ আমরা কন্টেইনার ব্যবহার করি। আমরা শুধু `Program.cs`-এ বলে দিই যে এই সার্ভিসটি সিঙ্গেলটন হবে।

```csharp
// Program.cs (ASP.NET Core বা DI কন্টেইনারে)
builder.Services.AddSingleton<IConfigurationManager, ConfigurationManager>();
```
*কেন ভালো:* ফ্রেমওয়ার্ক নিজেই নিশ্চিত করবে যে এর একটিই কপি তৈরি হয়েছে। আমাদের কোডে কোনো জটিল লজিক লিখতে হবে না।

### ৫. অধ্যায়ের সারসংক্ষেপ (Summary)

এই অধ্যায় থেকে আমরা যা শিখলাম:

1.  **Strategy Pattern:** এটি আমাদের `If-Else` এর জটিলতা থেকে মুক্তি দেয় এবং রানটাইমে লজিক পরিবর্তনের ক্ষমতা দেয়।
2.  **Abstract Factory:** এটি সম্পর্কিত অবজেক্টগুলোর ফ্যামিলি তৈরি করতে সাহায্য করে, যাতে ভুল কম্বিনেশন তৈরি না হয়।
3.  **Singleton Pattern:** এটি গ্লোবাল অবজেক্ট ম্যানেজ করতে সাহায্য করে। তবে ম্যানুয়ালি না করে **Dependency Injection Container** ব্যবহার করা আধুনিক এবং নিরাপদ পদ্ধতি।

এই প্যাটার্নগুলো ব্যবহার করলে আপনার কোড হবে **Flexible (নমনীয়)**, **Testable (পরীক্ষাযোগ্য)** এবং **Maintainable (রক্ষণাবেক্ষণযোগ্য)**।
