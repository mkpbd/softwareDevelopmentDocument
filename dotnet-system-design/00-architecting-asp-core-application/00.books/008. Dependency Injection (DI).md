এটি আধুনিক .NET এবং ASP.NET Core-এর **হৃদপিণ্ড**। আপনি যদি এই চ্যাপ্টারটি ভালোভাবে না বোঝেন, তবে প্রফেশনাল লেভেলের অ্যাপ্লিকেশন বানানো প্রায় অসম্ভব। এই অধ্যায়টি আমাদের শেখায় কিভাবে কোডকে **Loosely Coupled** (একে অপরের ওপর কম নির্ভরশীল) রাখা যায়।

আসুন, প্রতিটি টপিক খুব সহজ বাংলায় বুঝে নিই।

### ১. Dependency Injection (DI) এবং Inversion of Control (IoC)

**এটি কী:**
সোজা কথায়, DI হলো এমন একটি পদ্ধতি যেখানে আপনার ক্লাস তার প্রয়োজনীয় অবজেক্টগুলো (Dependencies) নিজে তৈরি করে না (`new` কিওয়ার্ড দিয়ে), বরং বাইরে থেকে (কন্টেইনার থেকে) চেয়ে নেয়।

**কেন এটি কাজ করে:**
সাধারণত ক্লাস `A` যদি ক্লাস `B`-কে ব্যবহার করে, তবে `A` নিজেই `B`-কে তৈরি করে। কিন্তু DI ব্যবহার করলে, আমরা এই নিয়ন্ত্রণটি উল্টে দিই (Inversion of Control)। এখন `A` জানে না `B` কিভাবে তৈরি হলো, সে শুধু `B`-কে ব্যবহার করে।

**বাস্তব উদাহরণ:**
মনে করুন আপনি পিৎজা খেতে চান।
*   **DI ছাড়া:** আপনি নিজে বাজারে গিয়ে ময়দা, চিজ কিনলেন, তারপর পিৎজা বানালেন। (কঠিন এবং সময়সাপেক্ষ)।
*   **DI সহ:** আপনি পিৎজা শপে অর্ডার দিলেন, ডেলিভারি বয় এসে পিৎজা দিয়ে গেল। আপনি জানেন না পিৎজাটা কিভাবে বানানো হয়েছে, আপনি শুধু খাচ্ছেন।

**কোড উদাহরণ:**

**খারাপ পদ্ধতি (Control Freak - নিজে তৈরি করা):**
```csharp
public class OrderService
{
    public void PlaceOrder()
    {
        // সমস্যা: এখানে আমরা 'new' ব্যবহার করে ইমেইল সার্ভিস তৈরি করছি
        var emailSender = new EmailSender(); 
        emailSender.Send("Order Placed");
    }
}
```

**ভালো পদ্ধতি (DI - বাইরে থেকে নেওয়া):**
```csharp
public class OrderService
{
    private readonly IEmailSender _emailSender;

    // কনস্ট্রাক্টরের মাধ্যমে ডিপেন্ডেন্সি চাওয়া হচ্ছে
    public OrderService(IEmailSender emailSender)
    {
        _emailSender = emailSender;
    }

    public void PlaceOrder()
    {
        _emailSender.Send("Order Placed");
    }
}
```

### ২. The IoC Container (Composition Root)

**এটি কী:**
IoC কন্টেইনার হলো একটি জাদুর বক্স (ASP.NET Core-এ `IServiceProvider`), যা জানে কোন ইন্টারফেসের জন্য কোন ক্লাসটি তৈরি করতে হবে। আমরা অ্যাপ্লিকেশনের শুরুতে (`Program.cs` ফাইলে) সব সার্ভিস রেজিস্টার করি। একে **Composition Root** বলা হয়।

**কেন এটি গুরুত্বপূর্ণ:**
এটি আমাদের পুরো অ্যাপ্লিকেশনের সব অবজেক্ট তৈরি এবং ম্যানেজ করার দায়িত্ব নেয়। আমাদের হাতে ধরে অবজেক্ট বানাতে হয় না।

**কোড উদাহরণ (Program.cs):**
```csharp
var builder = WebApplication.CreateBuilder(args);

// কন্টেইনারকে বলে দেওয়া হচ্ছে: কেউ যদি IEmailSender চায়, তাকে EmailSender দিও।
builder.Services.AddTransient<IEmailSender, EmailSender>(); 

var app = builder.Build();
```

### ৩. Object Lifetimes (অবজেক্টের আয়ুষ্কাল)

ASP.NET Core-এ সার্ভিস রেজিস্টার করার সময় ৩টি লাইফটাইম বা আয়ুষ্কাল নির্ধারণ করা যায়। এটি এই চ্যাপ্টারের সবচেয়ে গুরুত্বপূর্ণ অংশ।

#### ক. Transient
*   **কী:** প্রতিবার যখনই সার্ভিসটি চাওয়া হবে, কন্টেইনার **নতুন একটি কপি** তৈরি করে দেবে।
*   **কখন ব্যবহার করবেন:** হালকা এবং স্টেটলেস সার্ভিসের জন্য।
*   **কোড:** `builder.Services.AddTransient<IService, Service>();`

#### খ. Scoped
*   **কী:** একটি **HTTP Request**-এর জন্য একবারই তৈরি হবে। ওই রিকোয়েস্টের মধ্যে যতবার চাওয়া হবে, একই অবজেক্ট পাওয়া যাবে। রিকোয়েস্ট শেষ হলে অবজেক্ট ধ্বংস হয়ে যাবে।
*   **কখন ব্যবহার করবেন:** ডাটাবেস কানেকশন (`DbContext`) বা ইউজারের তথ্য রাখার জন্য।
*   **কোড:** `builder.Services.AddScoped<IService, Service>();`

#### গ. Singleton
*   **কী:** অ্যাপ্লিকেশন চালু হওয়ার পর **প্রথমবার** তৈরি হবে এবং অ্যাপ্লিকেশন বন্ধ না হওয়া পর্যন্ত **একই অবজেক্ট** সবাই ব্যবহার করবে।
*   **কখন ব্যবহার করবেন:** ক্যাশিং সার্ভিস বা কনফিগারেশন সার্ভিসের জন্য।
*   **কোড:** `builder.Services.AddSingleton<IService, Service>();`

**সমস্যা ও সমাধান:**
*   *সমস্যা:* আপনি যদি একটি `Singleton` সার্ভিসের ভেতরে `Scoped` সার্ভিস ইনজেক্ট করেন, তবে `Scoped` সার্ভিসটি `Singleton` হয়ে যাবে (Captive Dependency)। এটি মেমোরি লিক করতে পারে।
*   *সমাধান:* সবসময় ছোট লাইফটাইমের মধ্যে বড় লাইফটাইম ইনজেক্ট করবেন, উল্টোটা নয়।

### ৪. Code Smell: Service Locator Pattern

**এটি কী:**
এটি একটি অ্যান্টি-প্যাটার্ন (Anti-pattern)। যখন আমরা কনস্ট্রাক্টরে ডিপেন্ডেন্সি না চেয়ে, মেথডের ভেতরে সরাসরি কন্টেইনারকে ডাকি সার্ভিসটি দেওয়ার জন্য।

**কেন এটি খারাপ:**
এটি ডিপেন্ডেন্সি লুকিয়ে রাখে। কোড দেখে বোঝা যায় না এই ক্লাসের আসলে কী কী দরকার। এবং এটি ইউনিট টেস্টিং করা খুব কঠিন করে তোলে।

**কোড উদাহরণ (এটি করবেন না):**
```csharp
public void DoWork(IServiceProvider provider)
{
    // খারাপ: সরাসরি কন্টেইনার থেকে সার্ভিস খোঁজা হচ্ছে
    var service = provider.GetService<IEmailSender>(); 
    service.Send();
}
```

**সমাধান:**
সবসময় **Constructor Injection** ব্যবহার করুন (যেমনটি আমরা ১ নম্বর টপিকে দেখেছি)।

### ৫. Guard Clauses (সুরক্ষা ব্যবস্থা)

**এটি কী:**
কনস্ট্রাক্টরে যখন কোনো সার্ভিস ইনজেক্ট করা হয়, তখন সেটি `null` কি না তা চেক করা।

**কেন এটি গুরুত্বপূর্ণ:**
যদি কন্টেইনার কোনো কারণে সার্ভিস প্রোভাইড করতে ব্যর্থ হয় এবং `null` পাঠায়, তবে অ্যাপ ক্র্যাশ করবে। তাই শুরুতেই চেক করা ভালো।

**কোড উদাহরণ:**
```csharp
public class OrderService
{
    private readonly IEmailSender _emailSender;

    public OrderService(IEmailSender emailSender)
    {
        // যদি emailSender null হয়, সাথে সাথে এরর দেবে
        ArgumentNullException.ThrowIfNull(emailSender); 
        
        _emailSender = emailSender;
    }
}
```
**সুবিধা:** এররটি অ্যাপ্লিকেশনের গভীরে গিয়ে ধরা পড়ার চেয়ে শুরুতেই ধরা পড়ে, যা ডিবাগ করা সহজ।

### ৬. Revisiting Patterns using DI (Strategy & Factory)

DI ব্যবহার করে আমরা আগের চ্যাপ্টারের ডিজাইন প্যাটার্নগুলোকে আরও শক্তিশালী করতে পারি।

#### Strategy Pattern with DI
আমরা রানটাইমে ইন্টারফেসের ইমপ্লিমেন্টেশন পরিবর্তন করতে পারি।
*   **ব্যবহার:** `Program.cs`-এ `services.AddTransient<IPayment, BkashPayment>()` লিখলে পুরো অ্যাপে বিকাশ ব্যবহার হবে। শুধু এক লাইন বদলে `NagadPayment` করে দিলেই পুরো অ্যাপে নগদ চালু হয়ে যাবে। কোড এডিট করার দরকার নেই।

#### Factory Pattern with DI
জটিল অবজেক্ট তৈরির জন্য আমরা ফ্যাক্টরি ব্যবহার করি। DI-তে আমরা `Func<T>` ব্যবহার করে বা আলাদা ফ্যাক্টরি ক্লাস বানিয়ে তা ইনজেক্ট করতে পারি।

### অধ্যায়ের সারসংক্ষেপ (Summary of Key Points)

এই অধ্যায়ের মূল শিক্ষাগুলো হলো:

১. **New is Glue:** কোডের ভেতরে `new` কিওয়ার্ড ব্যবহার করে অবজেক্ট তৈরি করবেন না। এটি কোডকে অনমনীয় (Tightly Coupled) করে।
২. **Constructor Injection:** ডিপেন্ডেন্সি সবসময় কনস্ট্রাক্টরের মাধ্যমে ইনজেক্ট করুন। এটি কোডকে পরিষ্কার ও টেস্টযোগ্য রাখে।
৩. **Lifetimes:**
    *   `Transient`: প্রতিবার নতুন।
    *   `Scoped`: প্রতি রিকোয়েস্টে এক। (ডাটাবেসের জন্য সেরা)।
    *   `Singleton`: পুরো অ্যাপে এক। (ক্যাশিংয়ের জন্য সেরা)।
৪. **Service Locator এড়িয়ে চলুন:** সরাসরি কন্টেইনার থেকে সার্ভিস কল করবেন না, এটি খারাপ প্র্যাকটিস।
৫. **Guard Clauses:** ইনজেক্ট করা সার্ভিস `null` কি না তা চেক করুন।

Dependency Injection ঠিকমতো বুঝলে এবং ব্যবহার করলে আপনার অ্যাপ্লিকেশন হবে **Modular**, **Testable** এবং **Maintainable**।

### ২. Dependency Injection (DI) কী এবং কেন?

**সহজ কথায়:**
কোনো ক্লাসের ভেতরে `new` কিওয়ার্ড ব্যবহার করে অন্য ক্লাসের অবজেক্ট তৈরি না করে, কনস্ট্রাক্টরের মাধ্যমে বাইরে থেকে অবজেক্ট গ্রহণ করার নামই Dependency Injection।

**কেন এটি জরুরি?**
ধরা যাক, আপনার `OrderService` ক্লাসে ইমেইল পাঠানোর জন্য `EmailService` দরকার।
*   **DI ছাড়া:** আপনি ক্লাসের ভেতরে `new EmailService()` লিখবেন। সমস্যা হলো, ভবিষ্যতে যদি ইমেইল সার্ভিস বদলে এসএমএস সার্ভিস করতে চান, তবে আপনার `OrderService` ক্লাসের কোড কাটাকাটি করতে হবে। এটি **Tightly Coupled**।
*   **DI সহ:** আপনি বলবেন "আমার একটি মেসেজ সার্ভিস দরকার"। কন্টেইনার আপনাকে ইমেইল বা এসএমএস—যেটি কনফিগার করা আছে, সেটিই দেবে। এটি **Loosely Coupled**।

### ৩. কোড ইমপ্লিমেন্টেশন (বাস্তব উদাহরণ)

আমরা একটি **Notification System** তৈরি করব যেখানে আমরা দেখব কিভাবে DI ব্যবহার করে সহজেই ইমেইল থেকে কনসোল লগে সুইচ করা যায়।

#### ধাপ ১: ইন্টারফেস তৈরি (Contract)
প্রথমে একটি ইন্টারফেস তৈরি করি যা বলে দেবে আমাদের সার্ভিসটি কী করবে।

```csharp
// Services/INotificationService.cs
public interface INotificationService
{
    void Send(string message);
}
```

#### ধাপ ২: ইমপ্লিমেন্টেশন তৈরি (Concrete Classes)
এখন আমরা দুটি ভিন্ন সার্ভিস বানাবো যারা এই ইন্টারফেসটি ব্যবহার করবে।

```csharp
// Services/EmailService.cs
public class EmailService : INotificationService
{
    public void Send(string message)
    {
        // বাস্তবে এখানে ইমেইল পাঠানোর কোড থাকবে
        Console.WriteLine($"[Email Sent]: {message}");
    }
}

// Services/SmsService.cs
public class SmsService : INotificationService
{
    public void Send(string message)
    {
        Console.WriteLine($"[SMS Sent]: {message}");
    }
}
```

#### ধাপ ৩: কনস্ট্রাক্টর ইনজেকশন (Constructor Injection)
এখন আমরা এই সার্ভিসটি আমাদের কন্ট্রোলারে ব্যবহার করব। লক্ষ্য করুন, আমরা এখানে `new EmailService()` লিখব না।

```csharp
// Controllers/NotificationController.cs
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/[controller]")]
public class NotificationController : ControllerBase
{
    // আমরা ইন্টারফেসের ওপর নির্ভর করছি, নির্দিষ্ট ক্লাসের ওপর নয়
    private readonly INotificationService _notificationService;

    // কনস্ট্রাক্টর ইনজেকশন: কন্টেইনার এখানে অবজেক্ট পাস করবে
    public NotificationController(INotificationService notificationService)
    {
        // Guard Clause: নিশ্চিত করা হচ্ছে সার্ভিসটি যেন null না হয়
        _notificationService = notificationService ?? throw new ArgumentNullException(nameof(notificationService));
    }

    [HttpPost("send")]
    public IActionResult SendNotification(string message)
    {
        _notificationService.Send(message);
        return Ok("Notification process completed.");
    }
}
```

#### ধাপ ৪: Composition Root (Program.cs কনফিগারেশন)
এটাই সেই জাদুর জায়গা (IoC Container)। এখানে আমরা বলে দেব `INotificationService` চাইলে কোন ক্লাসটি দিতে হবে।

`Program.cs` ফাইলে `builder.Build()` এর আগে নিচের লাইনটি লিখুন:

```csharp
// আমরা এখানে বলে দিচ্ছি: কেউ INotificationService চাইলে তাকে EmailService দিও।
builder.Services.AddTransient<INotificationService, EmailService>();

// আপনি যদি ভবিষ্যতে SMS ব্যবহার করতে চান, শুধু উপরের লাইনটি বদলে নিচেরটি লিখলেই হবে:
// builder.Services.AddTransient<INotificationService, SmsService>();
```

### ৪. Service Lifetimes (খুবই গুরুত্বপূর্ণ)

DI কন্টেইনারে সার্ভিস রেজিস্টার করার সময় ৩টি লাইফটাইম থাকে। এটি ঠিক করে অবজেক্টটি কতক্ষণ মেমোরিতে বেঁচে থাকবে।

| Lifetime | মেথড | আচরণ (Behavior) | বাস্তব ব্যবহার |
| :--- | :--- | :--- | :--- |
| **Transient** | `AddTransient` | প্রতিবার চাওয়ার সময় **নতুন** অবজেক্ট তৈরি করে। | হালকা বা স্টেটলেস সার্ভিস (যেমন: EmailService)। |
| **Scoped** | `AddScoped` | প্রতি **HTTP রিকোয়েস্টে** একবার তৈরি হয়। একই রিকোয়েস্টে বারবার চাইলে একই অবজেক্ট দেয়। | ডাটাবেস কনটেক্সট (DbContext), ইউজার সেশন। |
| **Singleton** | `AddSingleton` | অ্যাপ চালু হলে **একবারই** তৈরি হয় এবং অ্যাপ বন্ধ না হওয়া পর্যন্ত মেমোরিতে থাকে। | ক্যাশিং সার্ভিস, কনফিগারেশন। |

**কোড ডেমো (লাইফটাইম বোঝার জন্য):**

```csharp
// একটি অপারেশন আইডি জেনারেটর সার্ভিস
public class OperationIdService
{
    public Guid Id { get; } = Guid.NewGuid(); // ইউনিক আইডি
}

// Program.cs এ রেজিস্টার করুন
builder.Services.AddTransient<OperationIdService>(); // অথবা AddScoped / AddSingleton দিয়ে টেস্ট করুন
```

*   **Transient** দিলে: একই রিকোয়েস্টে দুবার সার্ভিসটি ইনজেক্ট করলে দুটি আলাদা ID পাবেন।
*   **Scoped** দিলে: একই রিকোয়েস্টে ID এক থাকবে, কিন্তু ব্রাউজার রিফ্রেশ দিলে (নতুন রিকোয়েস্ট) ID বদলে যাবে।
*   **Singleton** দিলে: ব্রাউজার রিফ্রেশ দিলেও ID আর বদলাবে না (যতক্ষণ সার্ভার রিস্টার্ট না হচ্ছে)।

### ৫. সাধারণ সমস্যা এবং সমাধান (Common Problems)

**সমস্যা ১: Captive Dependency (বন্দী ডিপেন্ডেন্সি)**
আপনি যদি একটি `Singleton` সার্ভিসের কনস্ট্রাক্টরে একটি `Scoped` সার্ভিস ইনজেক্ট করেন, তবে `Scoped` সার্ভিসটি আর রিকোয়েস্ট শেষে ডিলিট হবে না। এটি মেমোরি লিক করতে পারে।
*   **সমাধান:** সবসময় ছোট লাইফটাইমের ভেতরে বড় লাইফটাইম ইনজেক্ট করবেন (যেমন: Scoped-এর ভেতর Singleton), কিন্তু উল্টোটা করবেন না।

**সমস্যা ২: Service Locator Anti-pattern**
কখনো কখনো ডেভেলপাররা কনস্ট্রাক্টরে ইনজেক্ট না করে সরাসরি মেথডের ভেতরে কন্টেইনার কল করেন।

```csharp
// ❌ খারাপ প্র্যাকটিস
public void DoWork(IServiceProvider provider)
{
    var service = provider.GetService<IEmailService>(); // এটি করবেন না
}
```
*   **সমাধান:** সবসময় কনস্ট্রাক্টর ইনজেকশন ব্যবহার করুন। এতে কোড দেখে বোঝা যায় এই ক্লাসের কী কী ডিপেন্ডেন্সি দরকার।

### ৬. অধ্যায়ের সারসংক্ষেপ (Summary of Key Points)

এই চ্যাপ্টার থেকে আপনার যা মনে রাখা জরুরি:

১. **New is Glue:** `new` কিওয়ার্ড দিয়ে সার্ভিস ক্লাসের অবজেক্ট তৈরি করবেন না। এতে কোড শক্তভাবে আটকে যায় (Tightly Coupled)।
২. **Abstraction:** সবসময় ইন্টারফেস (`INotificationService`) এর ওপর নির্ভর করবেন, ইমপ্লিমেন্টেশন (`EmailService`) এর ওপর নয়।
৩. **IoC Container:** `Program.cs` হলো সেই জায়গা যেখানে আপনি সিদ্ধান্ত নেন কোন ইন্টারফেসের জন্য কোন ক্লাস ব্যবহার হবে।
৪. **Lifetimes:**
    *   `Transient`: প্রতিবার নতুন।
    *   `Scoped`: প্রতি রিকোয়েস্টে এক।
    *   `Singleton`: আজীবনের জন্য এক।
৫. **Guard Clauses:** কনস্ট্রাক্টরে `ArgumentNullException.ThrowIfNull(...)` ব্যবহার করুন যাতে ডিপেন্ডেন্সি মিসিং হলে শুরুতেই ধরা পড়ে।

এই পদ্ধতিগুলো অনুসরণ করলে আপনার অ্যাপ্লিকেশন হবে **Modular**, **Testable** এবং ভবিষ্যতে পরিবর্তন করা হবে অত্যন্ত সহজ।
