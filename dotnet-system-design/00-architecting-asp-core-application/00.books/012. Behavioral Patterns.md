### ১. Template Method Pattern (টেমপ্লেট মেথড প্যাটার্ন)

**এটি কী:**
Template Method প্যাটার্ন হলো এমন একটি পদ্ধতি যেখানে একটি প্যারেন্ট ক্লাসে কোনো কাজের **মূল কাঠামো (Skeleton)** বা অ্যালগরিদম ঠিক করে দেওয়া হয়, কিন্তু সেই কাজের কিছু নির্দিষ্ট ধাপ (Steps) চাইল্ড ক্লাসের ওপর ছেড়ে দেওয়া হয়।

সহজ কথায়, "কাজের ফ্লো বা ধারা ঠিক থাকবে, কিন্তু ভেতরের ছোটখাটো কাজগুলো একেক জন একেকভাবে করবে।"

**সহজ বাংলা উদাহরণ (চা ও কফি বানানো):**
গরম পানীয় বানানোর ধাপগুলো দেখুন:
১. পানি গরম করা (সবার জন্য এক)।
২. **পানীয় মেশানো** (চা হলে টি-ব্যাগ, কফি হলে কফি পাউডার)।
৩. কাপে ঢালা (সবার জন্য এক)।
৪. **ফ্লেভার যোগ করা** (চায়ে লেবু/চিনি, কফিতে দুধ/চিনি)।

এখানে ১ ও ৩ নম্বর ধাপ সবার জন্য সমান (Parent Class-এ থাকবে)। কিন্তু ২ ও ৪ নম্বর ধাপ একেক পানীয়র জন্য একেক রকম (Child Class ঠিক করবে)।

**কোড উদাহরণ:**

```csharp
// ১. অ্যাবস্ট্রাক্ট ক্লাস (মূল কাঠামো)
public abstract class DataProcessor
{
    // এটিই Template Method (পুরো প্রসেস ঠিক করে দেয়)
    public void Process()
    {
        LoadData();
        ProcessData(); // এই ধাপটি চাইল্ড ক্লাস ঠিক করবে
        SaveData();
    }

    private void LoadData() => Console.WriteLine("Loading Data...");
    private void SaveData() => Console.WriteLine("Saving Data...");

    // এই মেথডটি চাইল্ড ক্লাসকে ইমপ্লিমেন্ট করতে হবে
    protected abstract void ProcessData();
}

// ২. চাইল্ড ক্লাস ১
public class ExcelProcessor : DataProcessor
{
    protected override void ProcessData()
    {
        Console.WriteLine("Processing Excel Data logic...");
    }
}

// ৩. চাইল্ড ক্লাস ২
public class JsonProcessor : DataProcessor
{
    protected override void ProcessData()
    {
        Console.WriteLine("Processing JSON Data logic...");
    }
}
```

**কেন এটি কাজ করে ও কেন জরুরি:**
এটি **DRY (Don't Repeat Yourself)** প্রিন্সিপাল মেনে চলে। কমন কোডগুলো প্যারেন্ট ক্লাসে থাকে, ফলে বারবার লিখতে হয় না। এটি কোড রিইউজাবিলিটি বাড়ায়।

**সমস্যা (Problems):**
*   **Liskov Substitution Principle (LSP) ভায়োলেশন:** যদি চাইল্ড ক্লাস প্যারেন্ট ক্লাসের মূল অ্যালগরিদমের ফ্লো নষ্ট করে ফেলে, তবে সমস্যা হতে পারে।
*   **Tight Coupling:** চাইল্ড ক্লাসগুলো প্যারেন্ট ক্লাসের ওপর খুব বেশি নির্ভরশীল হয়ে পড়ে।

**সমাধান:**
*   Template Method-টিকে `sealed` বা `final` করে দেওয়া উচিত যাতে চাইল্ড ক্লাস মূল ফ্লো পরিবর্তন করতে না পারে।
*   ইনহেরিটেন্সের বদলে প্রয়োজনে স্ট্র্যাটেজি প্যাটার্ন ব্যবহার করা।

**বাস্তব ব্যবহার:**
*   ডাটা ইম্পোর্ট বা এক্সপোর্ট টুল (যেখানে ফাইল রিড এবং রাইট এক, কিন্তু প্রসেসিং আলাদা)।
*   ASP.NET Core-এর বিভিন্ন লাইফসাইকেল মেথড (যেমন: `OnInitialized` বা `OnActionExecuting`), যেখানে ফ্রেমওয়ার্ক মূল ফ্লো চালায় কিন্তু আপনি লজিক বসাতে পারেন।

### ২. Chain of Responsibility Pattern (চেইন অফ রেসপন্সিবিলিটি)

**এটি কী:**
এই প্যাটার্নটি একটি রিকোয়েস্টকে হ্যান্ডেল করার জন্য অনেকগুলো অবজেক্টের একটি **চেইন বা শিকল** তৈরি করে। রিকোয়েস্টটি প্রথম হ্যান্ডলারের কাছে যায়। সে যদি হ্যান্ডেল করতে পারে তো করল, না পারলে পরের জনের কাছে পাঠিয়ে দেয়।

**সহজ বাংলা উদাহরণ (অফিসের ছুটির আবেদন):**
আপনি ছুটির আবেদন করলেন।
১. প্রথমে এটি **Team Lead**-এর কাছে গেল। সে যদি অনুমোদন করতে পারে ভালো, না পারলে...
২. সেটি **Manager**-এর কাছে যাবে। সে না পারলে...
৩. সেটি **HR**-এর কাছে যাবে।

অর্থাৎ, কেউ না কেউ এটি হ্যান্ডেল করবে, অথবা চেইন শেষ হয়ে যাবে।

**কোড উদাহরণ:**

```csharp
// ১. হ্যান্ডলার ইন্টারফেস
public abstract class Approver
{
    protected Approver NextApprover;

    public void SetNext(Approver next)
    {
        NextApprover = next;
    }

    public abstract void ProcessRequest(int amount);
}

// ২. টিম লিড (ছোট অ্যামাউন্ট হ্যান্ডেল করে)
public class TeamLead : Approver
{
    public override void ProcessRequest(int amount)
    {
        if (amount < 1000)
        {
            Console.WriteLine("Team Lead approved: " + amount);
        }
        else if (NextApprover != null)
        {
            NextApprover.ProcessRequest(amount); // পাস করে দিচ্ছে
        }
    }
}

// ৩. ম্যানেজার (বড় অ্যামাউন্ট হ্যান্ডেল করে)
public class Manager : Approver
{
    public override void ProcessRequest(int amount)
    {
        if (amount < 5000)
        {
            Console.WriteLine("Manager approved: " + amount);
        }
        else
        {
            Console.WriteLine("Amount too high! Meeting needed.");
        }
    }
}

// ৪. ব্যবহার
var lead = new TeamLead();
var manager = new Manager();

lead.SetNext(manager); // চেইন সেট করা হলো

lead.ProcessRequest(500);  // Team Lead অ্যাপ্রুভ করবে
lead.ProcessRequest(2500); // Manager অ্যাপ্রুভ করবে
```

**কেন এটি কাজ করে ও কেন জরুরি:**
এটি **Single Responsibility Principle (SRP)** মেনে চলে। প্রতিটি ক্লাস শুধু তার নিজের লজিকটুকু জানে। কে রিকোয়েস্ট পাঠাল বা পরে কে হ্যান্ডেল করবে, তা জানার দরকার নেই। এটি সিস্টেমকে ফ্লেক্সিবল করে।

**সমস্যা (Problems):**
*   **Uncaught Requests:** যদি চেইনের শেষ পর্যন্ত কোনো হ্যান্ডলার রিকোয়েস্ট হ্যান্ডেল না করে, তবে রিকোয়েস্ট হারিয়ে যেতে পারে।
*   **Debugging Difficulty:** চেইন অনেক লম্বা হলে ডিবাগ করা কঠিন হতে পারে যে আসলে সমস্যা কোথায়।

**সমাধান:**
*   চেইনের শেষে সবসময় একটি **Default Handler** রাখা উচিত যাUnhandled রিকোয়েস্টের লগ রাখবে বা এরর মেসেজ দেবে।

**বাস্তব ব্যবহার:**
*   **ASP.NET Core Middleware Pipeline:** এটি এই প্যাটার্নের সবচেয়ে বড় উদাহরণ। রিকোয়েস্ট আসলে সেটি অথেনটিফিকেশন, লগিং, রাউটিং—একেকটি মিডলওয়্যার হয়ে কন্ট্রোলারের কাছে পৌঁছায়।
*   **Exception Handling:** ট্রাই-ক্যাচ ব্লক (প্রথমে স্পেসিফিক এরর চেক করে, না পারলে জেনেরিক এররের কাছে পাঠায়)।

### ৩. Mixing Patterns (প্যাটার্নের সংমিশ্রণ)

বইটিতে এই দুটি প্যাটার্ন একসাথে ব্যবহার করার কথা বলা হয়েছে।

**কিভাবে কাজ করে:**
আপনি একটি `Chain of Responsibility` তৈরি করতে পারেন যেখানে প্রতিটি হ্যান্ডলারের ভেতরে `Template Method` প্যাটার্ন ব্যবহার করা হয়েছে।

*   **উদাহরণ:** একটি মেসেজ প্রসেসিং সিস্টেমে অনেকগুলো হ্যান্ডলার থাকতে পারে (Chain)। কিন্তু প্রতিটি হ্যান্ডলারের মেসেজ রিসিভ করা এবং লগ করার পদ্ধতি একই (Template), শুধু প্রসেসিং লজিক আলাদা।

### অধ্যায়ের সারসংক্ষেপ (Summary of Key Points)

১. **Template Method:** অ্যালগরিদমের মূল স্ট্রাকচার ঠিক রেখে সাব-ক্লাসকে নির্দিষ্ট ধাপগুলো কাস্টমাইজ করতে দেয়। এটি কোড ডুপ্লিকেশন কমায়।
২. **Chain of Responsibility:** একটি কাজ করার জন্য একাধিক হ্যান্ডলারকে সারিবদ্ধভাবে সাজায়। একজন না পারলে পরের জন চেষ্টা করে।
৩. **বাস্তব প্রয়োগ:**
    *   Template Method ব্যবহৃত হয় ফ্রেমওয়ার্ক বা লাইব্রেরি ডিজাইনে (যেমন: Data Processing)।
    *   Chain of Responsibility ব্যবহৃত হয় মিডলওয়্যার বা রিকোয়েস্ট পাইপলাইনে।
৪. **সতর্কতা:** ইনহেরিটেন্স ব্যবহারে সাবধান হতে হবে এবং চেইনের শেষে রিকোয়েস্ট যেন হারিয়ে না যায় তা নিশ্চিত করতে হবে।

এই প্যাটার্নগুলো আপনার কোডকে আরও মডুলার এবং অর্গানাইজড করতে সাহায্য করে, যা বড় অ্যাপ্লিকেশনের জন্য অত্যন্ত জরুরি।

### ২. Template Method Design Pattern

**এটি কী:**
Template Method প্যাটার্ন হলো এমন একটি ব্লু-প্রিন্ট বা ছাঁচ, যেখানে একটি প্যারেন্ট ক্লাসে কাজের মূল প্রবাহ (Workflow) বা অ্যালগরিদম ঠিক করে দেওয়া হয়। কিন্তু সেই কাজের কিছু নির্দিষ্ট ধাপ (Steps) ফাঁকা রাখা হয়, যা চাইল্ড ক্লাসগুলো নিজেদের মতো করে পূরণ করে।

**বাস্তব উদাহরণ:**
মনে করুন "ডাটা প্রসেসিং" এর একটি কাজ।
১. ফাইল রিড করা (সবাই একইভাবে করবে)।
২. ডাটা প্রসেস করা (একেক ফাইলের ফরম্যাট অনুযায়ী লজিক আলাদা হবে - XML/JSON)।
৩. ডাটা সেভ করা (সবাই একইভাবে করবে)।

এখানে ১ ও ৩ ফিক্সড, কিন্তু ২ নম্বর ধাপটি পরিবর্তনশীল।

**কোড ইমপ্লিমেন্টেশন:**

```csharp
using System;

// ১. Abstract Base Class (ছাঁচ)
public abstract class DataMiner
{
    // এটিই "Template Method"। এখানে 'sealed' ব্যবহার করা যেতে পারে যাতে কেউ ফ্লো চেঞ্জ না করে।
    public void MineData()
    {
        OpenFile();
        ExtractData(); // এই ধাপটি চাইল্ড ক্লাস ইমপ্লিমেন্ট করবে
        CloseFile();
    }

    private void OpenFile()
    {
        Console.WriteLine("1. File Opened.");
    }

    // Abstract Method: চাইল্ড ক্লাসকে এটি অবশ্যই ইমপ্লিমেন্ট করতে হবে
    protected abstract void ExtractData();

    private void CloseFile()
    {
        Console.WriteLine("3. File Closed.");
    }
}

// ২. চাইল্ড ক্লাস ১: PDF
public class PDFMiner : DataMiner
{
    protected override void ExtractData()
    {
        Console.WriteLine("2. Extracting data from PDF format...");
    }
}

// ৩. চাইল্ড ক্লাস ২: CSV
public class CSVMiner : DataMiner
{
    protected override void ExtractData()
    {
        Console.WriteLine("2. Extracting data from CSV format...");
    }
}

// ব্যবহার (Program.cs এ লিখুন)
DataMiner pdfMiner = new PDFMiner();
pdfMiner.MineData(); 
// Output: 
// 1. File Opened. 
// 2. Extracting data from PDF format... 
// 3. File Closed.

Console.WriteLine("---");

DataMiner csvMiner = new CSVMiner();
csvMiner.MineData();
```

**লজিক:**
*   `MineData()` মেথডটি পুরো অ্যালগরিদম নিয়ন্ত্রণ করছে। সে জানে কখন ফাইল ওপেন করতে হবে আর কখন ক্লোজ করতে হবে।
*   `ExtractData()` মেথডটি অ্যাবস্ট্রাক্ট, তাই চাইল্ড ক্লাস (PDF/CSV) বাধ্য হয়েছে তাদের নিজস্ব লজিক লিখতে।

### ৩. Chain of Responsibility Pattern

**এটি কী:**
এটি এমন একটি প্যাটার্ন যেখানে একটি রিকোয়েস্ট হ্যান্ডেল করার জন্য অনেকগুলো অবজেক্টের একটি চেইন বা শিকল তৈরি করা হয়। রিকোয়েস্টটি চেইনের এক মাথা দিয়ে ঢোকে এবং হ্যান্ডলাররা চেক করে যে তারা এটি প্রসেস করতে পারবে কি না। পারলে করে, না পারলে পরের জনের কাছে পাঠিয়ে দেয়।

**বাস্তব উদাহরণ:**
কাস্টমার কেয়ার সাপোর্ট।
১. লেভেল ১ সাপোর্ট (সাধারণ সমস্যা)। সমাধান না হলে ->
২. লেভেল ২ সাপোর্ট (টেকনিক্যাল সমস্যা)। সমাধান না হলে ->
৩. ম্যানেজার।

**কোড ইমপ্লিমেন্টেশন:**

আমরা এখানে একটি **লগিং সিস্টেম** বানাব। যেখানে `Info` লগ কনসোলে দেখাবে, কিন্তু `Error` লগ হলে সেটি ইমেইল করবে।

```csharp
// ১. হ্যান্ডলার ইন্টারফেস বা অ্যাবস্ট্রাক্ট ক্লাস
public abstract class Logger
{
    protected Logger NextLogger; // চেইনের পরের জন

    // চেইন সেট করার মেথড
    public void SetNext(Logger nextLogger)
    {
        NextLogger = nextLogger;
    }

    public void LogMessage(string level, string message)
    {
        if (CanHandle(level))
        {
            Write(message);
        }
        
        // যদি আমি হ্যান্ডেল করি বা না করি, চেইনে পরের জন থাকলে তাকেও জানাবো
        if (NextLogger != null)
        {
            NextLogger.LogMessage(level, message);
        }
    }

    protected abstract bool CanHandle(string level);
    protected abstract void Write(string message);
}

// ২. কনসোল লগার (INFO লেভেল হ্যান্ডেল করে)
public class ConsoleLogger : Logger
{
    protected override bool CanHandle(string level) => level == "INFO";

    protected override void Write(string message)
    {
        Console.WriteLine($"[Console]: {message}");
    }
}

// ৩. ইমেইল লগার (ERROR লেভেল হ্যান্ডেল করে)
public class EmailLogger : Logger
{
    protected override bool CanHandle(string level) => level == "ERROR";

    protected override void Write(string message)
    {
        Console.WriteLine($"[Email Sent]: {message}");
    }
}

// ব্যবহার (Program.cs)
var consoleLogger = new ConsoleLogger();
var emailLogger = new EmailLogger();

// চেইন সেট করা: Console -> Email
consoleLogger.SetNext(emailLogger);

// টেস্ট ১: INFO লগ
consoleLogger.LogMessage("INFO", "System started."); 
// Output: [Console]: System started.

// টেস্ট ২: ERROR লগ
consoleLogger.LogMessage("ERROR", "Database crashed!");
// Output: [Email Sent]: Database crashed!
```

**লজিক:**
*   এখানে `LogMessage` মেথডটি চেক করে যে বর্তমান লগার এটি হ্যান্ডেল করতে পারবে কি না।
*   `SetNext` মেথড দিয়ে আমরা একটার পর একটা লগার লিংক করেছি।

### ৪. Mixing Patterns (Template Method + Chain of Responsibility)

বইটিতে এই দুটি প্যাটার্নকে একসাথে ব্যবহার করার একটি চমৎকার কৌশল দেখানো হয়েছে।

**কেন মেশাবো?**
Chain of Responsibility প্যাটার্নে প্রতিটি ক্লাসে `NextLogger != null` চেক করা এবং পরের জনকে কল করার কোড বারবার লিখতে হয় (Duplication)। আমরা যদি **Template Method** ব্যবহার করি, তবে এই "পরের জনকে কল করার" লজিকটি প্যারেন্ট ক্লাসে একবার লিখলেই হয়ে যায়।

**অপটিমাইজড কোড:**

```csharp
// Base Handler with Template Method
public abstract class Handler
{
    private Handler _next;

    public void SetNext(Handler next) => _next = next;

    // এটি Template Method
    public void Handle(string request)
    {
        if (CanProcess(request))
        {
            Process(request); // নির্দিষ্ট কাজ
        }
        else if (_next != null)
        {
            _next.Handle(request); // পরের জনকে পাস করা
        }
    }

    // চাইল্ড ক্লাস শুধু এই দুটি মেথড ইমপ্লিমেন্ট করবে
    protected abstract bool CanProcess(string request);
    protected abstract void Process(string request);
}
```
*এখন চাইল্ড ক্লাসে আর `Next` বা লুপ নিয়ে চিন্তা করতে হবে না, শুধু নিজের লজিকটুকু লিখলেই হবে।*

### ৫. সাধারণ সমস্যা এবং সমাধান

**সমস্যা ১: চেইন হারিয়ে যাওয়া (Uncaught Requests)**
*   *বিবরণ:* যদি চেইনের শেষ পর্যন্ত কেউ রিকোয়েস্ট হ্যান্ডেল না করে, তবে রিকোয়েস্টটি হারিয়ে যায় এবং ইউজার কোনো রেসপন্স পায় না।
*   *সমাধান:* চেইনের একদম শেষে একটি `DefaultHandler` রাখা উচিত যা বলবে "Request could not be handled"।

**সমস্যা ২: লিসকভ সাবস্টিটিউশন প্রিন্সিপাল (LSP) ভায়োলেশন**
*   *বিবরণ:* Template Method-এ যদি চাইল্ড ক্লাস প্যারেন্টের মূল ফ্লো পরিবর্তন করে দেয়।
*   *সমাধান:* প্যারেন্ট ক্লাসের টেম্পলেট মেথডটিতে `sealed` (C#-এ) ব্যবহার করা যেতে পারে, যাতে চাইল্ড ক্লাস সেটি ওভাররাইড করতে না পারে।

### ৬. বাস্তব ব্যবহার (Real-World Example)

**ASP.NET Core Middleware Pipeline:**
ASP.NET Core-এর পুরো রিকোয়েস্ট প্রসেসিং পাইপলাইনটি **Chain of Responsibility** প্যাটার্নের ওপর ভিত্তি করে তৈরি।
1.  Browser থেকে Request আসে।
2.  **Exception Handling Middleware** (প্রথম হ্যান্ডলার)।
3.  **Authentication Middleware** (দ্বিতীয় হ্যান্ডলার - লগইন চেক করে)।
4.  **Routing Middleware** (তৃতীয় হ্যান্ডলার - কোথায় যাবে ঠিক করে)।
5.  **Controller** (শেষ হ্যান্ডলার - ডেটা দেয়)।

প্রতিটি মিডলওয়্যার `next()` কল করে রিকোয়েস্ট পরের জনের কাছে পাঠায়।

### ৭. অধ্যায়ের সারসংক্ষেপ (Summary of Key Points)

১. **Template Method:** এটি অ্যালগরিদমের কঙ্কাল (Skeleton) তৈরি করে এবং ছোটখাটো ডিটেইলস চাইল্ড ক্লাসের ওপর ছেড়ে দেয়। এটি **DRY** (Don't Repeat Yourself) প্রিন্সিপাল মেনে চলে।
২. **Chain of Responsibility:** এটি রিকোয়েস্ট হ্যান্ডলিং লজিককে ছোট ছোট ক্লাসে ভাগ করে এবং একটি চেইনের মাধ্যমে চালায়। এটি **SRP** (Single Responsibility Principle) মেনে চলে।
৩. **Power of Combination:** এই দুটি প্যাটার্ন একসাথে ব্যবহার করলে কোড অনেক বেশি ক্লিন এবং রিইউজেবল হয়। বেস ক্লাসে চেইনের লজিক থাকে (Template) এবং চাইল্ড ক্লাসে হ্যান্ডলিং লজিক থাকে।

এই প্যাটার্নগুলো শিখলে আপনি জটিল বিজনেস লজিক বা ওয়ার্কফ্লো খুব সহজেই ম্যানেজ করতে পারবেন।
