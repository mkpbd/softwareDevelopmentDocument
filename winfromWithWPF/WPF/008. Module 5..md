### **Module 5: Advanced Topics**

**Goal:** Master the core patterns that make MVVM applications robust and maintainable, starting with `ICommand`.

#### **1. Commands - The MVVM Way of Handling Events**

Remember in Module 2, we still had this code in our `MainWindow.xaml.cs`:

```csharp
// This is the last bit of logic in our code-behind.
private void MyButton_Click(object sender, RoutedEventArgs e)
{
    var viewModel = (MainViewModel)this.DataContext;
    viewModel.ChangeGreeting(); // We're calling a method on the ViewModel.
}
```
This still creates a link between the View's *event* (`Click`) and the ViewModel's *action*. It works, but we can do better. What if we wanted to disable the button under certain conditions? We'd have to write more code in the code-behind to manage the button's `IsEnabled` property.

**Commands** solve this elegantly. A command is an object that encapsulates two things:
1.  **An `Execute` action:** What to do when the command is invoked (e.g., when a button is clicked).
2.  **A `CanExecute` condition:** A function that returns `true` or `false`, determining if the action is currently allowed.

The View (e.g., a `Button`) binds its `Command` property to an `ICommand` property on the ViewModel. WPF then automatically handles enabling/disabling the button based on `CanExecute` and calling `Execute` when it's clicked.

**Let's implement this.**

##### **Step 1: Create a Reusable `RelayCommand` Class**

The .NET framework provides the `ICommand` interface, but not a concrete implementation. We need to create one. This is a standard "helper" class you will use in almost every WPF project.

> **Note:** Modern MVVM frameworks like the **MVVM Community Toolkit** provide this class for you, so you don't have to write it yourself. But for learning purposes, it's crucial to see how it's built once.

1.  In Solution Explorer, right-click your project and add a new class named `RelayCommand.cs`.
2.  Paste the following code into the file. Read the comments to understand what it's doing.

```csharp
using System;
using System.Windows.Input;

public class RelayCommand : ICommand
{
    private readonly Action<object?> _execute;
    private readonly Predicate<object?>? _canExecute;

    // Fired when the result of CanExecute may have changed.
    public event EventHandler? CanExecuteChanged
    {
        add { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }

    // Constructor for commands that can always execute.
    public RelayCommand(Action<object?> execute) : this(execute, null)
    {
    }

    // Constructor for commands with a condition.
    public RelayCommand(Action<object?> execute, Predicate<object?>? canExecute)
    {
        _execute = execute ?? throw new ArgumentNullException(nameof(execute));
        _canExecute = canExecute;
    }

    // The logic that determines if the command can run.
    public bool CanExecute(object? parameter)
    {
        return _canExecute == null || _canExecute(parameter);
    }

    // The logic that runs when the command is executed.
    public void Execute(object? parameter)
    {
        _execute(parameter);
    }
}
```

You don't need to memorize this code, just understand its purpose: it's a generic wrapper that turns your methods into `ICommand` objects that WPF can understand.

##### **Step 2: Add an `ICommand` Property to the ViewModel**

Now let's use our new `RelayCommand` in our ViewModel. We'll create a command for our login form.

1.  Open `MainViewModel.cs`.
2.  We need properties to hold the username and password from the UI. Add these properties, making sure they call `OnPropertyChanged`.

    ```csharp
    private string _username;
    public string Username
    {
        get => _username;
        set
        {
            _username = value;
            OnPropertyChanged();
        }
    }

    // Note: For a real app, you'd use a SecureString for passwords,
    // but for this example, a simple string is fine.
    private string _password;
    public string Password
    {
        get => _password;
        set
        {
            _password = value;
            OnPropertyChanged();
        }
    }
    ```

3.  Next, define the `ICommand` property for the login action.

    ```csharp
    // Add this using statement at the top
    using System.Windows.Input;

    // ... inside the MainViewModel class
    public ICommand LoginCommand { get; }
    ```

4.  In the `MainViewModel` constructor, we will create an instance of our `RelayCommand` and assign it to `LoginCommand`.

    ```csharp
    public MainViewModel()
    {
        // ... previous code ...

        // Initialize the command
        LoginCommand = new RelayCommand(ExecuteLogin, CanLogin);
    }

    // This is the method that will be executed.
    private void ExecuteLogin(object? parameter)
    {
        // Simple login logic for demonstration
        System.Windows.MessageBox.Show($"Logging in with Username: {Username}");
    }

    // This is the condition that determines if the button is enabled.
    private bool CanLogin(object? parameter)
    {
        // Enable the login button only if both username and password are not empty.
        return !string.IsNullOrEmpty(Username) && !string.IsNullOrEmpty(Password);
    }
    ```

##### **Step 3: Update the View to Bind to the Command**

1.  Open `MainWindow.xaml`.
2.  Bind the `TextBox` and `PasswordBox` to the new properties on the ViewModel.

    ```xaml
    <!-- Add the Text property binding -->
    <TextBox Grid.Row="0" Grid.Column="1"
             Text="{Binding Username, UpdateSourceTrigger=PropertyChanged}"/>

    <!-- We need a helper for PasswordBox binding, but for now we'll skip it. -->
    <!-- The principle is the same. Let's focus on the command. -->
    <PasswordBox Grid.Row="1" Grid.Column="1" x:Name="PasswordBox"/>
    ```
    *   `UpdateSourceTrigger=PropertyChanged`: This is important. By default, a `TextBox` only sends its value to the ViewModel when it loses focus. This tells it to update the `Username` property on *every keystroke*, which allows our `CanLogin` condition to be re-evaluated instantly.

3.  Find the `Button`. **Delete the `Click="...` event handler** entirely.
4.  Bind its `Command` property to our new `LoginCommand`.

    ```xaml
    <Button Grid.Row="2" Grid.ColumnSpan="2"
            Content="Login"
            Command="{Binding LoginCommand}"
            Width="100"
            HorizontalAlignment="Center"/>
    ```
5.  Finally, go to `MainWindow.xaml.cs` and **delete the entire `MyButton_Click` event handler method**. Your code-behind is now completely empty of logic!

**Run the application (F5).**

Observe the new behavior:
1.  When the app starts, the **Login button is disabled**. This is because `CanLogin` is returning `false` (Username and Password are null/empty).
2.  Start typing in the "Username" box.
3.  Type something in the "Password" box. As soon as you do, the **Login button enables itself automatically!**
4.  Click the button. The `ExecuteLogin` method runs, and you see the message box.

### **Why This is a Game-Changer**

*   **Zero Logic in the View:** Your `MainWindow.xaml.cs` is now empty. The View is purely declarative.
*   **Encapsulated Logic:** All the logic for the login action—including the conditions under which it's allowed—is contained within the `MainViewModel`.
*   **Automatic UI State:** WPF handles the `IsEnabled` state of the button for you. You don't write `MyButton.IsEnabled = true`. You simply state the conditions in your ViewModel, and the UI adapts.
*   **Testability:** You can now write a unit test for your `MainViewModel`. You can create an instance of it, set the `Username` and `Password` properties, and check if `LoginCommand.CanExecute()` returns the correct boolean value, all without ever creating a single UI element.

This pattern is the heart of professional WPF development.
