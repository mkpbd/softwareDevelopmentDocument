### **Module 6: The Modern WPF Ecosystem**

**Goal:** Understand how to leverage modern libraries like the MVVM Toolkit and Dependency Injection to build WPF applications faster and in line with current software development best practices.

#### **1. The Problem with "Classic" MVVM**

As you saw in the last two modules, "classic" MVVM requires you to write a lot of repetitive code:
*   The entire `INotifyPropertyChanged` implementation in every ViewModel.
*   The full property implementation (`private field`, `public property`, calling `OnPropertyChanged`).
*   The entire `RelayCommand.cs` helper class.
*   Manually creating instances of ViewModels (e.g., `this.DataContext = new MainViewModel();`).

This is boilerplate. It's necessary, but it's tedious. Modern tools can write this code *for you*.

#### **2. The MVVM Community Toolkit - Your New Best Friend**

This is an official Microsoft library designed to drastically reduce the boilerplate in MVVM applications. It uses a new C# feature called **Source Generators** to generate the required code for you at compile time.

**Let's refactor our `MainViewModel` to use it.**

##### **Step 1: Install the NuGet Package**

1.  In Visual Studio, go to **Tools > NuGet Package Manager > Manage NuGet Packages for Solution...**.
2.  Go to the **Browse** tab.
3.  Search for `CommunityToolkit.Mvvm`.
4.  Select it, check your project, and click **Install**.

##### **Step 2: Refactor the ViewModel**

Now, we'll replace all our manual code with simple attributes.

1.  Open `MainViewModel.cs`.
2.  Change the class to inherit from `ObservableObject`. This class comes from the toolkit and already implements `INotifyPropertyChanged` for us.
3.  Use the `[ObservableProperty]` and `[RelayCommand]` attributes.

Your entire `MainViewModel.cs` file can now be simplified to this:

```csharp
using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;
using System.Windows; // For MessageBox

namespace HelloWpfApp
{
    // 1. Inherit from ObservableObject (or use [INotifyPropertyChanged] attribute for partial class)
    public partial class MainViewModel : ObservableObject
    {
        // 2. The [ObservableProperty] attribute generates the full property for you.
        // It will create a private field _username and a public property Username.
        [ObservableProperty]
        private string _username;

        [ObservableProperty]
        private string _password;

        // 3. The [RelayCommand] attribute generates the ICommand property.
        // It automatically finds the CanLogin method by convention (prefixing the method name with "Can").
        [RelayCommand(CanExecute = nameof(CanLogin))]
        private void Login()
        {
            MessageBox.Show($"Logging in with Username: {Username}");
        }

        private bool CanLogin()
        {
            return !string.IsNullOrEmpty(Username) && !string.IsNullOrEmpty(Password);
        }

        // We also need to tell the command to re-evaluate when our properties change.
        partial void OnUsernameChanged(string value)
        {
            LoginCommand.NotifyCanExecuteChanged();
        }

        partial void OnPasswordChanged(string value)
        {
            LoginCommand.NotifyCanExecuteChanged();
        }
    }
}
```

**What just happened?**
*   **`ObservableObject`:** We no longer need our own `INotifyPropertyChanged` implementation.
*   **`[ObservableProperty]`:** The source generator automatically creates the full property with the backing field and the call to `OnPropertyChanged`.
*   **`[RelayCommand]`:** The source generator creates a `LoginCommand` property of type `IRelayCommand`. It wires up the `Login` method as the `Execute` action and `CanLogin` as the `CanExecute` condition.
*   **`partial` methods (`OnUsernameChanged`):** The source generator creates these partial methods for us. We can implement them to run extra logic whenever a property changes. Here, we use them to tell the `LoginCommand` that it needs to re-check its `CanExecute` status.

Our ViewModel is now much shorter, cleaner, and easier to read, but it functions identically. **This is the modern, recommended way to write ViewModels.**

#### **3. Dependency Injection (DI) - Managing Your Objects**

So far, we've been creating our ViewModel like this:

`this.DataContext = new MainViewModel();`

This is called "hard-coding a dependency." The `MainWindow` is directly responsible for creating its own `MainViewModel`. What if `MainViewModel` needed other services to do its job, like a service to talk to a database or a web API?

```csharp
// What if our ViewModel needed this?
public MainViewModel(IUserService userService, ILogger logger) { ... }
```
Now, `MainWindow` would also have to know how to create an `IUserService` and an `ILogger`. This gets complicated quickly.

**Dependency Injection** is a pattern that solves this. You register all your services and ViewModels in a central location called a **DI Container**. Then, you simply ask the container for the object you need (like `MainWindow`), and the container automatically figures out how to build it and all of its dependencies.

##### **Step 1: Install the NuGet Package**

1.  Install `Microsoft.Extensions.DependencyInjection` from NuGet.

##### **Step 2: Configure the DI Container**

1.  Open `App.xaml.cs`. This is the perfect place to set up our services.
2.  Modify the file to look like this:

```csharp
using Microsoft.Extensions.DependencyInjection;
using System.Windows;

namespace HelloWpfApp
{
    public partial class App : Application
    {
        private readonly ServiceProvider _serviceProvider;

        public App()
        {
            IServiceCollection services = new ServiceCollection();

            // Register your services and ViewModels here
            services.AddSingleton<MainViewModel>(); // One instance for the entire app
            services.AddSingleton<MainWindow>(provider => new MainWindow
            {
                // The MainWindow gets its ViewModel from the DI container
                DataContext = provider.GetRequiredService<MainViewModel>()
            });

            _serviceProvider = services.BuildServiceProvider();
        }

        protected override void OnStartup(StartupEventArgs e)
        {
            var mainWindow = _serviceProvider.GetRequiredService<MainWindow>();
            mainWindow.Show();

            base.OnStartup(e);
        }
    }
}
```
3.  Finally, open `App.xaml` and **remove** the `StartupUri="MainWindow.xaml"` attribute. We are now launching the window manually from our code.

Now, your application is configured to use DI. When you need to add a new service, you just register it in `App.xaml.cs`, and you can request it in the constructor of any ViewModel that needs it. This makes your application loosely coupled and much easier to manage as it grows.

The world of WPF is vast, but you have built an incredibly solid foundation. Happy coding
